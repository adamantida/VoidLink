## 3. Находки

### S2

#### BIZ-01 · Лимиты/федерация · S2 · высокая
**JOIN_FED обходит лимит входов в группу (`join_rate`), ради которого он и заведён**

Evidence — `crates/server/src/lib.rs:3002-3012`:
```rust
    if !s.groups[&gid].members.contains_key(me) {
        {
            let g = &s.groups[&gid];
            anyhow::ensure!(!g.banned.contains_key(me), "вы забанены в этой группе");
            anyhow::ensure!(
                !g.private,
                "группа приватная: вход только по приглашению владельца"
            );
            anyhow::ensure!(!g.full(), "группа заполнена");
        }
        let ip = s.ip_for(*me).context("нет свободных адресов на сервере")?;
```
Сравнить с обычным входом — `crates/server/src/lib.rs:4085-4094`:
```rust
            // Адрес — тот же, что у identity в остальных группах.
            let ip = s.ip_for(me).context("нет свободных адресов на сервере")?;
            let g = s.groups.get_mut(&gid).unwrap();
            // Каждый вход — ротация, а выход за ним — ротация с отзывом:
            // чехарда JOIN/LEAVE (новые identity бесплатны) ломала бы трафик
            // группы. Владельцу — без лимита.
            anyhow::ensure!(
                g.owner == me || g.joins.take(sh.limits.join_rate, sh.limits.join_burst),
                "слишком много входов в группу — повторите позже"
            );
```
`g.joins.take` вызывается **только** здесь (`grep joins\.take` → один вызов,
`lib.rs:4092`). В `join_fed` ни лимита, ни кулдауна `REJOIN_COOLDOWN` нет; при
`own` (своя группа) каждый вход — `g.rotate(false); g.bump()` (`lib.rs:3027-3031`)
и `publish_claims` всем пирам (`lib.rs:3042-3048`). Условие «вход не участника» —
то же, что у `JOIN_GROUP`; `JOIN_FED` доступен любому клиенту сервера с
включённой федерацией, а uuid публичных групп клиент получает кадром `FED_GROUPS`
(`lib.rs:2950-2975`, шлётся с каждым `GROUP_LIST`, `lib.rs:3327`).

**Сценарий.** Клиент с валидной identity в цикле шлёт `JOIN_FED(uuid)` →
`LEAVE_GROUP(gid)`. Потолок — `ctrl_rate` = 50/с на сессию (`lib.rs:183-184`), а
не 1/с с запасом 10, как задумано для группы. Каждый вход — ротация ключа и
`rev`+1 (дельта всем), каждый выход — ротация с `revoke_prev` (`lib.rs:4148`).
**Влияние.** Инвариант, записанный в `Limits::join_rate` («чехарда JOIN/LEAVE не
ломает трафик группы»), не держится для федерированных групп: участники получают
непрерывные ротации, при пропуске дельты и скачке эпохи прошлый ключ забывается
(`PROTOCOL.md:374-377`) — кадры отбрасываются. Дополнительно каждый вход
рассылает `FED_ADDR_PUSH` до 64 пирам — усилитель на 64 кадра с одного.
Принятый риск §15 №9 («Churn… в пределах лимитов; лимит входов на группу,
кулдаун повторного входа») в этой ветке не ограничен — это и есть находка, а не
сам риск.
**Как проверить.** Два сервера с `--federate` и пином друг на друга; клиент A
создаёт публичную группу; клиент B на втором сервере получает uuid из
`FED_GROUPS`, шлёт `JOIN_FED`/`LEAVE_GROUP` в цикле 10 с; смотреть в логе
сервера-владельца число `join_fed:`/`leave:` и рост `epoch`; ожидаемо — ни
одного «слишком много входов».
**Рекомендация.** В `join_fed` применить тот же `g.joins.take(...)` +
`REJOIN_COOLDOWN` по `g.left` (для `own`-группы) и лимит на `request_join` для
реплики; `publish_claims` — не на каждый вход, а по факту смены адреса identity.
Добавить тест-аналог `join_rate` для `JOIN_FED`.

**Реплика выдаёт членство и ключ группы до согласия владельца; отказа не
существует; баны не реплицируются → обход бана и чтение трафика**

Согласие приходит позже и может не прийти вовсе — `crates/server/src/lib.rs:2898-2925`:

`continue` — и всё: NACK нет, отката на реплике нет, а `group_snap`

(`lib.rs:3005`) на ней бессмысленна.

**Сценарий.** Публичная группа G с владельцем O на сервере S1, реплика G на S2
(любой пир). Identity X забанен в G на S1. X подключается к S2, узнаёт uuid из
`FED_GROUPS` и шлёт `JOIN_FED`: на S2 он проходит (банов там нет), получает
`GROUP_STATE` **с ключом группы** и попадает в `members` реплики. Заявка на S1
отклоняется по бану, но X уже участник S2 — ему релеят кадры группы, а его кадры
принимают как кадры участника (`src_ip` = его адрес).
**Влияние.** Обход бана (единственного механизма, который по §15 №10 «BAN
запрещает вход»); раскрытие ключа эпохи и чтение трафика группы до следующей
ротации у владельца; несанкционированный участник навсегда остаётся в составе
реплики, потому что `publish` диффит против собственной публикации (`mine`) и
`MemberRemove` для фантома не пошлёт никогда — только полный `FED_GROUP_PUSH`
(`federation.rs:931-955`). Предусловие: включена федерация (`--federate`) и есть
хотя бы один пир-реплика; группа публичная (приватную `join_fed` отвергает,
`lib.rs:3006-3009`).
**Как проверить.** S1+S2 с пином; группа G публичная; X забанен на S1; X шлёт
`JOIN_FED` на S2 → ожидаем `GROUP_STATE` с ключом; на S1 в логе — ни
`federation: вход`, ни отказа; затем участник Y на S2 шлёт кадр группе → X его
расшифровывает.
**Рекомендация.** Ввести явный отказ федеративного входа (`FED_JOIN_REJECT` с
uuid/pk/причиной) и откат членства на реплике; реплицировать `banned` (или
минимум `banned`-хэши) в `GroupSnap`/дельте; при `own == false` не выдавать ключ
до подтверждения (ждать дельту от владельца), а на время ожидания не включать pk
в `members`. Тест: забаненный не получает ключ ни на одном сервере.

#### BIZ-03 · Identity/невидимка · S2 · высокая
**Невидимка выдаётся в mesh-секции GROUP_STATE/GROUP_UPDATE: видно, что он
онлайн, и его статический x-ключ**

Evidence — `crates/server/src/lib.rs:2288-2303` (mesh-секция строится по всем
участникам с живой сессией):
```rust
    let mut mesh: Vec<pl::MeshEntry> = g
        .members
        .iter()
        .filter_map(|(pk, m)| {
            let (_, ses) = s.session_of(pk)?;
            if !mesh_fresh(ses) {
                return None;
            }
            let x_pub = ses.x_pub?;
            Some(pl::MeshEntry {
                ip: m.ip,
                x_pub,
                caps: ses.caps,
            })
        })
        .collect();
```
При этом соседняя функция того же файла невидимок **исключает** — `lib.rs:2331`:
```rust
            if ses.ed_pub == *me || ses.invisible || !mesh_fresh(ses) {
                return None;
            }
```
и это заявлено в `docs/PROTOCOL.md:932-933`: «Бутстрап: `MESH_SEED` от сервера
(≤ 16 ближайших онлайн-сессий по XOR; невидимки не выдаются)». Заявленный
контроль: `docs/TUI.md:274` «другие видят вас офлайн», `docs/CLIENT.md:577` то же.
Клиент публикует `MESH_INFO` независимо от невидимости —
`crates/client/src/engine.rs:3492-3500`:
```rust
    if connected && (st.info_due || now.duration_since(st.last_info) >= MESH_INFO_EVERY) {
        st.info_due = false;
        st.last_info = now;
        let caps = my_mesh_caps(env);
        st.send_ctrl(
            env,
            ctrl::MESH_INFO,
            &payloads::enc_mesh_info(&env.identity.x_pub(), caps),
        );
    }
```
Тот же дефект в дельте: `lib.rs:3104-3116` берёт `x_pub`/`caps` из сессии без
проверки `invisible`.

**Сценарий.** U включает невидимку и состоит в группе G с V. V получает
`GROUP_STATE`: в `MemberInfo` U — `online=false`, endpoint и кандидаты пусты, но
в mesh-хвосте есть запись с `ip` U и `x_pub`. Запись существует ровно пока жива
сессия U (`MESH_TTL_MS` = 15 мин с повтором раз в 5 мин), то есть её наличие =
«U онлайн сейчас». Дальше V как участник G делает `MESH_HELLO` на `x_pub` U —
рукопожатие подписано ed-ключом из состава группы, и клиент U его принимает: V
узнаёт endpoint U и RTT.
**Влияние.** Основная обещанная функция «невидимки» (скрыть присутствие) не
работает против участников общих групп; дополнительно раскрывается статический
x-ключ, который по документации должен выдаваться только как контакт DHT и
только не-невидимкам. Предусловия: mesh включён (по умолчанию `true`,
`crates/client/src/store.rs:157`) и есть общая группа — то есть ровно те, кто и
так видит состав.
**Как проверить.** Два клиента в одной группе, у одного `invisible on`; на втором
разобрать `GROUP_STATE` (или открыть карточку участника, где видны mesh-метрики):
в mesh-хвосте есть ip невидимки. Затем `ping` по его имени/pk — mesh-сессия
устанавливается.
**Рекомендация.** В `group_state` и в mesh-хвосте `push_update` применить тот же
фильтр, что в `mesh_seed`: `ses.invisible → None` (и не публиковать `MESH_INFO`
от невидимки на клиенте). Записать правило в `PROTOCOL.md` §4.2 явно и покрыть
тестом «невидимки нет в mesh-секции».

#### BIZ-04 · Группы/владение · S3 · высокая
**Владелец может выйти из своей группы (CLI/демон), и группа остаётся без

`crates/server/src/lib.rs:4133-4151`:

Запрет есть только в TUI — `crates/client/src/tui/app.rs:2761-2774`:
```rust

        match self.selected_group() {
            Some(g) if g.mine => {
```
(то есть выход доступен лишь для «моих» групп, а «моя» = членство, не владение).
CLI выходит без проверки — `crates/client/src/main.rs:647-656`: `"leave" => { let gid
= parse_gid(...); … conn.send_ctrl(ctrl::LEAVE_GROUP, …); println!("вышел из {gid}

`lib.rs:906-908`, а `mine` в `GroupSummary` — по членству, `lib.rs:3177`.

**Сценарий.** Владелец 16 групп (потолок) выполняет `tunnel-client leave 5`.
Группа 5 остаётся с `owner = он`, но `mine = false`: из `GROUP_LIST` она исчезает
(приватная — исчезает и для всех, кроме участников, `lib.rs:3178-3180`), в TUI её
больше нет, а квота `max_owned_groups` занята. Управлять можно только по памяти
через CLI по gid. Если identity владельца потеряна (новый профиль), группа
навсегда остаётся без управляющего: удалить её нельзя никому, gid не
освобождается, надгробия нет.
**Влияние.** Нарушен инвариант, который проект сам формулирует для аренды:
«**владелец группы не выселяется**: группа осталась бы без управляющего
(удалить, кикнуть, пригласить стало бы некому)» (`docs/SERVER.md:127-129`). Здесь
тот же результат достигается добровольным выходом.
**Как проверить.** Создать группу, выполнить `tunnel-client leave <gid>`, затем
`tunnel-client groups` — группы нет; `create` ещё 15 групп — на 16-й «лимит
групп: во владении уже 16».
**Рекомендация.** На сервере в `LEAVE_GROUP` отвергать выход владельца
(`g.owner == me`) с подсказкой «передайте владение или удалите группу»; в CLI
проверять до отправки. Если выход владельца нужен как продукт — при выходе
передавать владение самому старому участнику либо удалять группу с надгробием.

#### BIZ-05 · Друзья/приватность · S3 · высокая
**FRIEND_GROUPS отдаёт публичные группы любой identity любому, кто знает её ключ:
дружба не проверяется**

Evidence — `crates/server/src/lib.rs:3807-3822`:
```rust
        ctrl::FRIEND_GROUPS => {
            let target = pl::dec_pubkey(payload)?;
            let mut groups = Vec::new();
            for g in s.groups.values() {
                let i_am = g.members.contains_key(me);
                let he_is = g.members.contains_key(&target);
                if !(he_is && (!g.private || i_am)) {
                    continue;
                }
                groups.push(pl::FriendGroup {
                    gid: g.id,
                    name: g.name.clone(),
                    private: g.private,
                    shared: i_am && he_is,

```
Ни `s.friends.is_friend(me, target)`, ни проверки, что `target` вообще друг, нет —
в отличие от `FRIEND_*_RCVD`, где адресат вычисляется из заявки.
**Сценарий.** Friend code — это base32 публичного ключа (`protocol/src/lib.rs:291-298,
318-340`), его публикуют в чатах и тикетах. Любой, кто его видел, шлёт
`FRIEND_GROUPS(pk)` и получает имена и gid всех публичных групп жертвы на этом
сервере (и общие с запросившим). Дружба не нужна, приглашение не нужно.
**Влияние.** Раскрытие социального графа и имён групп (часто содержательных:
«work», «family») тому, кто знает код. Невидимка не помогает: она скрывает
онлайн-статус, но не членство. Документация обещает это только про друга —
`docs/PLAN.md:112-113`: «Enter по другу → карточка: в каких группах он состоит
(запрос серверу: публичные группы друга + общие с тобой)».
**Как проверить.** Два клиента без дружбы; второй шлёт `FRIEND_GROUPS` с ключом
первого → получает список его публичных групп.
**Рекомендация.** Требовать принятую дружбу (или общую группу) для
`FRIEND_GROUPS`; иначе — `ERROR`. Обновить `PROTOCOL.md` (0x0D) и добавить тест
«незнакомец не получает список групп».

#### BIZ-06 · Клиент/автовход · S3 · высокая
**Автовход по gid переживает удаление группы: после `tomb_ttl` клиент молча
входит в чужую группу с тем же номером**

Evidence — вход по автовходу на первом `GROUP_LIST`, `crates/client/src/engine.rs:4850-4857`:
```rust
                if std::mem::take(&mut st.autojoin_due) {
                    let auto = env.cfg.lock().unwrap().autojoin.clone();
                    for gid in auto {
                        let live = env.groups.lock().unwrap().contains_key(&gid);
                        if !mine.contains(&gid) && !live && !st.leaving.contains_key(&gid) {
                            st.send_ctrl(env, ctrl::JOIN_GROUP, &payloads::enc_gid(gid));
                        }
                    }
                }
```
Ошибка входа не несёт gid и не чистит автовход — `engine.rs:5005-5009`:
```rust
        ctrl::ERROR => {
            if let Ok(text) = payloads::dec_error(payload) {
                env.emit(Event::Error(text));
            }
        }
```
Чистка есть только для групп, которые **есть локально**, — `engine.rs:5213-5227`
(`reconcile` перебирает `g.iter()`), а список групп на клиенте не персистится
(`crates/client/src/store.rs:52-97`: `Config` групп не содержит) — после
перезапуска TUI/движка он пуст. Автовход пополняется автоматически при каждом
входе — `engine.rs:5382-5388`: `if is_new { … env.autojoin_add(st.gid); }`.
Надгробие держит gid лишь `tomb_ttl` = 7 дней (`lib.rs:199`, `PROTOCOL.md:546-558`).
Дополнительно: приглашение в gid из автовхода входит **без подтверждения** —
`engine.rs:5201-5204`:
```rust

    if in_autojoin {
        st.send_ctrl(env, ctrl::JOIN_GROUP, &payloads::enc_gid(gid));
    }
```
**Сценарий.** U состоял в публичной группе 7 и вышел/был кикнут, пока клиент был
выключен; группу удалили. U запускает клиент: `GROUP_LIST` без 7, локальных групп
нет → `reconcile` ничего не чистит, автовход шлёт `JOIN_GROUP(7)`, сервер
отвечает «группа не существует», запись остаётся в `client.json` навсегда. Через
7+ дней кто-то создаёт группу 7 (номер свободен) — при следующем подключении U
молча в неё входит: получает её ключ, его имя и адрес видит чужой владелец, его
трафик идёт в чужую группу.
**Влияние.** Тихая потеря контроля над тем, в каких группах состоит пользователь;
раскрытие его имени/адреса посторонним. Проект сам считает этот класс проблем
реальным: `autojoin_by_server` заведён именно потому, что «gid у каждого сервера
свои, и при смене сервера чужие gid вошли бы в посторонние группы»
(`store.rs:83-86`).
**Как проверить.** Клиент: `autojoin` содержит 7, группы 7 на сервере нет (или
удалена) → в логе «группа не существует», `client.json.autojoin` по-прежнему `[7]`;
создать новую группу с gid 7 другим клиентом → переподключение входит в неё.
**Рекомендация.** Хранить в автовходе не только gid, но и отпечаток группы (имя +
`owner`/uuid); при входе сверять и при расхождении снимать автовход и спрашивать
пользователя. `ERROR` дополнить gid (или слать `KICKED`-подобный отказ на
`JOIN_GROUP`), чтобы клиент снимал мёртвую запись. Приглашение в gid из
автовхода — не входить без подтверждения, если владелец/имя не совпадают.

#### BIZ-07 · Друзья/TUI · S3 · высокая
**Панель друзей показывает «○ не в сети» для друга без общих групп, даже если он
в сети; документация обещает обычный online/offline**

Evidence — `crates/client/src/tui/app.rs:777-801`:
```rust

            // офлайн-участник держит lease и остаётся в списке участников.
            let known: HashSet<[u8; 32]> = snap
                .groups
                .iter()

                .collect();
```
Заявление — `docs/TUI.md:97`: «- **Друзья.** `●` — друг в сети, `○` — не в сети.
Справа указано число общих групп.» Сервер присутствие друзей не сообщает вовсе:
в `FriendInfo` полей онлайн-статуса нет — `crates/protocol/src/payloads.rs:1088-1097`

показывается никогда.
**Как проверить.** Два клиента, взаимная дружба, общих групп нет, оба в сети:
панель друзей у обоих — «○».
**Рекомендация.** Либо добавить в `FRIEND_LIST` признак присутствия (с учётом
невидимости — тогда «невидимка» и здесь даст `online=false`), либо честно
описать в `TUI.md`/`CLIENT.md`: «● — друг онлайн в общей группе». Третий вариант —
показывать «?» вместо «○» при отсутствии общих групп.

#### BIZ-08 · Адреса/аренда · S4 · высокая

## 4. Проверено — находок нет

- **Модерация.** `KICK`/`BAN`: только владелец, нельзя владельца
  (`lib.rs:4427-4428`); `BAN` идемпотентен, лимит `max_bans_per_group` с
  подсказкой «исключите без бана» (`lib.rs:4429-4432`); `KICK`/`BAN` снимают
  приглашение и `detached`, ротируют ключ с `revoke_prev` и шлют `KICKED` с
  ревизией (`lib.rs:4433-4476`); `UNBAN` идемпотентен и отвечает `ADMIN_INFO`
  (`lib.rs:4487-4503`); `TRANSFER_OWNER` требует участника, уважает лимит нового
  владельца, идемпотентен для себя (`lib.rs:4504-4526`). Баны и имена банов
  персистятся (`persist.rs:179-181`, `lib.rs:1410-1414`) и переживают рестарт.

- **Надгробия и gid.** `alloc_gid` не выдаёт живой надгробный gid, при полном

  ревизию, `detached` снимается при JOIN/LEAVE/KICK/BAN (`lib.rs:4166-4191`,
  `4102`, `4147`, `4436`); отключённый не считается онлайн и не получает релей
  (`lib.rs:2253-2265`, `3159-3164`).
- **Невидимка (кроме BIZ-03/BIZ-10).** `MemberInfo`: `online=false`, endpoint и
  кандидаты пусты (`lib.rs:2253-2265`); в `GroupSummary.online` не считается, себя

  (`lib.rs:2331`); `PRESENCE_ACK` шлётся всегда, повтор без изменения не двигает
  ревизию (`lib.rs:3907-3924`).
- **Адреса и аренда.** Один адрес на identity, общий для всех групп

  (`profile.rs:164-176`); импорт не затирает identity без `--force`
  (`main.rs:284-286`); KDF не ниже `KDF_MIN_ITERATIONS` и не выше
  `KDF_MAX_ITERATIONS` (`profile.rs:40-43`); friend code — 52 символа Crockford,
  терпим к регистру/разделителям/кириллице, «TUN» однозначен (нет `U` в алфавите)
  (`protocol/src/lib.rs:316-399`) — коллизий на 256 битах нет, «короткий код» в UI
  только отображение.
- **DNS `*.vl`.** Резолв по составу моих групп, `<member>.<group>.vl` с проверкой
  метки группы, при совпадении имени — меньший gid, IPv6 из того же IPv4
  (`engine.rs:5970-6004`, `ipv6::v6_of`) — согласовано с `my_ip` и IPv6-мэппингом.
- **Офлайн-режим.** Очередь `ui-pending.json` атомарна, переживает перезапуск,
  битый файл не роняет TUI (`offline.rs:77-90`, тесты 1014-1024); сетевые команды
  офлайн отклоняются (`offline.rs:398-406`); при совпадении конфига с демоном
  очередь очищается как уже применённая (`offline.rs:298-309`).
- **Мульти-сервер.** `switch_server` сбрасывает сессию, группы, `leaving`,
  `tombs`, `pending_leave` и подсказки федерации, `autojoin` — по серверам
  (`engine.rs:4748-4811`, `store.rs:79-86`); общая identity сохраняется.

## 5. Гипотезы и вопросы к владельцу

**Гипотезы (не подтверждены прогоном, в находки не включены):**

1. **Двойное применение офлайн-тоглов.** `apply_local` применяет правку к конфигу и
   кладёт команду в очередь (`offline.rs:356-363`); при `adopt` очередь
   проигрывается, если вид конфига демона не совпал с локальным
   (`offline.rs:281-316`). Для `Cmd::ToggleAutojoin` (`offline.rs:446-451`) и
   `DelServer{idx}` (индексный) повтор не идемпотентен: при расхождении любого
   другого поля (например, демон уже записал `active_server`) настройка может
   вернуться в исходное состояние или удалиться не тот сервер. Проверяемо только
   на живом демоне.
2. **Точка «в сети» и релей при мёртвом сервере.** `SERVER_TIMEOUT` снимает
   `connected` (`engine.rs:3139-3141`), но бейдж «◆ N прямых» считается по
   свежести `direct_addr` (`path.rs:60-68`); при живом прямом канале и мёртвом
   сервере список участников не обновляется — возможен «прямой путь» до
   участника, которого уже нет в группе. Нужен стенд.
3. **L3 в TUI.** `PathKind` знает только `Direct`/`Server`/`PeerRelay`
   (`path.rs:88-95`), кросс-серверный релей клиент видит как «◇ сервер» —
   `NETWORKING.md:373` это признаёт («клиент видит его как серверный путь»), а
   `NETWORKING.md:108` ставит L3 «✅ работает (T4)». Пользователь не может узнать,
   что трафик идёт через **чужой** сервер (риск §15 №19). Считаю это осознанным
   ограничением, а не дефектом, но стоит показать в карточке участника метку
   «через федерацию».
4. **`max_friends` на приём.** Лимит проверяется в `accept` и при встречной заявке
   (`friends.rs:200-203`), но не в `request`: identity с 512 друзьями может
   накопить 64 входящие заявки, которые нельзя принять, пока не удалишь друга.
   Это UX-ловушка, а не дыра.

**Вопросы к владельцу / запросы на прогон (Linux-хост у ведущего):**

- **Федерация.** Нужен прогон «забаненный входит через реплику» (BIZ-02) и «churn
  `JOIN_FED`/`LEAVE`» (BIZ-01) на двух серверах — это единственный способ
  подтвердить S2 стендом. Сценарий: `--federate --peer <другой> --fed-pool`,
  клиент A создаёт публичную группу, B банит X, X шлёт `JOIN_FED`.
- **Невидимка.** Ожидаемое поведение: должен ли невидимка вообще попадать в
  mesh-секцию `GROUP_STATE` (сейчас попадает, BIZ-03)? Если да — надо
  зафиксировать это в `PROTOCOL.md` и снять обещание «видят офлайн» из TUI/CLIENT.
- **Выход владельца.** Считать ли выход владельца из своей группы легальным
  (BIZ-04)? Если да — нужен механизм «группа без владельца» (автопередача или
  удаление), иначе админ остаётся с неудаляемой группой.
- **Автовход.** Допустимо ли, что автовход хранит только gid (BIZ-06)? Если да —
  нужен срок жизни записи автовхода, сравнимый с `tomb_ttl`.
- **Принятые риски.** Прошу подтвердить, что §15 №9 (churn «в пределах лимитов»)
  и §15 №19 (федерация) не покрывают BIZ-01/BIZ-02 — по коду не покрывают.

## 6. Итог

Ядро правил — групп, владения, модерации, приглашений, надгробий, аренды адресов —
сделано аккуратно и с редкой для проекта дисциплиной: каждое правило имеет
комментарий с причиной, лимиты из `CONFIG.md`/`SERVER.md` совпадают с
`Limits::default` до последнего числа, а состояния, которые легко потерять
(надгробия, отметки выхода, баны, аренды), персистятся и переживают рестарт. В
этой части аудита подтверждённых дефектов нет — есть одно следствие (`BIZ-04`,
выход владельца) и одна ошибка порядка проверок (`BIZ-08`).

Главные риски лежат на границе этапа 9. Федерация добавила вторую точку принятия
решения о членстве и не привела её к правилам основной: реплика выдаёт ключ
группы до согласия владельца, отказа не существует, баны не реплицируются
(`BIZ-02`), а `JOIN_FED` не подчиняется лимиту входов, ради которого написан
`join_rate` (`BIZ-01`). Оба дефекта — в одной ветке `join_fed` и оба
устраняются приведением её к правилам `JOIN_GROUP` плюс явным отказом
федеративного входа. Это единственные находки, которые я оцениваю как блокирующие
для эксплуатации федерации в публичном режиме.

Третья S2 — «невидимка» против mesh (`BIZ-03`): сервер сам, в соседней функции,
исключает невидимок из `MESH_SEED`, но в mesh-секции `GROUP_STATE`/`GROUP_UPDATE` отдаёт их ip и x-ключ, а клиент публикует `MESH_INFO` не глядя на
флаг. Обещанный контроль «другие видят вас офлайн» не держится против участников
общих групп — это не принятый риск §15, а незамеченная асимметрия двух фильтров.

Остальное — дрейф заявлений и узкие ложные состояния интерфейса (`BIZ-05`…`BIZ-12`): список групп любого ключа без дружбы, автовход по gid после
переиспользования номера, «○ не в сети» у друга без общих групп, бейдж
невидимости без подтверждения. По отдельности они S3/S4, но вместе создают
класс проблем «интерфейс знает меньше, чем обещает»: их стоит закрыть одной
волной правок документации и трёх точечных проверок в коде, не дожидаясь
следующего этапа.
