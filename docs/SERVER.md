# Сервер VoidLink (`tunnel-server`)

Сервер — точка встречи и релей: хранит группы, адреса пользователей, инвайты, раздаёт
endpoint-ы для hole punching и пересылает трафик, пока прямого канала нет.
Работает на Linux (собирается и на macOS/Windows — для отладки). Наружу нужен
один UDP-порт (по умолчанию 5555).

## Сборка под Linux

На самом сервере (или любой Linux-машине той же архитектуры):

```
cargo build --release -p tunnel-server
# → target/release/tunnel-server
```

С macOS/Windows — кросс-сборка статического бинарника (не зависит от glibc
на VPS):

```
rustup target add x86_64-unknown-linux-musl
cargo install cargo-zigbuild        # или cross
cargo zigbuild --release -p tunnel-server --target x86_64-unknown-linux-musl
# → target/x86_64-unknown-linux-musl/release/tunnel-server
```


## Установка (systemd)

```
sudo infrastructure/linux/install-server.sh [путь/к/tunnel-server] [--listen 0.0.0.0:5555]
```

Скрипт:

- создаёт системного пользователя `tunnel` (без shell и home);
- кладёт бинарник в `/opt/tunnel/tunnel-server`, юнит —
  `/etc/systemd/system/tunnel-server.service`;
- создаёт `/etc/default/tunnel-server` (адрес `TUNNEL_LISTEN` и доп. флаги
  `TUNNEL_ARGS`), если его ещё нет;
- включает и запускает службу, печатает **Server code** (`TUN-…`) — его
  вписывают клиенты (`add-server <ip:порт> <TUN-код>`);
- повторный запуск — обновление: стоп → замена бинарника → старт,
  `server.json` не трогается.

Состояние — `/var/lib/tunnel/server.json` (`StateDirectory=tunnel`, права
0700). Юнит ужесточён: `NoNewPrivileges`, `ProtectSystem=strict`,
`ProtectHome`, `PrivateTmp`, `PrivateDevices`, пустой набор capabilities,
фильтр системных вызовов. Писать сервер может только в `/var/lib/tunnel`.

Файрвол: открыть только UDP-порт сервера, например `ufw allow 5555/udp`.

Полезное:

```
systemctl status tunnel-server
journalctl -u tunnel-server -f             # события и сводка раз в 5 минут
sudoedit /etc/default/tunnel-server && sudo systemctl restart tunnel-server
```


## Флаги

```
tunnel-server [адрес=0.0.0.0:5555] [флаги]
tunnel-server rotate-key [--data <dir>]
tunnel-server unpeer <addr|hex ed> [--data <dir>]
```

Позиционный аргумент — адрес прослушивания (UDP и TCP на одном порту).
Неизвестный флаг — ошибка запуска (`неизвестный флаг … (см. --help)`), и
служба под systemd уходит в цикл перезапусков: не добавляйте в `TUNNEL_ARGS`
ничего, чего нет в таблицах ниже.

| флаг | по умолчанию | смысл |
|---|---|---|
| `--data <dir>` | `tunnel-data` | каталог состояния (`server.json`); в юните — `/var/lib/tunnel` |
| `--workers N` | 0 = по ядрам, до 8 | потоков-воркеров на UDP-сокете |
| `-q`, `--quiet` | — | полная тишина: не печатаются ни события, ни сводка раз в 5 минут, ни строка `Server code: TUN-…` |
| `--tcp` / `--no-tcp` | включён | TCP-фолбэк на том же порту, что UDP (см. «TCP-фолбэк») |
| `--metrics <адрес>` | выключено | HTTP-эндпоинт метрик `/metrics` и `/healthz` (см. «Метрики»); слушать только на `127.0.0.1` |
| `--federate` | выключено | федерация серверов: `SRV_HELLO`/`ACK`, TOFU-пиннинг, репликация групп и адресов, `FED_RELAY`, `SERVER_HINT` (см. «Проба, mesh и федерация») |
| `--peer <addr>` | — | явный пин сервера-пира, можно повторять |
| `--fed-pool <addr>` | — | сервер общего пула адресов федерации, можно повторять |

Лимиты (значения по умолчанию — `Limits::default()` в `crates/server/src/lib.rs`):

| флаг | по умолчанию | смысл |
|---|---|---|
| `--relay-rate R` / `--relay-burst B` | 4000 / 8000 | релей: фреймов/с на сессию и запас |
| `--ctrl-rate R` / `--ctrl-burst B` | 50 / 100 | управляющие фреймы на сессию |
| `--hello-rate R` / `--hello-burst B` | 5 / 20 | HELLO/HELLO3, RESET и открытые ответы на них — в секунду на IP (IPv6 — на /64) |
| `--plain-rate R` / `--plain-burst B` | 2000 / 4000 | открытые ответы без подтверждённого адреса (CHALLENGE, UNSUPPORTED, RESET) — на весь сервер |
| `--join-rate R` / `--join-burst B` | 1 / 10 | входы не-участников в группу — в секунду на группу |
| `--session-timeout <сек>` | 30 | сессия без пакетов столько — офлайн |
| `--max-owned-groups N` | 16 | групп во владении одной identity |
| `--invite-ttl-days N` | 7 | срок жизни приглашения, дней |
| `--lease-ttl-days N` | 30 | аренда адреса оверлея без активности, дней; `0` — не освобождать |
| `--max-invites-per-group N` | 256 | приглашений на группу |
| `--max-bans-per-group N` | 1024 | банов на группу |
| `--max-invites-per-target N` | 64 | живых приглашений одной identity по всем группам |

Лимиты друзей (issue #24) заданы в `Limits` и пока не выведены флагами
`tunnel-server`: `friend_req_ttl` — 7 дней, `max_friends` — 512 принятых пар
на identity, `max_friend_reqs_per_target` — 64 живых заявки, адресованных
одной identity (раздел 9 [PROTOCOL.md](PROTOCOL.md)).

Параметры `*-rate` должны быть числами > 0, `*-burst` — ≥ 1, таймаут и срок
приглашения — ≥ 1. `--lease-ttl-days` принимает `0` (освобождение выключено)
и не больше 3650 дней. Подробнее о лимитах — раздел 9 [PROTOCOL.md](PROTOCOL.md).

### Подкоманды

| Команда | Что делает | `--data` |
|---|---|---|
| `rotate-key [--data <dir>]` | Смена ключа сервера: старый ключ подписывает новый, звено дописывается в `server.json → rotations`; печатает старый и новый Server code, pubkey и число звеньев. | `tunnel-data` (в юните — `/var/lib/tunnel`) |
| `unpeer <addr \| hex ed> [--data <dir>]` | Снимает TOFU-пин федерации по адресу пира или hex его ed25519-ключа. | `tunnel-data` |

`--data` у подкоманд — тот же каталог, что у сервера: по умолчанию
`tunnel-data` относительно текущего каталога. Обе команды берут
advisory-блокировку `server.json.lock`. `rotate-key` можно выполнять при
запущенном сервере: новый ключ вступит в силу после перезапуска и не будет
затёрт. `unpeer` требует остановленного сервера — работающий вернёт пин из
памяти (см. «Снятие пина федерации»).


## server.json

Файл пишет и читает `tunnel-server` в каталоге `--data`. В нём identity сервера,
группы, участники, баны, приглашения и цепочка ротации ключа. Структура —
`Persisted` и `PGroup` в `crates/server/src/persist.rs`. Файл переписывается
раз в ~3 секунды, если состояние изменилось, а срочные события (кик, бан, выход,
удаление группы) сохраняются не чаще раза в 200 мс.

Файл содержит приватные ключи сервера. Потеря или подмена файла означает
новую identity: клиенты, закрепившие старый ключ, перестанут подключаться.
Резервные копии — в [SERVER.md](SERVER.md#резервная-копия-serverjson).

### Структура server.json

| Поле | Тип | Описание |
|---|---|---|
| `ed_seed` | массив из 32 байт | Приватный ключ ed25519 сервера (identity, на которую пиннятся клиенты). |
| `x_seed` | массив из 32 байт | Сид X25519 для рукопожатия. |
| `next_gid` | `u32` | Следующий свободный номер группы. |
| `rotations` | массив строк | Цепочка ротации ключа: hex 160-байтных звеньев, от старых к новым. Пишет `rotate-key`. По умолчанию пусто. |
| `user_ips` | объект | hex pubkey → адрес оверлея (`u32`): один на все группы identity. По умолчанию пусто (файл v3 — адреса берутся из групп). |
| `lease_seen` | объект | hex pubkey → unix мс последнего продления аренды адреса (issue #21): по нему истекает `--lease-ttl-days`. По умолчанию пусто — всем арендам ставится отсчёт от момента загрузки. |
| `groups` | массив `PGroup` | Группы сервера. |
| `federation` | объект | Федерация (этап 9): `peers` — закреплённые по TOFU пиры (≤ 64, снять пин — `unpeer`, см. [SERVER.md](SERVER.md#снятие-пина-федерации-unpeer)); `groups` — uuid ↔ gid и сервер-источник правды; `addr_claims` — заявки на адреса общего пула. По умолчанию пусто. |
| `deleted` | массив `PTomb` | Надгробия удалённых групп: `{gid, name, owner, rev, at_ms}`; живут 7 дней (`tomb_ttl`). |
| `left` | массив `PLeft` | Недавние выходы: `{pk, gid, at_ms}`; приватная группа пускает только по новому приглашению 10 минут (`left_ttl`). |
| `friends` | объект | Дружбы и заявки (issue #24): `requests` (7 дней) и `edges` — принятые пары. |

Поля `PGroup`:

| Поле | Тип | По умолчанию | Описание |
|---|---|---|---|
| `id` | `u32` | — | gid группы. |
| `name` | строка | — | Название. |
| `owner` | строка | — | hex pubkey владельца. |
| `private` | bool | `false` | Закрытая группа: вход только по приглашению. |
| `key` | массив из 32 байт | — | Текущий групповой ключ. |
| `epoch` | `u32` | `0` | Номер группового ключа (раздел 5 спецификации). Растёт при ротации. |
| `rev` | `u32` | `0` | Ревизия состояния группы. |
| `revoke_prev` | bool | `false` | Последняя ротация отзывает прошлый ключ (LEAVE, KICK, BAN). |
| `members` | массив пар `[hex pubkey, ip]` | — | Участники и выданный им адрес в сети группы (`ip` — `u32`). |
| `banned` | массив строк | `[]` | hex pubkey забаненных. |
| `invites` | массив строк | `[]` | hex pubkey приглашённых, ещё не ответивших. |
| `invite_times` | объект | `{}` | hex pubkey приглашения → время приглашения, unix в миллисекундах. |
| `invite_names` | объект | `{}` | hex pubkey приглашённого → последнее известное имя. |
| `member_names` | объект | `{}` | hex pubkey участника → имя. Офлайн-участники после рестарта показываются с последним именем, а не «…». |
| `member_status` | объект | `{}` | hex pubkey участника → статус. |
| `ban_names` | объект | `{}` | hex pubkey забаненного → последнее имя (ADMIN_INFO). |

Поля, добавленные в v3, имеют значения по умолчанию, поэтому файл v2 читается
без правок (см. [Миграция](#миграция-serverjson)).

### Срок жизни приглашений и лимиты на группу

- Приглашение живёт `invite_ttl` (по умолчанию 7 дней, флаг `--invite-ttl-days`).
  Отсчёт идёт от `invite_times`. После загрузки старого файла, где таких
  времён нет, срок начинается с момента загрузки.
- На группу действуют ограничения `Limits`: не больше **256** приглашений
  (`--max-invites-per-group`) и **1024** банов (`--max-bans-per-group`); на одну
  identity по всем группам — не больше **64** живых приглашений
  (`--max-invites-per-target`). Сверх лимита команда возвращает ошибку.
  Освободить место можно снятием старых банов (`unban`) или отзывом
  приглашения (`kick`).

### Номера `epoch` и `rev`

Номера `epoch` и `rev` растут монотонно. Чтобы после падения сервера номера не
повторялись, при загрузке к ним добавляется запас `LOAD_MARGIN` (65 536).
Поэтому после аварии номера в файле могут выглядеть «прыжком» вперёд: это ожидаемо.


### Миграция server.json

**Сервер (v2 → v3).** `server.json` версии 2 загружается без изменений.
Новые поля (`epoch`, `rev`, `revoke_prev`, `member_names`, `member_status`,
`ban_names`, `invite_times`, `invite_names`, `rotations`) получают значения по
умолчанию. Последствия, которые стоит знать:

- `epoch` и `rev` начинаются заново (с 1 по умолчанию, плюс запас при загрузке).
- Имена офлайн-участников показываются как «…», пока участник не выйдет на связь.
- Срок приглашений отсчитывается от момента загрузки файла.

**Сервер: `lease_seen` (issue #21).** Файл без поля (есть `user_ips`, нет
`lease_seen`) читается без правок: всем арендам ставится отсчёт от момента
загрузки, поэтому обновление сервера никого не выселяет сразу. Так же
клэмпится запись, просроченная больше `--lease-ttl-days` (сервер лежал
дольше срока) — иначе первый же проход освобождения выселил бы всех
подряд. `user_ips` и `lease_seen` пишутся вместе, при освобождении аренды
исчезают оба.

Идентичность сервера сохраняется, поэтому клиенты переподключаются без нового
кода. Повреждённый файл сервер не перезаписывает: он завершается с ошибкой,
которую нужно исправить или восстановить из копии. Новая identity означает
новый код для всех клиентов.

**Что делать при переносе на другой сервер.** Скопируйте `server.json` целиком
(с правами `0600`) и не генерируйте новый ключ. Если ключ нужно сменить, сделайте
это командой `rotate-key` и раздайте новый код, чтобы клиенты перезакрепились.

## Адреса оверлея: выдача и освобождение

У каждой identity на сервере один адрес из `100.66.0.0/16`, общий для всех
её групп (раздел 3 [PROTOCOL.md](PROTOCOL.md)). Адрес закреплён за ключом:

- **выдаётся** при первом входе в группу (создание или JOIN) и живёт, пока
  identity проявляет активность — успешный HELLO3 и каждый вход в группу
  продлевают аренду;
- **не меняется** при выходе из всех групп (пока аренда жива) и переживает
  рестарт сервера — он в `server.json` (`user_ips`, `lease_seen`);
- **освобождается** через `--lease-ttl-days` дней без активности (по
  умолчанию 30): адрес возвращается в пул, а identity выселяется из всех
  своих групп так же, как по `LEAVE_GROUP` — участник, приглашение, отметка
  выхода, смена ключа группы с отзывом прошлого, дельта `Removed`
  остальным. Причина: удалённый профиль пересоздаётся с новым ключом, и без
  срока аренда (вместе с «призрачным» участником групп) осталась бы навсегда.

Исключения:

- identity с живой сессией аренду не теряет — продление идёт на каждом
  проходе освобождения, даже если HELLO3 давно не было;
- **владелец группы не выселяется**: группа осталась бы без управляющего
  (удалить, кикнуть, пригласить стало бы некому). Его аренда продлевается,
  в журнале — предупреждение `lease kept`;
- реплики федерации не трогаются: их источник правды — сервер-владелец
  группы.

Освобождение выключено (`--lease-ttl-days 0`) — поведение до исправления:
адрес закреплён за ключом навсегда. Проверка идёт не чаще раза в 60 с
(`LEASE_GC_EVERY`), поэтому из `server.json` аренда исчезает в пределах
нескольких секунд после истечения. Метрики: датчик `voidlink_leases`,
счётчик `voidlink_leases_expired_total`.

Про `-q`: Server code в журнале при нём не появится, и `install-server.sh`
его не покажет. Чтобы узнать код, один раз запустите сервер без `-q`
(уберите флаг из `TUNNEL_ARGS`, `systemctl restart tunnel-server`,
`journalctl -u tunnel-server | grep TUN-`), затем верните флаг.

Флаги в службе задаются через `TUNNEL_ARGS` в `/etc/default/tunnel-server`:

```
TUNNEL_LISTEN=0.0.0.0:5555
TUNNEL_ARGS=--workers 4
```


## Группы: надгробия, выходы и отключение

`gid` — номер группы (1..=254), и он не идентичность: после удаления группы
номер нельзя выдавать сразу.

* **Надгробие.** `DELETE_GROUP` (и федеративное удаление) оставляет
  `{gid, name, owner, rev, at_ms}` в `State::deleted`; оно сохраняется в
  `server.json` → `deleted` и живёт `tomb_ttl` (по умолчанию 7 дней).
  Пока надгробие живо: `alloc_gid` не выдаёт этот номер, `CREATE_GROUP` его
  снимает, а `JOIN_GROUP` по нему отвечает **«группа не существует»**.
  Все 254 номера в надгробиях — вытесняется самое старое (с записью в лог),
  иначе после серии удалений сервер не создал бы ни одной группы.
* **Недавний выход.** `LEAVE_GROUP` пишет `left` (unix мс) и сохраняет его в
  `server.json` → `left`. Приватная группа с живым `left` (`left_ttl`, по
  умолчанию 10 минут) пускает только по новому приглашению — проверка идёт
  до ветки «уже участник», потому что потерянный `LEAVE` оставлял бы
  вышедшего участником. Успешный вход запись снимает. Для публичных групп
  действует прежняя пауза `REJOIN_COOLDOWN` = 3 с.
* **Отключение от доставки.** `GROUP_ATTACH` (0x1A, клиент → сервер):
  участник остаётся в группе, но `Group.detached` исключает его из релея
  (`relay_group`), из онлайна (`visible_counts`, `GroupSummary.online`) и
  показывает офлайн в `MemberInfo` (в том числе ему самому — это
  подтверждение). Ключ группы **не** ротируется, состав не меняется;
  `rev += 1` и `GROUP_UPDATE` kind 1 — как при смене presence. `detached`
  снимается при JOIN/LEAVE/KICK/BAN и не сохраняется: после рестарта сервера
  доставка включена, клиент повторяет `GROUP_ATTACH` в новой сессии.

Истёкшие надгробия и записи `left` чистит housekeeping (раз в 2 с), чтобы
`server.json` не рос бесконечно.


## Ротация ключа сервера

Сервер должен быть остановлен (запущенный на том же каталоге сервер новый
ключ не затирает, но вступит он в силу только после перезапуска):

```
sudo systemctl stop tunnel-server
sudo -u tunnel /opt/tunnel/tunnel-server rotate-key --data /var/lib/tunnel
sudo systemctl start tunnel-server
```

`rotate-key [--data <dir>]` печатает число звеньев цепочки, старый и новый
Server code и pubkey. Старый ключ подписывает новый, звено дописывается в
`server.json` (`rotations`). Клиенты, закрепившие любой из последних 8 ключей
цепочки, перезакрепляются сами; новым клиентам раздаётся напечатанный новый
код. Перед ротацией сделайте резервную копию (ниже). Раздел 8
[PROTOCOL.md](PROTOCOL.md).


## Снятие пина федерации (`unpeer`)

Пин — закреплённый по TOFU ключ сервера-пира в
`server.json → federation.peers` (≤ 64, `MAX_PEERS`). Пин переживает
рестарт и не даёт подменить ключ пира молча. Снять пин вручную стоит, когда
пир сменил ключ или адрес и автоматически не перезакрепился, а также когда
таблица заполнена и новый пир не влезает.

```
sudo systemctl stop tunnel-server
sudo -u tunnel /opt/tunnel/tunnel-server unpeer 203.0.113.10:5555 --data /var/lib/tunnel
sudo systemctl start tunnel-server
```

Аргумент — адрес пира или hex его ed25519-ключа (регистр не важен). Команда
печатает `Снято пинов: N` или `Пин не найден`. **Сервер должен быть
остановлен:** таблица пиров живёт в памяти работающего сервера, и при
следующем сохранении он вернул бы снятый пин. Команда берёт ту же
advisory-блокировку `server.json.lock`, что `rotate-key`. Снятый пин
вернётся и сам, если пир снова успешно пройдёт `SRV_HELLO`/`ACK` —
проверьте метрику `voidlink_fed_peers` и журнал.


## Метрики

`--metrics 127.0.0.1:9100` поднимает крошечный HTTP-сервер (один поток):

- `GET /metrics` — формат Prometheus: датчики `voidlink_sessions`,
  `voidlink_groups`, `voidlink_members`, `voidlink_invites_pending`
  (снимаются с состояния при каждом запросе) и счётчики
  `voidlink_relayed_frames_total`, `voidlink_bytes_relayed_total`,
  `voidlink_dropped_frames_total`, `voidlink_hello_total`,
  `voidlink_challenge_total`, `voidlink_ctrl_frames_total`,
  `voidlink_probes_total`, `voidlink_fed_peers`, `voidlink_fed_groups`,
  `voidlink_fed_addr_claims`, `voidlink_fed_relayed_total`,
  `voidlink_fed_hint_rejected_total`;
- `GET /healthz` — `200 ok`, если живы все воркеры и housekeeping
  отмечался за последние 10 с, иначе `503 unavailable`.

Эндпоинт без авторизации — наружу (`0.0.0.0`) его не выставлять.


## Проба, mesh и федерация (этап 9)

Сервер уже умеет то, что нужно клиентам этапа 9; федерация — T4.

**Проба доступности (`PROBE_REQ` → `PROBE_RESP`).** Проба ходит открытым
текстом, без сессии и рукопожатия: её можно задать любому серверу из списка,
не ломая текущее подключение. Сервер:

* принимает запрос ровно 64 байта, иначе молча отбрасывает;
* проверяет свежесть `ts_ms` (разброс не больше 120 с) — ответ на старый
  nonce не нужен;
* применяет лимит по IP (`allow_ip`) и общий бюджет открытых ответов
  (`plain`, флаги `--plain-rate` / `--plain-burst`);
* отвечает 24 байтами (`nonce | ts_ms`) или 56 (плюс `ed_pub`, если клиент
  просил `want_key`) — **не длиннее запроса**;
* не создаёт сессию и не занимает адрес; считает `voidlink_probes_total`.

Проба — подсказка о доступности и RTT, не доказательство подлинности
(см. [SECURITY.md](SECURITY.md), раздел 18.2).

**Mesh-контакты (`MESH_INFO` → `MESH_SEED`).** Клиент публикует статический
X25519-ключ и `caps`; сервер хранит их в сессии и:

* отвечает `MESH_SEED` — до 16 ближайших онлайн-сессий по XOR ed-ключей;
  невидимки в семя не попадают;
* держит публикацию 15 минут без повтора (`MESH_TTL_MS`): клиент шлёт
  `MESH_INFO` раз в 5 минут, а выключивший mesh перестаёт попадать в семя и
  в mesh-секцию;
* при изменении контакта поднимает ревизию группы и рассылает дельту, чтобы
  остальные увидели `x_pub`/`caps` в mesh-секции `GROUP_STATE`/`GROUP_UPDATE`;
* в mesh-секцию включает только онлайн-участников, публиковавших
  `MESH_INFO`; старые клиенты хвост игнорируют.

**Федерация (T4).** Включается флагом `--federate`.

* **Как серверы узнают друг о друге.** Явный пин — `--peer <addr>` (можно
  повторять) и `--fed-pool <addr>` для общего пула адресов; либо недоверенная
  подсказка клиента `SERVER_HINT` (≤ 8 кандидатов; клиент берёт их из
  `client.json.servers` и контактов DHT). Кандидат — только повод послать
  `SRV_HELLO`; ключ проверяется по подписи в `SRV_HELLO`/`ACK` (домен
  `voidlink-fed-v1`), первое успешное рукопожатие закрепляет пару по TOFU в
  `server.json → federation.peers` (≤ 64). При переполнении вытесняется
  самый старый пин без живой сессии, вручную пин снимает `unpeer`.
* **Что ходит между серверами.** Репликация групп (`FED_GROUP_PUSH`/
  `DELTA`), адреса (`FED_ADDR_PUSH`/`REVOKE`), кросс-серверный релей
  (`FED_RELAY` + `ACK`/`NACK`). Конфликт адресов решает меньший ed25519;
  встречные `SRV_HELLO` разрешаются тай-брейком (меньший ed — инициатор).
* Метрики: `voidlink_fed_peers`, `voidlink_fed_groups`,
  `voidlink_fed_addr_claims`, `voidlink_fed_relayed_total`,
  `voidlink_fed_hint_rejected_total`.


## Релей и порты

### Порты и файрвол

#### Сервер

| Порт | Протокол | Направление | Назначение |
|---|---|---|---|
| 5555 | UDP | входящий | управление, рукопожатие и релей (по умолчанию; адрес — позиционный аргумент сервера или `TUNNEL_LISTEN` в systemd) |
| тот же (5555) | TCP | входящий | TCP-фолбэк (включён по умолчанию, `--no-tcp` отключает) |
| 127.0.0.1:порт | TCP | локальный | HTTP-метрики (`/metrics`, `/healthz`), если включены флагом `--metrics <addr>`; по умолчанию выключены |

Открывайте только то, что нужно. Для UDP на Linux, например: `ufw allow 5555/udp` (и `5555/tcp`, если нужен TCP-фолбэк). Метрики слушайте на `127.0.0.1`, наружу их не выставляйте.

#### Клиент

Клиенту не нужны входящие правила. Он открывает UDP-сокет на эфемерном порту, который выбирает ОС (настройки фиксированного порта нет). Трафик исходящий:

- UDP к серверу (порт сервера);
- UDP к адресам пиров: `endpoint` и LAN-кандидаты, в том числе на порты, которые выбрали пиры.

Stateful-файрвол пропускает ответы и входящие пакеты от пира, если исходящий PUNCH уже создал состояние. Поэтому прямой канал работает без проброса портов на роутере. Прямой пир, который ждёт входящего пакета от незнакомого адреса, не получит его, пока пробив не состоялся. Это штатная ситуация, и тогда работает релей.

На Windows при первом запуске может появиться запрос файрвола. Разрешайте доступ для частных сетей; для публичных сетей прямая связь обычно не нужна.


### Релей и пропускная способность

- **Прямой канал.** Задержка — один путь между участниками. Пропускная способность ограничена каналом сторон и MTU.
- **Релей.** Задержка — сумма двух участков: клиент → сервер → клиент. Пропускная способность ограничена лимитом сервера.
- **Релей через пира (L2, этап 9).** Задержка — два участка плюс надбавка за чужой процесс: `rtt(us→R) + rtt(R→dst) + 15 + 10 * load(R)`. Пропускная способность ограничена каналом реле-пира и его `relay_budget_kbps` — по умолчанию ≈ 2 МБ/с на пира (окно 10 с), не больше 8 реле-пиров одновременно.
- **Кросс-серверный релей (L3, T4).** Задержка — два серверных участка; пропускная способность — лимитами обоих серверов. Реализован: `FED_RELAY` между серверами, клиент видит его как серверный путь.

Лимиты сервера по умолчанию (настраиваются флагами, см. [SERVER.md](SERVER.md)):

| Параметр | Значение по умолчанию | Смысл |
|---|---|---|
| relay rate / burst | 4000 / 8000 фреймов/с на сессию | релей, включая RTT-зонды |
| ctrl rate / burst | 50 / 100 фреймов/с на сессию | управляющие фреймы |
| hello rate / burst | 5 / 20 в секунду на IP | рукопожатие |
| plain rate / burst | 2000 / 4000 в секунду на весь сервер | открытые ответы без cookie |
| join rate / burst | 1 / 10 в секунду на группу | входы в группу |
| session timeout | 30 с | сессия без пакетов считается офлайн |

Оценка верхней границы релея: 4000 фреймов/с при полном MTU 1400 — около 5,6 МБ/с (≈45 Мбит/с) на сессию. Это грубая оценка: часть фреймов — служебные, и лимит считается по фреймам, а не по байтам. На практике для игр и голосовой связи лимит не бывает узким местом, для больших передач через релей он ощутим.

Клиент шлёт RTT-зонд `PING` всем онлайн-пирам раз в `rtt_interval_ms` — 5 с по умолчанию, 2–20 с допустимо (issue #16). При интервале 2 с это была заметная постоянная нагрузка (300–600 Б/с при трёх участниках), поэтому по умолчанию 5 с; ниже 2 с — «чаттер», выше 20 с — NAT-маппинг прямого канала успевает протухнуть, поэтому потолок именно 20 с.

Рекомендации:

- для больших передач (файлы, стриминг) стремитесь к прямому каналу: проверьте, что нет симметричного NAT и что LAN-обнаружение включено;
- на слабом канале сервера держите группы небольшими, так как каждый участник шлёт и получает трафик через релей;
- сервер в том же регионе, что и участники, заметно снижает задержку релея.


## TCP-фолбэк

По умолчанию сервер слушает и TCP на том же адресе и порту, что UDP (для
сетей, где режут UDP). По TCP ходят те же кадры протокола в рамке
`u16 LE длина` + кадр; сессия TCP-клиента ключуется адресом соединения,
ответы и релей ему идут по тому же соединению. Закрытие соединения сразу
снимает сессию (офлайн без ожидания `--session-timeout`). Лимиты: 1024
соединения, 8 с одного IP, простой без целого кадра 30 с — закрытие.
Порт TCP занят — сервер пишет предупреждение и работает только по UDP.
`--no-tcp` выключает фолбэк. Файрвол: `ufw allow 5555/tcp`.


## Обновление и удаление сервера

#### Обновление сервера

Повторный запуск infrastructure/linux/install-server.sh останавливает службу, заменяет бинарник и не трогает server.json (identity). См. [Установка (systemd)](#установка-systemd).

#### Удаление сервера

Остановите службу, удалите юнит и каталог данных (/var/lib/tunnel). Перед удалением сохраните server.json, если планируете восстановить сервер с той же identity.

## Остановка

`systemctl stop` шлёт `SIGTERM` (`SIGINT`/Ctrl+C — так же; на Windows —
Ctrl+C, Ctrl+Break и закрытие консоли): сервер останавливает воркеры, TCP и
метрики, делает финальное сохранение `server.json` и выходит с кодом 0.
Повторный сигнал во время остановки — немедленный выход с кодом 1. Запись
файла атомарная (tmp + rename) — наполовину записанным он не бывает.
Клиенты после рестарта сервера получают `RESET` и переподключаются за секунды.

`Restart=on-failure`: упавший сервер поднимается через 2 с. Если
`server.json` повреждён, сервер **не стартует** (а не создаёт новую identity,
из-за которой все клиенты потеряли бы сервер) — восстановите файл из копии.


## Резервная копия `server.json`

В `server.json` — identity сервера (приватный ключ; от него зависит Server
code), группы, `user_ips` (постоянный оверлейный адрес каждой identity, один
на все её группы), `lease_seen` (когда аренда адреса продлевалась в
последний раз), бан-листы, инвайты, цепочка ротаций. Потеря файла =
новый Server code и пустой сервер: всем клиентам придётся перенастраиваться.

Адреса пользователей (`user_ips`, hex pubkey → IP) сохраняются в `server.json`
и переживают рестарт и выход из всех групп, пока identity проявляет
активность (иначе адрес освобождается — см. «Адреса оверлея: выдача и
освобождение»). `server.json` от v3 (без `user_ips`) загружается
автоматически: адрес identity берётся из группы с наименьшим gid. Файл без
`lease_seen` тоже читается: всем арендам ставится отсчёт от момента
загрузки, поэтому обновление сервера никого не выселяет сразу. Подробнее об
адресации — в [Сеть и пути](CLIENT.md#сеть-и-пути).

### Секция `friends` (issue #24)

```json
"friends": {
  "requests": [
    { "from": "<64 hex>", "to": "<64 hex>", "created_ms": 1763000000000, "from_name": "anna" }
  ],
  "edges": [
    { "a": "<64 hex>", "b": "<64 hex>", "since_ms": 1763000600000 }
  ]
}
```

* `requests` — неотвеченные заявки в друзья; живут `friend_req_ttl` (7 дней),
  повтор заявки обновляет `created_ms`, а не создаёт вторую запись.
* `edges` — принятые пары, всегда упорядоченные (`a < b` по ключу): дружба
  одно множество, а не два направления, поэтому снятие с любой стороны
  удаляет одну запись и уведомляет вторую.

Ников, групп и адресов оверлея в записи **о принятой дружбе** нет — только
ключи и время. У неотвеченной заявки хранится ещё имя инициатора
(`from_name`): без него адресат не увидел бы, кто просит дружбы; имя
удаляется вместе с заявкой (принятие, отказ, истечение).
Имя для `FRIEND_LIST`/`FRIEND_REQ_RCVD` сервер берёт из живой сессии или
групп в момент отправки кадра, поэтому у офлайн-друга ник может быть пустым
(клиент показывает свой кэш). Заявки и пары переживают рестарт; `FRIEND_ACCEPT` и
`FRIEND_REMOVE` сохраняются сразу, не в окне `SAVE_EVERY` — иначе падение
сервера воскрешало бы снятую дружбу. Секции нет в старом файле — читается как
«дружб нет», файл не ломается.

Копия «на горячую» безопасна (файл заменяется атомарно, читается целиком):

```
sudo install -m 0600 /var/lib/tunnel/server.json ~/server.json.$(date +%F)
```

Периодически, например cron/systemd-timer раз в сутки:

```
0 4 * * * root install -m 0600 /var/lib/tunnel/server.json /root/backup/server.json.$(date +\%F)
```

Восстановление:

```
sudo systemctl stop tunnel-server
sudo install -o tunnel -g tunnel -m 0600 server.json.YYYY-MM-DD /var/lib/tunnel/server.json
sudo systemctl start tunnel-server
```

Перенос на другой VPS — то же самое: новый сервер с этим `server.json`
сохраняет Server code; клиентам достаточно сменить адрес
(`del-server` + `add-server` с прежним кодом).
