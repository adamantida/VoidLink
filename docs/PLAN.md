## Этап 0 — MVP (сделано)

- Рандеву-сервер + релей, клиенты с Wintun-адаптером, ping между пирами.
- UDP hole punching → direct P2P, шифрование ChaCha20-Poly1305.

## Этап 1 — Идентичность и группы (протокол v2) — ✅ сделано (11.2026)

### 1.1 Идентичность клиента ✅
- При первом запуске клиент генерирует **ed25519 + x25519 пары**, хранит в
  `%APPDATA%\tunnel\client.json` (единый конфиг, не отдельный identity.json).
- **Friend code** — base32 (Crockford, без I/L/O/U) ed25519-pubkey:
  `TUN-XXXX…-…`, 52 символа. Добавление друга = вставка кода
  (`add-friend <code> [alias]`). ✅

### 1.2 Группы ✅
- Группа = отдельная виртуальная сеть, подсеть `100.66.<gid>.0/24`
  (CGNAT, gid 1..254).
- Атрибуты: id, имя, владелец (pubkey создателя), публичная/приватная,
  участники (pubkey → IP), ban-список, инвайты. Управляет владелец. ✅
- **Публичная** — видна всем в списке, вход по желанию. ✅
- **Приватная** — видна только участникам; вход по приглашению владельца
  (`invite <gid> <peer>` → у друга INVITE_RCVD «вас пригласили»). ✅
- **Отказ от приглашения** — `DECLINE_INVITE` (0x0E): сервер снимает инвайт
  и шлёт владельцу `INVITE_DECLINED` (0x87). Неотвеченные приглашения
  доставляются заново после каждого HELLO (`INVITE_LIST`, 0x88), в том числе
  тем, кто был офлайн в момент приглашения. ✅ (11.2026, подробности —
  этап 4, «Окно приглашения»)

### 1.3 Выдача IP сервером ✅
- Сервер держит lease-таблицу `pubkey → ip` на группу. Участник при возврате
  получает **тот же IP**. Проверено рестартом сервера и клиентов. ✅
- Клиент IP никогда не выбирает сам; сервер гарантирует уникальность. ✅
- Отклонение от плана: **lease освобождается по leave/kick/delete**, не по
  таймауту офлайна — офлайн-участник сохраняет IP (стабильность важнее). ✅

### 1.4 Шифрование v2 ✅
- В DATA-фрейме dst_ip и group_id в открытом заголовке, payload под AEAD
  ключом группы; релей читает только заголовок. ✅ (Сквозного шифрования до
  сервера нет: ключ группы генерирует и раздаёт сам сервер, поэтому он
  технически может расшифровать релеируемый payload — см. SECURITY.md §3.)
- Ключ группы генерирует сервер и раздаёт при join по шифрованному каналу;
  с протокола v3 — по эпохам с ротацией (этап 8). ✅
- Дополнение (не было в плане): HELLO идёт открытым текстом, но **подписан**
  ed25519; ответ WELCOME — открытый (x_pub сервера + подпись ed25519, клиент
  pinned ed-ключ сервера). Дальше весь ctrl-канал шифруется static-static
  X25519. Без этого клиент не мог вывести канальный ключ (не знал x_pub
  сервера), а подмена сессии с чужого IP исключена подписью.

## Этап 4 — TUI (ratatui) — ✅ сделано (11.2026)

```
┌ Группы ─────────────┬ Группа "gamers" (публичная) ─────────────┐
│ ● gamers     3/253  │  имя     IP            связь    ping    │
│ ● work       2/253  │  alpha   100.66.0.2    direct    1 мс    │
│ 🔒 secret    2/253  │  bravo   100.66.0.3    relay     45 мс   │
├ Друзья ─────────────┤                                          │
│ ● alpha (2 группы)  │                                          │
│ ○ charlie           │                                          │
└─────────────────────┴──────────────────────────────────────────┘
 100.66.0.2 @ 127.0.0.1:5555   [F2 создать] [a добавить друга] …
```

- **Группы**: создать (F2), удалить (F8, только владелец), переименовать (F6),
  пригласить друга (i), покинуть, список публичных → войти (j).
- **Друзья**: добавить (a, вставка friend code), удалить (d, с
  подтверждением), Enter по другу → карточка: в каких группах он состоит
  (запрос серверу: публичные группы друга + общие с тобой).
- **Popup'ы**: ввод текста, выбор друга для инвайта, подтверждения.
- **Статус-бар**: мой IP, сервер, счётчик direct/relay.
- **Лог**: последние события (подключения, ошибки) отдельным блоком/вкладкой.

### Что реализовано

- Крейт `tunnel-client` получил подкоманду **`tui`** (alias `ui`) — тот же
  движок, что и `run`, но с графическим интерфейсом; `run` (CLI-лог) сохранён.
- Модуль `crates/client/src/tui/`: `app.rs` (состояние и клавиши), `ui.rs`
  (отрисовка), `theme.rs` (3 темы, позже 5 — см. «Виджеты и темы»),
  `identicon.rs` (аватар по pubkey).
- Движок расширен: `Cmd::ToggleAutojoin`, `Engine::save_config` (правка
  client.json из UI), `Event`-ы уже покрывают всё для тостов.
- Исправлена сломанная сборка HEAD: не хватало `conn_sock_placeholder()`,
  а `engine_loop` не принимал текущий дата-сокет → после реконнекта tun-поток
  писал в старый сокет (потеря трафика до перезапуска клиента).

### Движок под TUI (коммит «Часть 5»)

TUI потребовал от движка постоянного состояния и фоновой работы, а не только
однострочных команд:

- **Потоки**: `engine` (цикл сессии и реконнекта), tun-поток (адаптер →
  сокет), `sampler` (раз в секунду пишет КБ/с в историю для спарклайна,
  60 точек). Состояние для UI — `Engine::groups` / `meta` / `stats`
  (атомарные счётчики байт и пакетов).
- **Состояние групп** (`GROUP_STATE`): участники пересобираются по pubkey с
  сохранением `direct` и RTT; новые и ушедшие пиры → события
  PeerOnline/PeerOffline.
- **Групповые фреймы** (DATA … KEEPALIVE) разбираются в том же цикле, что и
  ctrl: любой фрейм пира, пришедший не через сервер, включает `direct` и
  запоминает его endpoint (событие Direct); PING → ответ PONG, по PONG
  считается RTT; DATA вбрасывается в адаптер.
- **Раунды по таймеру**: RTT-зонд каждому пиру раз в 1 с (direct — напрямую,
  иначе через релей); NAT-раунд раз в 5 с (CTRL_PING серверу +
  PUNCH/KEEPALIVE пирам); список групп раз в 10 с.
- **Сверка** (`reconcile`): группы, которых больше нет в списке сервера
  (удалили/кикнули, пока клиент был офлайн), убираются локально; у только что
  созданной группы 10 с «форы», чтобы её не снесло до прихода списка.
- **Реконнект**: сервер считается потерянным после 20 с тишины. Пауза 1 с →
  2 → 4 … → 30 с; после входа заново отправляются статус, автовход в группы и
  запрос списка. (В этапе 6 потоки и таймеры переделаны — см. ниже.)

  перерисовки, после клика кадр перерисовывается до следующего события.

### Окно приглашения ✅

Раньше приглашение было только тостом и строкой лога, отказаться было
нельзя, а приглашение офлайн-цели терялось. Теперь — окно «★ Приглашение в
группу» и сквозная поддержка от протокола до TUI.

- **Окно**: кто пригласил (для друга — «alias (имя на сервере)», иначе имя
  от сервера), «группа», gid, когда получено, в заголовке «ещё N» —
  сколько ждёт в очереди, внизу подсказка клавиш. Тост и строка лога
  остались.
- **Клавиши**: `Enter` / `y` — Принять (`Cmd::Join`); `n` / `т` —
  Отклонить (`Cmd::DeclineInvite`); `Esc` / `l` / `д` — Позже (ничего не
  шлётся, приглашение остаётся на сервере). `н` (на месте `y`) не
  принимает: по-русски она читается как «нет» (`[Д/н]`), а принять — самое
  весомое действие; на неё — только подсказка в строке статуса. Любое сочетание с `Ctrl` —
  Позже; `Ctrl-C` откладывает всю очередь, чтобы следующий `Ctrl-C` вышел из
  программы. Прочие клавиши игнорируются, окно не закрывается.
- **Мышь**: кнопки `Принять` / `Отклонить` / `Позже`; клик мимо окна —
  Позже, никогда не Отклонить.
- **Защита от промаха** (`INVITE_GUARD`, 400 мс): сразу после появления окна
  клавиши и клики принять/отклонить игнорируются, `Esc` работает.
- **Очередь**: одно окно за раз, очередь `App::invites` без дублей по gid
  (повторная доставка обновляет данные, но не открывает окно заново;
  отложенное остаётся отложенным). Пока открыто любое другое окно или идёт
  поиск (`/`), приглашение ждёт — нажатия для поля ввода не должны на него
  ответить. Запоздавшая карточка друга не ложится поверх приглашения.
- **Позже и повтор**: отложенные — в `later_invites`; `o` или `:invites`
  показывает их снова, `:decline <gid>` отклоняет без окна. Принять тоже
  держит приглашение в `later_invites`, пока не придёт `GroupJoined` —
  после JOIN, отклонённого из-за заполненности, оно доступно по `o`; при
  отказе по другой причине (группы нет, приглашение отозвано) сервер
  вместе с ошибкой шлёт свежий список, и сверка его снимает.
- **Офлайн**: Принять/Отклонить без соединения ничего не шлют — приглашение
  откладывается, тост с ошибкой.
- **Без окна**: если уже участник или gid в автовходе (только строка лога).
  Приглашение снимается по `GroupJoined`, `GroupDeleted`, `InviteRevoked` и
  при сверке `InvitesSynced` (тост «приглашение … больше
  недействительно»): окно списка снимает всё, чего в нём нет, от своего
  `from` — полное до конца, неполное (обрезан хвост по gid) только до
  последнего gid в нём; приглашения, пришедшие меньше 2 с назад
  (`INVITE_SYNC_GRACE`), сверка не трогает — список мог быть собран раньше
  них (другой поток сервера, перестановка UDP). Отклонённое 5 с
  (`INVITE_DECLINE_MEMORY`) не показывается снова: запоздавший список,
  собранный до отказа (медленная связь), вернул бы его свежим окном.
- **Владелец**: на `InviteDeclined` — тост и лог «X отклонил приглашение в
  «группа» (gid)».

Протокол и сервер:

- `DECLINE_INVITE` (0x0E, клиент → сервер, payload — gid) — идемпотентен:
  нет группы или инвайта — без ошибки. Сервер снимает инвайт и, если
  владелец онлайн, шлёт ему `INVITE_DECLINED` (0x87, `gid | имя группы |
  pubkey | имя`, раскладка как у INVITE_RCVD) — только если инвайт и правда
  был; офлайн-владелец об отказе не узнаёт. Отказавшему — всегда свежий
  `INVITE_LIST`, окно которого покрывает этот gid (подтверждение отказа).
- `INVITE_LIST` (0x88, сервер → клиент) — окно неотвеченных приглашений
  (не участник, не в бане) с gid ≥ `from`, по возрастанию gid, не больше 16
  (`INVITES_PER_LIST`) + флаг `complete` (дальше ничего нет); раскладка
  `from | complete | n | n × INVITE_RCVD`. Ответ не растёт с числом
  приглашений ни на HELLO, ни на фреймы сессии: адрес сессии ничем не
  подтверждён (HELLO принимается с любого адреса, ctrl-ключ —
  static-static DH, его знает владелец identity и без ответа сервера),
  любой ответ может уйти на подделанный адрес — усилитель отражённого
  трафика. Окно с начала (`from` = 0) — после HELLO (и при реконнекте) и
  после JOIN, потратившего приглашение (всегда: так видны приглашения
  сверх первых 16 по мере ответов, сколько бы их ни осталось). Окно,
  покрывающее gid (с начала, если до gid меньше 16 неотвеченных, иначе с
  gid), — в ответ на `DECLINE_INVITE`, на JOIN, отклонённый не из-за
  заполненности (группы нет, бан, приватная без приглашения: клиент снимет
  мёртвое приглашение, а не будет снова и снова получать отказ), и
  приглашённому онлайн после KICK/BAN, снявшего его приглашение.
  `LIST_INVITES` (0x0F, клиент → сервер, payload — `from`) — окно без
  побочных эффектов: движок дочитывает неполное окно сам (`from` = gid
  после последнего), CLI — для `invites` и проверки `decline`. Имя
  пригласившего — из сессии владельца, затем из ростера, после рестарта
  сервера — короткий pubkey. Живой INVITE_RCVD в момент INVITE не
  изменился. ⏳ Проверка обратного адреса (cookie в WELCOME) — тогда и
  `GROUP_LIST`/`GROUP_STATE`, растущие с числом групп и участников, не
  будут усилителем.
- Сервер: INVITE уже участнику — ERROR «уже участник группы»; KICK/BAN и
  LEAVE снимают инвайт цели; при KICK/BAN приглашённого онлайн-цели сразу
  уходит свежий `INVITE_LIST` (окно закрывается; KICK приглашённого, но не
  вошедшего = отозвать приглашение); при удалении группы приглашённые
  онлайн тоже получают `GROUP_STATE` с `deleted` (без дублей); при
  загрузке `server.json` устаревшие инвайты участников и забаненных
  вычищаются.
- Движок: `Cmd::DeclineInvite`; `Event::Invite` несёт `from_pubkey`;
  новые `Event::InviteDeclined`, `InviteRevoked` (удалена группа, в которой
  мы не состоим), `InvitesSynced { gids, from, complete }` (после каждого
  `INVITE_LIST`; неполное окно движок дочитывает `LIST_INVITES`). Ожидаемое
  окно (после HELLO — с 0, дальше — следующая страница) движок
  перезапрашивает `LIST_INVITES` раз в 3 с, пока не придёт покрывающее его
  окно (`INVITE_SYNC_RETRY`; через 20 с сдаётся — старый сервер), иначе
  потерянный UDP-фрейм прятал бы офлайн-приглашения до реконнекта.
  `DECLINE_INVITE` движок повторяет раз в секунду (как LEAVE), пока окно
  списка не покроет gid без него (`DECLINE_GIVE_UP` 20 с; при реконнекте —
  заново), а приглашения в gid, отказ от которого ещё повторяется, из
  списков не показывает. `run`
  печатает новые события; ответить на месте нельзя: и CLI-команды, и TUI —
  отдельный HELLO той же identity, он вытесняет сеанс `run` (а реконнект
  `run` — их), так что сначала остановить `run`, потом `join`/`decline`

  подтверждается свежим окном, покрывающим gid, при потере повторяется;

- Совместимость: `PROTOCOL_VERSION` не менялся. Старый сервер молча

- Исправлено по ходу: JOIN тратил инвайт до проверки «группа заполнена»

## Этап 6 — Prod: сеть, многопоточность, баги — ✅ (11.2026)

### Найденные баги

- **Бесконечный спам пакетами.** На PUNCH клиент отвечал PUNCH, второй
  клиент — снова PUNCH: пинг-понг без конца, и каждый NAT-раунд (раз в 5 с)
  запускал ещё одну такую цепочку. В e2e-тесте — ~10 000 пак/с на клиента.
  Теперь на PUNCH отвечают KEEPALIVE, на который не отвечают (совместимо со
  старыми клиентами: им KEEPALIVE не отражается).
- **Невозможно выйти из группы.** Таймеры движка (CTRL_PING, раунды)
  срабатывали только на таймауте приёма: при постоянном входящем потоке (тот
  же спам) клиент переставал пинговать сервер, сервер через 30 с снимал
  сессию и молча игнорировал LEAVE. Кроме того, потерянный LEAVE или
  запоздавший GROUP_STATE возвращали группу (и автовход). Теперь таймеры
  идут по часам, LEAVE повторяется до подтверждения, состояния выходящей
  группы игнорируются.
- **Лаги интерфейса** — следствие спама: поток движка обрабатывал тысячи
  пакетов в секунду и на каждый брал мьютекс групп, а UI берёт тот же
  мьютекс на каждом кадре.
- **Длина friend code.** Профиль был уже кода: `friend code: TUN-…` (75
  символов) обрезался рамкой окна, выделенный мышью код был короче 52
  символов. Окна расширены, код — отдельной строкой; разбор терпим к
  пробелам/переводам строк/рамкам/кириллице и сообщает, сколько символов
  получено.
- **Кик не распознавался**: сервер пишет «кикнут», клиент искал «кикнул».
- `--server N` всегда выбирал первый сервер; `del-server N` удалял **все**
  серверы (числовой токен сравнивался сам с собой).
- DATA к пиру без прямого канала уходили на его endpoint (терялись в NAT до
  пробития), а не через релей.
- Длинное имя/статус кириллицей (>255 байт) роняло поток движка (`assert`
  в кодеке строк) — теперь обрезается по границе символа.
- Сервер: после 254 созданий групп нельзя было создать ни одной (gid не
  переиспользовались); повреждённый `server.json` молча заменялся новой
  identity; при входе обнулялся статус участника; кик не обновлял список
  групп кикнутого; сервер не рассылал состояние групп при переподключении
  участника (новый адрес пира узнавали только при следующем JOIN).

### Клиент: потоки

- `rx` — блокирующий приём с единственного сокета; групповые фреймы
  обрабатывает сам, управляющие фреймы сервера передаёт движку. P2P
  работает и во время реконнекта.
- `engine` — состояние соединения, команды UI, таймеры по часам (RTT 2 с,
  PUNCH 5 с, CTRL_PING 5 с, список 15 с, повтор LEAVE 1 с, DECLINE 1 с,
  неполученного окна приглашений 3 с).
- `tun`, `sampler` — как раньше. Сокет один на всё время работы; реконнект
  — новый HELLO с того же адреса.
- `TunDev` — абстракция адаптера: Wintun в проде, заглушка в e2e-тестах.

### Сервер: потоки и защита

- Логика — в `lib.rs` (`Server::start/stop`), `main.rs` — разбор аргументов.
- Воркеры (по числу ядер, 2..8) на одном сокете, состояние под `RwLock`,
  индексы `by_pub` (identity → адрес) и `by_ip` (IP группы → identity):
  релей за O(1) под блокировкой на чтение. Ответы собираются и уходят после
  снятия блокировки.
- Релей: только от сессии, только участнику той же группы, только со своим
  `src_ip`. Лимиты token bucket: релей 4000 пак/с и управление 50/с на
  сессию, HELLO/RESET 5/с на IP. Мусор отбрасывается без записи в лог.
- `RESET` (0x8E, открытым текстом): фрейм от неизвестного адреса → клиент
  сразу шлёт HELLO.
- Сводка раз в 5 минут: сессии, группы, релей пак/с, отброшено.

### Тесты

- e2e в клиенте (`engine_e2e.rs`): сервер + 2 движка на localhost —
  прямой канал, доставка пакета, < 5 пак/с в простое (со старым PUNCH тест
  падает: ~10 000 пак/с), выход без возврата группы, кик, рестарт сервера
  с переподключением < 12 с; посторонний релей → RESET; мусор не роняет

- Сервер (идут и на Linux в CI): выдача gid по кругу, очистка имён, релей
  только своим (подмена `src_ip` отбрасывается), повторный LEAVE,
  сохранение и загрузка состояния.
- Протокол: friend code из буфера обмена, обрезка длинных строк.

### Принятые решения (черновик, утвердить до 7.2)

- **Источник истины — демон.** Фронтенды не хранят состояния кроме своего
  (выбор строки, тосты, тема); всё остальное — из снимков демона.
- **Конфиг службы** — `%ProgramData%\tunnel\client.json` (ACL: SYSTEM и
  Administrators — полный доступ, остальным — нет). Identity принадлежит
  машине, а не пользователю: `%APPDATA%` у LocalSystem — это
  `System32\config\systemprofile`, туда класть нельзя. Сиды ключей никогда
  не уходят по IPC. Настройки UI (тема) — `%APPDATA%\tunnel\ui.json`.
- **Транспорт** — свой тонкий слой без async-рантайма (проект на std-потоках):
  Windows — named pipe через `windows-sys` (`CreateNamedPipeW` с
  `PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE`, явный
  security descriptor), Unix — `std::os::unix::net::UnixStream` (для тестов
  и разработки на Linux/mac). Крейт `interprocess` рассмотрен: удобен, но
  контроль над флагами и SDDL пайпа нам важнее лишней зависимости.
- **Формат** — фрейм `u32 LE длина | JSON` (serde уже в зависимостях,
  читается глазами, трафик ~1–2 КБ/с). Лимит фрейма 1 МиБ. Бинарный формат
  не нужен.
- **Трей** — `tray-icon` + `muda` (см. 7.5), служба — `windows-service`
  (крейт Mullvad, проверен в проде VPN).

### 7.1 Движок в отдельный крейт + трейт `EngineApi` ✅ (с отступлением)

(`lib.rs`); демон зависит от него как от библиотеки. Поэтому в описании
ниже «`crates/engine`/`tunnel-engine`» читайте как `tunnel-client` (lib).
`wintun` — только под `cfg(windows)`, на Linux/macOS — `tun_linux.rs` /
`tun_macos.rs`, клиент и e2e-тесты идут в CI на ubuntu и macOS.
**Осталось:** ничего.

- `crates/engine` (`tunnel-engine`, lib): переносятся `engine.rs`, `store.rs`,

  клиент и e2e-тесты идут в CI на ubuntu без зеркала со стабом.
- `crates/engine/src/api.rs`: снимок и трейт, которым пользуется TUI.

  ```rust

      fn snapshot(&self) -> Arc<Snapshot>;      // группы, meta, stats, cfg-вид
      fn poll_events(&self) -> Vec<Event>;      // без блокировки
      fn send(&self, cmd: Cmd) -> Result<()>;
  ```

  5 с не возвращается запоздавшим списком) переезжают из `App` в
  `invites.rs` вместе с памятью отказов; повтор DECLINE до подтверждения
  уже в движке (этап 4). Очередь окон и `later_invites` остаются

- `App::sync`/`handle_*` принимают `&dyn EngineApi` вместо `&Engine`; прямые

  состоянии «нет сервера» (сетевые команды — `Ack` Err «нет сервера») и

- `Cmd`, `Event` → `Serialize/Deserialize`; для `GroupSummary`/`FriendGroup`

- `LocalEngine` (обёртка над `Engine`) реализует трейт — embedded-режим.

### 7.2 Крейт `crates/ipc` (протокол + транспорт) ✅

**Что сделано.** `proto.rs`, `codec.rs` (фрейм `u32 LE | JSON`, лимит
1 МиБ), `client.rs`, `lock.rs` (общий замок single-instance),
`transport/{unix,windows}.rs`; тесты — `crates/ipc/tests/unix_socket.rs` и
юнит-тесты кодека. Windows-транспорт (SDDL, `FIRST_PIPE_INSTANCE`, проверка
SYSTEM у сервера пайпа) написан и собирается в CI, **вживую на Windows не
проверен**. **Осталось:** ручная проверка пайпа (чек-лист TESTING.md §7.2).

- `proto.rs`: `ClientMsg = Hello{proto:1, kind:Tui|Tray|Cli, ver} |
  Req{id, cmd} | Subscribe{snapshots_ms} | Bye`; `DaemonMsg = Welcome{proto,
  daemon_ver, me} | Reject{причина} | Ack{id, Ok|Err(текст)} | Event{seq, ev} |
  Snapshot{seq, snap} | Shutdown{причина}`. Несовпадение мажорной версии —
  `Reject` в ответ на Hello (у Hello нет `id` для `Ack`) и закрытие:
  «обновите tunnel-client / демон».
- Результаты команд по-прежнему приходят событиями (`GroupJoined`, `Error`);
  `Ack` — только «принято/отклонено демоном» (неверный gid, нет сервера…).
- `transport/{windows.rs, unix.rs}`: `Listener::bind(name)` →
  `accept()` → `Conn: Read + Write`; `connect(name)`.
- Безопасность: SDDL пайпа `D:P(A;;GA;;;SY)(A;;GA;;;BA)(A;;GRGW;;;<SID
  владельца>)`, SID пишется при установке; удалённые клиенты отклонены
  флагом. Клиент проверяет, что сервер пайпа — процесс службы
  (`GetNamedPipeServerProcessId` → токен SYSTEM), защита от подмены пайпа
  непривилегированным процессом до старта службы. Пайп поднимает только
  служба: SID владельца есть лишь после `install`, а сервер пайпа не от
  SYSTEM клиент по этому правилу отвергает — у embedded TUI (7.4) и у
  `tunnel-daemon console` (7.3, процесс администратора, не SYSTEM) пайпа
  нет; dev-исключений в правиле доверия нет. Unix — сокет `0600` в
  каталоге данных (его поднимает и `console`: так работают `ipc_e2e` и
  разработка на Linux/mac).

Готово, когда: кодек и транспорт покрыты тестами (круг Hello→Req→Ack,
битая длина / >1 МиБ / мусорный JSON → разрыв без паники).

### 7.3 `crates/daemon` (`tunnel-daemon.exe`) ✅ (кроме ⏳ ниже)

**Что сделано.** Хаб событий и снимков, кольцо 500 событий, замок,
лог с ротацией, режимы `console` и `service`, `--fake`; `DaemonEngine`
(`engine_backend.rs`) — бэкенд на настоящем движке с конфигом
`client.json` каталога данных; состояние «нет сервера» (демон отвечает по
IPC и ждёт `AddServer`); `Reconnect` после пробуждения (resume-хук службы).
**Осталось:** ⏳ `Cmd::SwitchServer` в демоне (в embedded/`LocalEngine`
переключение сервера работает); ⏳ IPC для embedded TUI отдельным пайпом.

- `core.rs` (кроссплатформенный): поднимает `Engine`, хаб событий
  (`mpsc` движка → копия каждому подписчику, очередь на клиента ограничена;
  переполнение → клиенту пропуск, он видит дырку в `seq` и ждёт снимок),
  снимок раз в 1 с и сразу после изменений, кольцо последних 500 событий —
  новый фронтенд сразу получает историю лога.
- `pending_invites` — из `tunnel-engine` (7.1), своей логики у демона нет.
  Источник истины — сервер: отказ — `DECLINE_INVITE`, неотвеченные приходят
  после каждого HELLO (`INVITE_LIST`, этап 4).
- Single-instance: Windows — `Global\TunnelEngine` (named mutex) +
  `FIRST_PIPE_INSTANCE`; Unix — `flock` на `daemon.lock` в каталоге данных
  (сокет, к которому не подключиться, считается устаревшим и удаляется
  только под этим замком). Замок берёт любой, кто поднимает движок (демон,
  embedded TUI, `run`). `ipc::Server` поднимает только демон: embedded TUI
  — процесс пользователя (не SYSTEM, без установки), его пайп не прошёл бы
  проверку клиента из 7.2, а ослабить её — снова открыть подмену пайпа.
  Поэтому при embedded TUI CLI и трей не работают, а говорят, почему
  (7.4). ⏳ IPC и для embedded — только отдельным пайпом со своим правилом
  доверия: имя с SID пользователя, SDDL из SID текущего пользователя при
  старте, клиент проверяет, что токен сервера пайпа — тот же пользователь
  и elevated.
- Режимы: `tunnel-daemon console` (от администратора, лог в консоль — для
  разработки движка и хаба; на Windows без пайпа, как embedded TUI — 7.2,
  на Unix с сокетом), `tunnel-daemon service` (точка входа SCM). Сон/пробуждение:
  `SERVICE_CONTROL_POWEREVENT` (resume) → немедленный HELLO.
- Логи: `%ProgramData%\tunnel\logs\daemon.log`, ротация 1 МиБ × 5; `--debug`
  движка — туда же. `eprintln!` движка заменить на колбэк лога.
- ⏳ Смена сервера без перезапуска: `Cmd::SwitchServer` пересоздаёт движок
  внутри демона (адаптер сохраняется).

Готово, когда: на Windows `tunnel-daemon console` держит туннель и ping
идёт (фронтендов у него нет — пайпа нет, 7.2); подключение/отключение
фронтендов на туннель не влияет — в `ipc_e2e` на Unix-сокете (7.7,
`TunDev`-заглушка); на Windows это проверяется у службы, после `install`
(7.6), когда есть SID владельца для пайпа.
Риски: `Engine::drop` сейчас глушит движок — хаб должен владеть им сам.

## Развёртывание

- **Клиенты — Windows, Linux, macOS.** Windows: Wintun, служба
  `TunnelDaemon` + трей (`infrastructure/windows/install.ps1`), TUI без прав
  администратора при службе; Linux/macOS: TUN, нужен root (или
  `CAP_NET_ADMIN` на Linux), демон работает через Unix-сокет. На Linux и
  macOS реальный TUN вручную не проверялся (см. этап 8).
- **Сервер — Linux**: крейт `tunnel-server` чисто кроссплатформенный (std +
  crypto, без windows-зависимостей). Сборка под Linux: `cargo build --release`
  на хосте или в CI; бинарник + systemd-юнит:

  ```ini
  [Service]
  ExecStart=/opt/tunnel/tunnel-server 0.0.0.0:5555 --data /var/lib/tunnel
  Restart=always
  DynamicUser=yes
  NoNewPrivileges=yes
  ProtectSystem=strict
  StateDirectory=tunnel   # сюда ляжет server.json
  ```
- Правила файрвола на сервере: только UDP-порт (5555) наружу/внутрь.

## Принятые решения

1. **Друзья** — хранятся локально у клиента; сервер не знает список дружб.
2. **Публичные группы** — свободный вход (увидел в списке → вошёл).
3. **Адресация** — `100.66.0.0/16` (CGNAT-диапазон), группа `i` →
   `100.66.<i>.0/24`.
4. **Порядок работ** — сначала протокол v2 + сервер + engine, затем TUI.
5. **Движок остаётся в `crates/client`** (lib+bin), отдельный крейт
   `tunnel-engine` не создавался.
6. **Сервер раздаёт ключи групп** (по эпохам): сквозного шифрования до
   сервера нет, сервер — доверенная сторона (SECURITY.md §3).
