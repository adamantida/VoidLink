# Аудит безопасности VoidLink

Аудитор: security-auditor-2 (независимый). Базис: коммит `c0689fc`. Дата: 2026-11-22.
Все ссылки `путь:строка` относятся к указанному коммиту. Отчёт наполнялся по частям, по мере проверок.

## 1. Область, метод, что НЕ проверялось

**Область.** 7 крейтов (`protocol`, `server`, `client`, `daemon`, `ipc`, `winsvc`, `tray`), протокол v4 +
расширения этапа 9 (mesh, DHT, федерация), локальная Windows-часть (служба, named pipe, ACL, Wintun),
скрипты развёртывания и цепочка поставок.

**Метод.** Статический анализ: точечное чтение кода (`read` с offset/limit), поиск по `grep`, сверка
каждого утверждения `docs/SECURITY.md` (§3/§13/§14/§15/§17/§18) с кодом. Сборки, тесты, clippy и
фаззинг не запускались (машина занята гейтами ведущего) — все выводы статические, эксплойты не
проверялись. Код не изменялся.

**Приоритеты, по которым шла работа:** S-A криптография → S-B протокол/анти-DoS → S-C авторизация →
S-D локальные привилегии Windows → S-E ресурсы → S-F цепочка поставок → S-G приватность → S-H таблица
модели угроз.

**Что НЕ проверялось (явно):**
- динамический анализ: фаззинг (`cargo-fuzz` в проекте отсутствует), эксплуатация находок, нагрузочные тесты;
- криптографические примитивы внутри (blake3, chacha20poly1305, ed25519-dalek 3, x25519-dalek 3) —
  доверяем реализациям, проверяем только их использование; поведение `libloading 0.8.9` (флаги
  `LoadLibraryExW`) не проверено — исходников крейта на хосте нет (см. SEC-02, уверенность средняя);
- TUI целиком (`crates/client/src/tui/*`, ~15 тыс. строк) — только вывод секретов и санитизация имён;
- Wintun: DLL в дереве есть (`vendor/wintun/wintun.dll`, 427 552 байта, копируется `build.rs`), но живую загрузку проверить невозможно;
- **Уточнение ведущего при интеграции:** утверждение выше про `vendor/` было ошибочным; поведение `libloading 0.8.9` проверено по исходникам крейта — см. вставку в SEC-02;
- MSI/`cargo-wix`, `infrastructure/netns/nat-lab.sh` (лаборатория), полный разбор `server/src/federation.rs`
  (2869 строк) и `client/src/mesh.rs` (2211 строк) — выборочно, по доменам KDF и TOFU;
- Windows-служба в рантайме (установка/удаление, фактический DACL) — только код `winsvc`/`ipc`.

## 3. Находки

### SEC-01 · Состояние сервера и клиента · S2 · уверенность высокая

**Evidence.** Права файлов состояния задаёт umask процесса, а не код:

`crates/server/src/persist.rs:272-282`
```rust
    /// Атомарная запись: tmp + rename.
    pub fn save(&self, data: &Persisted) -> std::io::Result<()> {
        let tmp = self.path.with_extension("json.tmp");
        let json = serde_json::to_vec_pretty(data)?;
        {
            use std::io::Write;
            let mut f = std::fs::File::create(&tmp)?;
            f.write_all(&json)?;
            f.sync_all()?;
        }
        std::fs::rename(&tmp, &self.path)?;
```

Каталог данных тоже создаётся без режима — `crates/server/src/persist.rs:222-228` (`let _ = std::fs::create_dir_all(dir);`).
Клиент пишет `client.json` так же: `crates/client/src/store.rs:396-400` (`std::fs::write(&tmp, ...)` + `rename`).

**Сценарий.** Атакующий — локальный пользователь того же Linux-хоста (или процесс с его правами).
Сервер запущен не через юнит, а вручную (`cargo build --release` из `docs/SERVER.md:13`, затем
`./tunnel-server 0.0.0.0:5555 --data ./data` — такой запуск ничем не запрещён, а `--data` по умолчанию вообще
относительный `tunnel-data`, `docs/SERVER.md:74`) либо с собственным `--data`; umask 022 → каталог 0755,
`server.json` 0644. `server.json` содержит открытые `ed_seed`/`x_seed` сервера и ключи **всех** групп
(`Persisted`), а `client.json` — identity клиента (§15 #4 признаёт открытое хранение).

**Влияние.** Чтение `server.json` = имперсонация сервера: MITM на всех клиентах (клиент принимает только
подпись сервера), расшифровка группового трафика (ключи эпох), вход в любую группу от имени сервера-участника.
Это S1-по-влиянию, но требует локального доступа и не-юнит запуска, поэтому S2.

**Предусловия.** Многопользовательский Linux; запуск не через `infrastructure/linux/tunnel-server.service`
(там `UMask=0077` и `StateDirectoryMode=0700` — это и есть фактический контроль) или свой `--data`.
На Windows каталог закрывает `winsvc::acl::secure_data_dir` — там находка не воспроизводится.

**Как проверить.** `umask 022; ./tunnel-server 0.0.0.0:5555 --data /tmp/vl; stat -c %a /tmp/vl /tmp/vl/server.json`.

**Рекомендация.** Явно: `create_dir_all` + `set_permissions(0o700)` на каталог, `OpenOptionsExt::mode(0o600)`
на tmp-файл и `set_permissions` после rename (`cfg(unix)`), независимо от umask; при старте проверять, что
каталог не доступен group/other, и отказываться работать иначе (как это уже делает Windows-ветка).

### SEC-02 · Локальные привилегии Windows · S2 · уверенность средняя

> **Проверено ведущим (2026-11-24).** Исходники крейта доступны в cargo-registry:
> `libloading-0.8.9/src/os/windows/mod.rs:70-71` — `Library::new` = `load_with_flags(filename, 0)`,
> а `:163-175` вызывает `LoadLibraryExW(name, 0, flags)` с `flags = 0`. Флаги
> `LOAD_LIBRARY_SEARCH_*` не передаются, значит действует стандартный порядок поиска,
> включающий CWD и `PATH`. Находка **подтверждена**, уверенность повышена до высокой;
> пункт «деградирует до S4 при `LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`» снимается.

**Evidence.** `crates/client/src/tun.rs:9-25`:
```rust
    if let Some(p) = explicit {
        return unsafe { wintun::load_from_path(p) }.context(format!("cannot load {p}"));
    }
    if let Ok(exe) = std::env::current_exe()
        && let Some(dir) = exe.parent()
    {
        let p = dir.join("wintun.dll");
        if p.exists() {
            return unsafe { wintun::load_from_path(&p) }
                .context(format!("cannot load {}", p.display()));
        }
    }
    unsafe { wintun::load_from_path("wintun.dll") }
        .context("wintun.dll not found (положи рядом с exe или укажи --dll)")
```

Голое имя (не абсолютный путь) уходит в загрузчик; `crates/client/src/store.rs:98` прямо документирует
«пусто — рядом с exe или из PATH». В отличие от службы (`winsvc::service_wintun_dll` вызывает
`acl::verify_install_dir`, `crates/winsvc/src/common.rs:309-314`), клиент никакой проверки ACL каталога не делает.

**Сценарий.** `tunnel-client run` требует администратора (`crates/client/src/main.rs:1269`: «нужен запуск от
администратора»). Атакующий — обычный пользователь (или вредонос в его контексте), который может писать в
каталог, откуда идёт поиск: текущий каталог процесса, каталог из `PATH` или каталог exe, если он доступен на
запись (проверки, как у службы, нет). Подкладывает `wintun.dll` → повышенный процесс грузит его и исполняет
код с правами администратора.

**Влияние.** Повышение привилегий до администратора из контекста обычного пользователя.

**Предусловия.** Пользователь запускает `run` из каталога, доступного атакующему на запись (Desktop, Downloads,
`C:\Temp`, сетевой ресурс), либо у атакующего есть запись в один из каталогов `PATH` (частый случай —
пользовательские каталоги в PATH).

**Как проверить.** Положить `wintun.dll` в CWD, запустить повышенный `tunnel-client run` под Process Monitor
(событие `Load Image`) и посмотреть путь; либо прочитать флаги `LoadLibraryExW` в `libloading 0.8.9`
(зависимость `wintun 0.5.1`, `Cargo.lock:3195-3205`). Если libloading передаёт
`LOAD_LIBRARY_SEARCH_DEFAULT_DIRS|DLL_LOAD_DIR`, поиск по CWD/PATH не выполняется и находка деградирует до
S4 (мёртвый fallback).

**Рекомендация.** Убрать fallback на голое имя; грузить только `System32\\wintun.dll` или файл рядом с exe,
и перед загрузкой вызывать `winsvc::acl::verify_install_dir` (код уже есть). В §15 добавить строку про CLI/TUI.

### SEC-03 · Identity: экспорт · S3 · уверенность высокая

**Evidence.** `crates/client/src/profile.rs:335-358` — ограничение прав только под Unix:
```rust
/// Пишет файл, доступный только владельцу (0600 на Unix): в экспорте могут
/// лежать открытые seed'ы.
fn write_private(path: &Path, data: &[u8]) -> Result<()> {
    let mut opts = std::fs::OpenOptions::new();
    opts.write(true).create(true).truncate(true);
    #[cfg(unix)]
    {
        use std::os::unix::fs::OpenOptionsExt;
        opts.mode(0o600);
    }
```
Путь — обязательный позиционный аргумент (`usage: export-identity <файл>`, `crates/client/src/main.rs:193-195`),
то есть файл создаётся там, куда указал пользователь (на практике — часто текущий каталог).

**Сценарий.** `tunnel-client export-identity C:\Temp\me.json` (без пароля) на Windows: файл с открытыми
`ed_seed`/`x_seed` получает унаследованные ACL каталога. Любой другой пользователь машины (или процесс,
читающий `C:\Temp`, общий/сетевой каталог) забирает identity: друзья, членство в группах, федерация.

**Как проверить.** `tunnel-client export-identity C:\Temp\x.json` на Windows, затем `icacls C:\Temp\x.json` —
в ACL будут `BUILTIN\Users`/`NT AUTHORITY\Authenticated Users` с наследованием, а в файле открытый `ed_seed`.

**Влияние.** Полная имперсонация клиента. §15 #13 честно говорит «права 0600 на Unix», но в таблице
остаточных рисков нет строки «на Windows защиты нет вообще» — оператор может считать, что файл закрыт.

**Рекомендация.** На Windows ставить явный DACL (SYSTEM + владелец), как `DATA_DIR_SDDL`; либо писать через
DPAPI; либо отказывать в незашифрованном экспорте за пределы защищённого каталога данных.

### SEC-04 · Криптография: отсутствие zeroize · S3 · уверенность высокая

**Evidence.** Ключи — простые массивы и клонируемые структуры, стирания нет:
- `crates/protocol/src/lib.rs:234` — `pub type SymKey = [u8; 32];`
- `crates/protocol/src/lib.rs:239-243` — `pub struct Identity { pub ed_seed: [u8; 32], pub x_seed: [u8; 32] }` с `#[derive(Clone)]`;
- `crates/client/src/engine.rs:326-327` — `struct KeyLog(Arc<Mutex<VecDeque<(proto::SymKey, KeyState)>>>)` хранит отслуженные ключи групп;
- `crates/protocol/src/handshake.rs:31-37` — стирание есть только у `EphemeralKey` (внутри `x25519_dalek::StaticSecret`),
  тогда как `Identity::x_seed` живёт до конца процесса.

**Сценарий.** Атакующий уже имеет доступ к файлам дампа (чужой крэш-дамп в `%ProgramData%\Microsoft\Windows\WER`,
гибернация/pagefile, отладочный дамп службы, снятый администратором или вредоносом) — и читает оттуда seed'ы,
не имея доступа к `client.json`/`server.json`.

**Влияние.** Дамп процесса, файл подкачки, крэш-дамп Windows Error Reporting (служба работает как SYSTEM)
содержат долговременные seed'ы и групповые ключи; после утечки дампа ключи не отозвать (identity сервера
меняется только `rotate-key`).

**Как проверить.** `procdump -ma <pid> dump.dmp`, затем поиск 32-байтового `ed_seed` из `client.json` в дампе;
либо `grep -rn 'Zeroize\|zeroize' crates/protocol/src crates/client/src` — совпадений нет.

**Рекомендация.** `zeroize` + `ZeroizeOnDrop` для обёрток над `SymKey` и `Identity`, убрать `Clone` у seed'ов,
ограничить время жизни `KeyLog`.

### SEC-05 · Криптография: проверка ed25519 · S3 · уверенность средняя

**Evidence.** `crates/protocol/src/lib.rs:284-288`:
```rust
    pub fn verify(pubkey: &[u8; 32], msg: &[u8], sig: &[u8; 64]) -> Result<()> {
        let vk = VerifyingKey::from_bytes(pubkey)?;
        vk.verify(msg, &ed25519_dalek::Signature::from_bytes(sig))
            .map_err(|_| anyhow!("bad signature"))
    }
```
Используется `verify`, а не `verify_strict`; через эту функцию проверяются HELLO3, WELCOME, звенья ротации,
`MESH_HELLO` и федеративные приветствия.

**Сценарий.** Атакующий (участник mesh/федерации или клиент на этапе HELLO3) предъявляет ключ, у которого в
точке A есть компонента малого порядка, и подпись, у которой такая компонента есть в R. Не-строгая проверка
уравнения такие значения принимает: для одной и той же пары (ключ, сообщение) появляется несколько разных
валидных подписей, а для ключа с малой компонентой подпись подделывается без секрета. Практического обхода
аутентификации это не даёт, пока мы пиним/TOFU-закрепляем ключ (атакующий и так выбрал бы свой ключ), но
ломает предположение «подпись канонична и единственна»: дедуп/кеш по байтам подписи, сравнение подписей и
будущие схемы, опирающиеся на строгость, станут неверными.

**Влияние.** Принимаются ключи и подписи с компонентами малого порядка (torsion) в A/R — малеабельность
подписи и возможность подделки для вырожденного ключа. Практическая эксплуатация ограничена: ключи, которые мы
проверяем, либо закреплены (pin/friend code), либо принимаются по TOFU, где атакующий и так выбирает ключ.
Домены подписи разделены, поэтому перенос подписи в другой контекст невозможен. Каноничность S (S < L)
проверяется и в не-строгом режиме — здесь разницы нет.

**Как проверить.** Юнит-тест: ключ/подпись с компонентой малого порядка в A или R проходит `verify` и
отвергается `verify_strict` (поведение задокументировано в ed25519-dalek). Плюс
`grep -n 'verify(' crates/protocol/src/*.rs` — все вызовы идут через `Identity::verify`.

**Рекомендация.** `verify_strict` для всех внешних ключей.

### SEC-06 · DoS: число сессий · S3 · уверенность средняя

**Evidence.** `crates/server/src/lib.rs:1126-1140` — на IP ограничен только темп HELLO (5/с, burst 20):
```rust
    fn allow_ip(&self, ip: IpAddr) -> bool {
        use std::hash::BuildHasher;
        let (rate, burst) = (self.limits.hello_rate, self.limits.hello_burst);
        let key = ip_key(ip);
        let shard = self.ip_hash.hash_one(key) as usize % IP_SHARDS;
        ip_take(
            &mut self.per_ip[shard].lock().unwrap(),
            key,
            rate,
            burst,
            IP_SHARD_MAX,
        )
    }
```
Предела на число живых сессий (глобально и на IP) в `Limits` (`crates/server/src/lib.rs:122-176`) нет;
`session_timeout` 30 с не помогает, пока атакующий пингует.

**Сценарий.** Одна identity (генерация ключей бесплатна), один IP: 5 новых сессий в секунду с разных
исходных портов (до ~65 тыс. портов на адрес), каждая держится CTRL_PING. За час — ~18 тыс. сессий, каждая
с ключами, окном повторов, token-bucket релея и очередью писателя.

**Как проверить.** Скрипт на 5 HELLO3/с с уникальных портов одной identity + CTRL_PING каждые 5 с; через 10 мин
смотреть `sessions` в `/metrics`/отладочном выводе и RSS процесса — растут монотонно, предела нет.

**Влияние.** Постепенный рост памяти и числа таймеров; при заполнении портов — отказ новым клиентам того же
адреса. Не мгновенный DoS, поэтому S3.

**Рекомендация.** Предел `max_sessions` глобально и на IP с вытеснением самой старой сессии; метрика занятости.

### SEC-07 · CI · S4 · уверенность высокая

**Evidence.** `.github/workflows/ci.yml:1-16` — нет `permissions:` на уровне workflow (только у job `audit`,
строки 94-97).

**Сценарий.** PR из ветки этого же репозитория (или скомпрометированный `build.rs`/тест) исполняется в job
`test` с токеном, у которого по умолчанию есть `contents: write`; код шага может эксфильтрировать токен или
пушить в репозиторий.

**Влияние.** Все остальные job получают дефолтные права `GITHUB_TOKEN`; для `push` в `master` это запись.
Компрометация шага сборки (или PR из ветки этого же репозитория) даёт токен с правом записи.

**Как проверить.** `grep -n 'permissions' .github/workflows/ci.yml` — только внутри job `audit`; в логе job
видно `GITHUB_TOKEN` с областью `contents: write`.

**Рекомендация.** `permissions: contents: read` на уровне workflow, повышение — точечно в job.

### SEC-08 · Дрейф документации · S4 · уверенность высокая

**Evidence.** `infrastructure/linux/tunnel-server.service:30-31`:
```
# SIGTERM: обработчика в сервере пока нет — процесс завершается сразу,
# теряются изменения после последнего периодического сохранения (~3 с)
```
При этом обработчик есть и подключён: `crates/server/src/main.rs:105` (`signals::Shutdown::install()`),
`crates/server/src/signals.rs`, а §15 #15 утверждает «SIGTERM/SIGINT сохраняют состояние (`Server::stop`) ✅».
Рядом устаревший маркер `#![allow(dead_code)] // подключается при интеграции` в `signals.rs:19` и `tcp.rs:33`,
хотя оба модуля используются (`crates/server/src/lib.rs:41`, `:263`).

**Сценарий.** Оператор читает юнит, видит «обработчика нет, изменения теряются» и либо не останавливает
сервер штатно (делает `kill -9`), либо, наоборот, считает финальный persist несостоявшимся и вручную правит
`server.json` — оба решения хуже, чем `systemctl stop`.

**Влияние.** Оператор, читающий юнит, делает неверный вывод о потере состояния при `systemctl stop` —
это влияет на решения об остановке сервера (например, перед `rotate-key`).

**Как проверить.** Сравнить строки 30-31 юнита с `crates/server/src/main.rs:105` и `crates/server/src/signals.rs`.

**Рекомендация.** Обновить комментарий юнита и снять устаревшие `allow(dead_code)`.

### SEC-09 · Федерация: обход лимитов входа · S3 · уверенность высокая

**Evidence.** `join_fed` не применяет ни `join_rate`, ни кулдаун повторного входа, хотя обычный `JOIN_GROUP` — применяет.

`crates/server/src/lib.rs:3027-3031`:
```rust
            if own {
                // Владелец здесь: вход — как JOIN_GROUP (ротация ключа).
                g.rotate(false);
                g.bump();
            }
```

Для сравнения — `crates/server/src/lib.rs:4091-4094` (`JOIN_GROUP`):
```rust
            anyhow::ensure!(
                g.owner == me || g.joins.take(sh.limits.join_rate, sh.limits.join_burst),
                "слишком много входов в группу — повторите позже"
            );
```

В `join_fed` (`crates/server/src/lib.rs:2980-3060`) нет ни `joins.take`, ни проверки `g.left`/`REJOIN_COOLDOWN`;
при этом каждый вход в локально-владеемую федеративную группу ротирует ключ (3029), а ответ — полный
`GROUP_STATE` (3057), то есть для группы на 253 участника ~215 КБ и ~175 кусков FRAG
(`crates/client/src/engine.rs:1584`). Список федеративных групп с uuid виден любой сессии: `push_fed_groups`
вызывается из HELLO-ветки (`crates/server/src/lib.rs:3327`, функция — 2950-2975).

**Сценарий.** Сервер запущен с `--federate`, есть хотя бы одна публичная федеративная группа (владелец — этот
сервер либо реплика). Атакующий — любая identity (бесплатна) с одной сессией: посылает `JOIN_FED(uuid)` и
`LEAVE_GROUP(gid)` по кругу. `ctrl_rate` = 50/с, то есть до 50 ротаций ключа в секунду на группу.

**Влияние.** Каждая ротация — новый ключ и `GROUP_UPDATE`/`GROUP_STATE` всем участникам (до 253), плюс
перестроение ~215 КБ состояния на каждый `JOIN_FED`; трафик участников группы прерывается на каждой ротации.
§15 #9 заявляет митигацию «Лимит входов на группу, кулдаун повторного входа 3 с» — через `JOIN_FED` она не действует.

**Предусловия.** `--federate` включён; есть публичная федеративная группа; атакующий знает uuid (виден всем).

**Как проверить.** Сервер с `--federate`, группа с владельцем A; B посылает `JOIN_FED`/`LEAVE_GROUP` 20 раз в
секунду — счётчик эпохи группы растёт на ~20/с, лимит `joins` не срабатывает.

**Рекомендация.** Применить в `join_fed` те же два гейта, что в `JOIN_GROUP` (лимит входов группы и кулдаун
после выхода), либо отдельный лимит на `JOIN_FED`; при `own == false` не перестраивать `GROUP_STATE` целиком,
если ревизия не изменилась.


## 4. Проверено — находок нет

Ниже — проверки, которые я считал наиболее вероятными источниками S1. Все они сошлись: контроль есть в коде
и делает то, что заявлено.

1. **Построение nonce и запрет повтора.** ctrl: `nonce = 0⁴ || counter LE`, `aad = hdr` (`crates/protocol/src/lib.rs:487-513`);
   группа: `nonce = src_ip BE || counter LE`, `aad = hdr || GroupHeader` (`crates/protocol/src/lib.rs:576-581, 595-639`).
   Ключи направлений разные (`c2s`/`s2c`, `crates/protocol/src/handshake.rs:104-137`), поэтому совпадение счётчиков
   в разные стороны nonce не повторяет.
2. **Переполнение счётчика — паника, а не обёртка:** `crates/protocol/src/lib.rs:471-477` (`checked_add(1).expect(...)`),
   тот же приём в клиенте (`crates/client/src/engine.rs:596`).
3. **Рестарт клиента не даёт повтор nonce под старым ключом группы.** Ключи групп клиент не хранит, а сервер
   ротирует ключ всех групп участника на каждом HELLO3: `crates/server/src/lib.rs:3598-3610`
   («HELLO участника — ротация ключа всех его групп (клиент ключи не хранит)»). После рестарта клиент получает
   новый ключ и начинает счётчик с нуля — это безопасно. Это ключевая проверка: без неё был бы S1.
4. **Состояние счётчиков привязано к материалу ключа, а не к номеру эпохи:** `KeyLog`/`KeyState`
   (`crates/client/src/engine.rs:312-349, 489-524`): возврат к отслуженному ключу продолжает его счётчик, а
   тот же номер эпохи с другим ключом (откат после падения сервера) окон не наследует — ровно то, что нужно.
5. **x25519: точка малого порядка отвергается** в обоих DH — `Identity::dh` (`crates/protocol/src/lib.rs:270-277`)
   и `EphemeralKey::dh` (`crates/protocol/src/handshake.rs:53-60`), через `was_contributory()`.
6. **Cookie анти-DoS:** blake3-keyed от `"tunnel/v3/cookie" || ip || port || eph_pub || bucket`, 16 байт,
   принимается текущий и предыдущий bucket (30-60 с), сравнение `ct_eq` (`crates/protocol/src/handshake.rs:189-227`).
   Подпись HELLO3 проверяется **после** cookie (`crates/server/src/lib.rs:3415-3430`) — дорогая операция не
   выполняется для подделанных адресов.
7. **Анти-усиление.** CHALLENGE — 17 байт тела (`crates/protocol/src/handshake.rs:327-332`) против ~164 байт
   минимального HELLO3; WELCOME/`GROUP_STATE` уходят только после cookie; открытые ответы дополнительно
   ограничены общим бюджетом (`crates/server/src/lib.rs:1143-1148`) и шардированной картой по IP
   (`:1126-1140`, переполнение шарда — отказ новым адресам). Усиления нет.
8. **Домены подписи и KDF разделены.** `"tunnel/v3/hello|welcome|rotate|cookie|session|c2s|s2c"`, mesh и федерация —
   свои домены (`MESH_DOMAIN`, `FED_DOMAIN`, `crates/protocol/src/mesh.rs:124-127`, `federation.rs:105-108`),
   есть тест, что ключи mesh не совпадают с `c2s` (`mesh.rs:814`). Метки `tunnel/v3/*` при `PROTOCOL_VERSION = 4`
   — **не расхождение**: `docs/PROTOCOL.md:82,94,167,187-189` задаёт их дословно так же, это стабильные
   домены-разделители, а не маркер версии.
9. **Цепочка ротации ключа сервера** (`resolve_pin`, `crates/protocol/src/handshake.rs:509-532`): требуется звено
   с `old_ed == pinned`, сцепление (`p[1].old_ed == p[0].new_ed`), валидные подписи и последнее звено ровно в
   (`server_ed`, `server_x`). Подделка цепочки без ключа закреплённого сервера невозможна.
10. **Релей проверяет отправителя:** сессия есть, отправитель — участник группы, и `m.ip == h.src`
    (`crates/server/src/lib.rs:2144-2166`); получатель — участник, `detached` не получает (`:2164-2171`).
11. **Прямой путь:** получатель требует, чтобы адрес источника был известен от сервера для этого участника
    (`crates/client/src/engine.rs:5584-5595`), а внутренний IPv4-источник DATA совпадал с `h.src` (`:5571-5574`) —
    подмена L3-источника внутри группы не проходит. Оговорка: `is_relay` включает `src == env.server()`
    (`:5543`), поэтому участник, подделавший адрес сервера, проверку адреса обходит — но это ровно принятый
    риск §15 #2 (общий ключ группы, подписи отправителя нет), а не новый дефект.
12. **GET_GROUP только участнику** (`crates/server/src/lib.rs:3833-3847`): не-участник получает ошибку, а не ключ.
13. **Административные команды — только владелец:** KICK/BAN (`:4427`), UNBAN (`:4490`), TRANSFER_OWNER (`:4508`),
    RENAME (`:4531`), DELETE_GROUP (`:4540`); владельца исключить нельзя (`:4428`), баны ограничены (`:4429-4432`),
    передача — только участнику (`:4509-4512`).
14. **Вход в приватную группу:** приглашение с TTL, бан, полнота, надгробие, кулдаун повторного входа и лимит
    входов (`crates/server/src/lib.rs:4029-4097`); проверка «приватная после выхода» стоит до ветки «уже участник».
15. **Переиспользование gid и надгробий не путает ключи:** `alloc_gid` не берёт gid с живым надгробием
    (`crates/server/src/lib.rs:933-945`), а новая группа всегда получает новый случайный ключ (`:3979-3980`).
    Старый ключ под тем же gid не воскресает: другой материал ключа заменяет текущий (`set_key`, `crates/client/src/engine.rs:496-524`),
    а счётчики отслуженного ключа остаются в `KeyLog`.
16. **FRAG без перекрытий и с ограниченной памятью:** на каждый `idx` свой слот, длины кусков проверяются
    (`crates/protocol/src/frag.rs:85-118`), ≤ 8 сборок × 281 600 байт, таймаут 5 с (`:15-23, 130-135`).
17. **Окно повторов 1024, `check` и `commit` раздельно** (`crates/protocol/src/replay.rs:5,39,54`): окно не
    двигается до успешной расшифровки (`crates/client/src/engine.rs:1834-1840`), поэтому мусор не «съедает» окно.
18. **Имена и статусы чистятся от управляющих символов** (`clean`, `crates/server/src/lib.rs:1249-1257`;
    применяется к имени в HELLO3 `:3534`, статусу `:3880`, именам групп `:3965, 4529`) — инъекция переводов строк
    в лог сервера и escape-последовательностей в TUI через имя/статус не проходит.
19. **Метрики без кардинальности:** фиксированный список из 18 имён (`crates/server/src/metrics.rs:134`), меток
    с пользовательскими значениями нет.
20. **Named pipe:** `PIPE_REJECT_REMOTE_CLIENTS | PIPE_TYPE_BYTE | PIPE_WAIT`, `FILE_FLAG_FIRST_PIPE_INSTANCE` на
    первом экземпляре (`crates/ipc/src/transport/windows.rs:270-300`), SDDL `O:SY|O:BA` + владельцу `0x12019b`
    (`:209-211`), клиент открывает с `SECURITY_IDENTIFICATION` (`:340-349`) и проверяет сервер таблицей
    `decide_trust` (`:405-419`) — неповышенный процесс того же пользователя отвергается.
21. **Windows-служба:** `service_wintun_dll` берёт только `current_exe().parent()` и вызывает `verify_install_dir`
    (`crates/winsvc/src/common.rs:309-314`), проверка DACL exe, DLL и каталогов-предков (`crates/winsvc/src/acl.rs:97-114`),
    `secure_data_dir` для каталога данных (`:118-146`), failure actions 5/10/30 с (`crates/winsvc/src/install.rs:231-240`).
    Демон в принципе не читает путь DLL из конфига (`crates/daemon/src/engine_backend.rs:156, 191-205`) —
    заявленный запрет `--dll` для службы выполнен «по построению».
22. **Мьютекс single-instance:** захват имени посторонним не блокирует (`crates/ipc/src/lock.rs:188-245`),
    `owner_trusted` + `squatted()`; SDDL мьютекса `D:(A;;GA;;;SY)(A;;GA;;;BA)(A;;0x120000;;;AU)` (`:311`).
23. **Цепочка поставок:** `deny.toml` — единственный `ignore` (`RUSTSEC-2024-0370`) с обоснованием и проверкой
    достижимости; CI гоняет fmt/clippy/test на Linux/macOS/Windows + `cargo-deny` + `cargo-audit`
    (`.github/workflows/ci.yml:17-102`); внешних секретов, кроме `GITHUB_TOKEN` в job `audit`, нет.
24. **Логи сервера — только `eprintln!` в stderr** (`crates/server/src/lib.rs:1095-1099`), файлов журнала код не
    пишет: залив диска логами ограничен внешним journald, а не кодом.

## 6. Гипотезы и вопросы к владельцу

1. **`is_relay` включает `src == env.server()`** (`crates/client/src/engine.rs:5543`). Значит, кадр, пришедший с адреса
   сервера, не проверяется на «адрес от сервера» для отправителя. Участник группы, умеющий подделывать
   UDP-источник (on-path или blind-спуфинг), обходит проверку адреса и может выдать свой кадр за кадр другого
   участника — ровно то, что уже принято в §15 #2, но заявленная там митигация «прямой канал — по адресам от
   сервера» в этом случае не работает. Вопрос: нужен ли shortcut, если сервер и так помечает свои кадры флагом
   `relayed`, а подлинность даёт AEAD? Предложение: не доверять адресу источника и убрать `|| src == env.server()`.
2. **SEC-01:** планируется ли перенести права каталога/файла состояния в код (`0700`/`0600`), чтобы защита не
   зависела от юнита и umask? Сейчас `server.json` защищён только `StateDirectoryMode=0700` + `UMask=0077`
   (`infrastructure/linux/tunnel-server.service:24,57`), а `rotate-key`, запущенный руками, пишет файл с umask оболочки.
3. **SEC-02:** fallback `wintun::load_from_path("wintun.dll")` (`crates/client/src/tun.rs:23`) — намеренное решение
   «чтобы работало из PATH» или недосмотр? Для повышенного `run` это путь повышения привилегий; `verify_install_dir`
   у клиента не вызывается вовсе.
4. **SEC-06:** есть ли причина не ограничивать число сессий (глобально и на IP)? `session_timeout` 30 с не мешает
   держать сессии пингами; при 5 HELLO/с на IP за час накапливается ~18 тыс. сессий.
5. **SEC-09:** `JOIN_FED` без `join_rate`/кулдауна — намеренно (публичные федеративные группы открыты) или
   пропущенный гейт? Если намеренно, стоит записать это в §15 #9: текущая формулировка обещает лимит.
6. **`verify_strict` (SEC-05):** есть ли причина использовать не-строгую проверку ed25519? Все ключи приходят
   извне (HELLO3, WELCOME, звенья ротации, mesh, федерация) — это как раз случай для `verify_strict`.
7. **Одна статическая x25519-пара на два протокола:** `Identity::x_seed` используется и в рукопожатии с сервером
   (`crates/protocol/src/handshake.rs:139-157`), и как mesh-ключ (`crates/client/src/dht.rs:65`, mesh-секция
   `GROUP_STATE`). Домены KDF разные (`MESH_DOMAIN` vs `tunnel/v3/session`), но планируется ли раздельная пара?
8. **Приватность журналов:** сервер пишет имя и IP каждого онлайн-клиента (`crates/server/src/lib.rs:3596`). Это
   соответствует §15 #3, но на публичном сервере journald хранит эти данные долго. Есть ли политика хранения
   (ротация/срок) в `infrastructure/linux/`, или это целиком на операторе?
9. **Устаревшие маркеры:** `#![allow(dead_code)] // подключается при интеграции` в `crates/server/src/signals.rs:19`
   и `crates/server/src/tcp.rs:33` при том, что оба модуля используются (`crates/server/src/lib.rs:41, 263`), плюс
   комментарий юнита про SIGTERM (SEC-08) — планируется ли синхронизация?
10. **Паддинг:** §15 #3 фиксирует отсутствие паддинга (размеры видны). Для v4 это осознанно, но при работе через
    недоверенную сеть размеры выдают профиль трафика; есть ли это в планах?

## 7. Итог

Криптографическое ядро сделано аккуратно — заметно лучше среднего для self-hosted решений такого класса.
Nonce строятся из раздельных по направлениям ключей и монотонных счётчиков (переполнение — паника, а не обёртка),
AEAD покрывает открытые заголовки (AAD), cookie привязан к адресу/порту/эфемерному ключу и bucket-у и сравнивается
константно, DH отвергает точку малого порядка, подписи доменно разделены, цепочка ротации сервера проверяется по
всем звеньям, а счётчики ключей групп привязаны к материалу ключа, а не к номеру эпохи. Ключевой инвариант «нет
повтора nonce под ключом» держится в том числе потому, что сервер ротирует ключи всех групп участника на каждом
HELLO3 (`crates/server/src/lib.rs:3598-3610`): без этого рестарт клиента дал бы повтор nonce и был бы S1.
Находок S1 я не обнаружил.

Найденное — в основном «контроль заявлен, но живёт не там, где заявлен». Главные три: **SEC-01** — права каталога и
файла состояния задаёт systemd-юнит и umask, а не код, поэтому запуск в обход юнита (документация его не
запрещает, `--data` по умолчанию относительный) отдаёт `server.json` с identity сервера и ключами всех групп
любому локальному пользователю; **SEC-02** —
повышенный `tunnel-client run` грузит `wintun.dll` по голому имени без проверки ACL каталога, которую служба
делает; **SEC-09** — `JOIN_FED` обходит лимит входов и кулдаун, обещанные в §15 #9, что даёт дешёвую чехарду
ротаций ключа на федеративных группах. К ним примыкают SEC-03 (экспорт identity на Windows без явного DACL) и
SEC-04 (отсутствие zeroize при том, что seed`ы живут в куче и в клонах).

Авторизация проверена по матрице команд: административные операции — только владелец, `GET_GROUP` — только
участник, приватная группа требует приглашения, переиспользование gid/надгробий не путает ключи, релей сверяет
`src_ip` с сессией. Windows-часть (SDDL пайпа, `FIRST_PIPE_INSTANCE`, `decide_trust`, проверка каталога установки
и каталога данных, проверка владельца мьютекса) соответствует документации; единственная брешь — клиентский путь
загрузки DLL (SEC-02). Цепочка поставок в порядке: один обоснованный `ignore` в `deny.toml`, CI с
fmt/clippy/test/deny/audit; из гигиены — отсутствие `permissions` на уровне workflow (SEC-07).

Ограничения отчёта: всё статически, без сборки и эксплуатации; `probe.rs`, лимиты §18.4 и TUI проверены выборочно
(помечено ⏳ в §5); поведение `libloading 0.8.9` не подтверждено исходниками (SEC-02 — уверенность средняя). Если
`libloading` использует `LOAD_LIBRARY_SEARCH_DEFAULT_DIRS`, SEC-02 деградирует до S4.
