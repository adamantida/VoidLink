## 1. Область, метод, что НЕ проверялось

Инструменты: `read`/`grep`/`glob`, CodeGraph, `git` только на чтение. Сборка/тесты/clippy **не запускались** (по условию задачи: гейты параллельно гоняет ведущий, машина занята) — все выводы статические, подтверждены цитатами; эксплуатационные проверки вынесены в поле «как проверить».

### CORE-01 · федерация: любой узел интернета закрепляется TOFU и навсегда занимает слот пина · **S2** · уверенность высокая

**Evidence.** `crates/server/src/federation.rs:1395-1403`:
```rust
fn on_handshake_frame(sh: &Shared, src: SocketAddr, typ: u8, body: &[u8]) -> bool {
    if !sh.fed.lock().unwrap().enabled {
        return false;
    }
    // Общий бюджет открытых ответов: рукопожатие не должно превращаться в
    // усилитель/нагрузку на подпись.
    if !sh.allow_plain() {
        return false;
    }
```
`crates/server/src/federation.rs:636-647`:
```rust
        if !self.pins.contains_key(&hello.ed) {
            if self.pins.len() >= MAX_PEERS {
                return Ok(vec![Action::Reject(format!(
                    "SRV_HELLO с {src}: таблица пиров заполнена ({MAX_PEERS})"
                ))]);
            }
            let pin = Pin {
                addr: src,
                ed: hello.ed,
                x: hello.x,

```
`federation.rs:127`: `pub(crate) const MAX_PEERS: usize = 64;`. Пин сохраняется на диск: `federation.rs:1351-1355` (`Action::Pinned` → `sh.save_soon()`), в `server.json → federation.peers` (`federation.rs:1688-1703`). Флага снятия пина нет: `main.rs:44-49` (USAGE) знает только `--federate/--peer/--fed-pool`.

**Сценарий.** Сервер запущен с `--federate` и доступен из интернета (обычная эксплуатация: пиры — другие хосты). Атакующий генерирует 64 пары ключей ed25519/x25519 и посылает 64 `SRV_HELLO` с разных source-портов (или адресов). Каждый проходит `hello.verify(&expected = hello.ed)` — то есть проверку подписи **самим заявленным ключом** (TOFU, `federation.rs:579-584`), закрепляется и попадает в `server.json`. Дальше `self.pins.len() >= MAX_PEERS` отвергает **любой** новый `SRV_HELLO` — в том числе от настоящего пира.

**Влияние.** (1) Федерация с новым сервером невозможна навсегда: у таблицы пинов нет TTL, эвикции и CLI-снятия, чинится только ручной правкой `server.json`. (2) 64 записи в `server.json` + 64 срочных сохранения (`save_soon`). (3) Закреплённый «пир» получает сессию и право присылать `FED_GROUP_PUSH/DELTA/ADDR`: например `on_group_delta` от него превращается в `Action::JoinRequest` → `fed_accept_join` (`lib.rs:2867-2946`) добавляет **произвольные** `pk` в любую нашу публичную группу с ротацией ключа на каждого. Предусловие: доступность UDP-порта сервера (федерация своего порта не заводит — `federation.rs:19-21`); аутентификации, кроме самоподписи, нет. Это **не** принятый риск №19 SECURITY.md («первое знакомство уязвимо к MITM» — про подмену известного пира), а исчерпание таблицы и неудаляемое состояние.

**Как проверить.** `tunnel-server --federate --data <tmp>`; послать 64 `SRV_HELLO` с разными ключами (`SrvHello::new` + `to_frame`); затем `--peer <настоящий>` — в логе `таблица пиров заполнена (64)`; в `server.json` 64 чужих `peers`. Тест-каркас: `federation.rs:2387` (`hint_рукопожатие_пин_и_рестарт`).

**Рекомендация.** Закреплять только тех, с кем мы сами инициировали рукопожатие (`pending` содержит `src`/`expected_ed`) либо кто заявлен в `--peer/--fed-pool/SERVER_HINT`; для «входящих без приглашения» — отдельная ограниченная и **не** персистентная таблица с TTL; добавить `--unpeer <ed|addr>` и/или TTL пина; на отказ по переполнению — метрика.

### CORE-02 · TCP-фолбэк делит пространство адресов с UDP: чужие кадры уходят не тому транспорту, `close` TCP убивает UDP-сессию · **S2** · уверенность высокая (механизм) / средняя (выполнимость)

**Evidence.** Контракт самого модуля — `crates/server/src/tcp.rs:18-23`:
```rust
//! Адресация: TCP и UDP — РАЗНЫЕ пространства адресов. Один и тот же
//! `ip:port` может одновременно быть UDP-клиентом за NAT и TCP-соединением,
//! поэтому обработчик получает `Peer`, помеченный транспортом. При интеграции
//! сессии сервера нужно ключевать по `Peer` (или держать отдельную карту для
//! TCP), а ответ слать по транспорту из ключа сессии — НЕ маршрутизировать
//! по `is_live(Peer::Tcp(addr))` для адреса, пришедшего из UDP-сокета.
```
Интеграция делает ровно то, что запрещено — `crates/server/src/lib.rs:405-413`:
```rust
            let on_frame: tcp::FrameHandler = {
                let sh = shared.clone();
                Arc::new(move |peer, frame| handle_datagram(&sh, peer.addr(), frame))
            };
            let on_close: tcp::CloseHandler = {
                let sh = shared.clone();
                Arc::new(move |peer| drop_session_at(&sh, peer.addr()))
            };
```
Сессии ключуются по «голому» `SocketAddr` (`lib.rs:830-832`, `3567`), а отправка выбирает транспорт по адресу — `lib.rs:1110-1123`:
```rust
    fn send_to(&self, frame: &[u8], addr: SocketAddr) {
        if let Some(t) = self.tcp.get() {
            let peer = tcp::Peer::Tcp(addr);
            if t.is_live(peer) {
                if !t.send(peer, frame) {
                    self.drop_frame();
                }
                return;
            }
        }
        let _ = self.sock.send_to(frame, addr);
    }
```
Закрытие TCP снимает сессию по адресу без проверки транспорта — `lib.rs:1073-1079`:
```rust
fn drop_session_at(sh: &Shared, addr: SocketAddr) {
    let mut out = Outbox::new();
    {
        let mut s = sh.state.write().unwrap();
        let Some(ses) = s.remove_session(&addr) else {
            return;
        };
```

**Сценарий.** У жертвы живая UDP-сессия с адреса `X = ip:port`. Атакующий открывает **TCP**-соединение к серверу, чей source-адрес тоже `X` (тот же публичный IP и тот же номер порта; TCP и UDP — независимые пулы портов, поэтому совпадение возможно: один NAT/хост, CGNAT, офисная сеть — вероятность растёт как `N²/2/28000` для N клиентов за одним IP). Рукопожатие по TCP **не нужно**: достаточно, чтобы запись появилась в реестре (`admit`, `tcp.rs:305-363`). С этого момента `send_to` отдаёт все кадры сессии `X` в TCP-соединение атакующего: `GROUP_STATE` с ключом группы, `GROUP_UPDATE`, `INVITE_LIST`, `WELCOME`. Обратный вариант: атакующий открывает и сразу закрывает TCP с адреса `X` → `on_close` → `drop_session_at(X)` снимает **UDP**-сессию жертвы (повторяемо — DoS без лимита на число TCP-соединений сверх 8 на IP).

**Влияние.** При выполнимом совпадении `ip:port` — выдача ключа группы чужому соединению (потенциал S1 по шкале: утечка ключей) и/или снос чужой сессии. При невыполнимом — тихая несовместимость: честный TCP-клиент и честный UDP-клиент с одним адресом не могут сосуществовать, кадры одного уходят другому.

**Как проверить.** Тест: поднять сервер, `Raw`-клиент по UDP с порта P; отдельным TCP-сокетом подключиться к серверу, **предварительно забиндив локальный порт P**; послать `GET_GROUP` по UDP и прочитать кадры из TCP-сокета. Ожидаемо (дефект): в TCP приходит `GROUP_STATE`; при закрытии TCP `s.sessions` теряет UDP-сессию.

**Рекомендация.** Ключевать сессии по `Peer` (UDP/TCP) либо держать отдельную карту TCP-сессий, как предписано в шапке `tcp.rs`; в `drop_session_at` передавать `Peer` и снимать сессию только своего транспорта; `send_to` должен брать транспорт из ключа сессии, а не угадывать по `is_live`.

### CORE-03 · повтор HELLO3 участника — ротация ключа всех его групп и дельта всем участникам: усиление ×250 на третьих лиц · **S3** · уверенность высокая

**Evidence.** `crates/server/src/lib.rs:3597-3611`:
```rust
    out.push((src, welcome));
    // HELLO участника — ротация ключа всех его групп (клиент ключи не
    // хранит). Ему — GROUP_STATE целиком, остальным — дельта kind 1.
    for gid in s.groups_of(&ed) {
        let g = s.groups.get_mut(&gid).unwrap();
        if let Some(m) = g.members.get_mut(&ed) {
            m.name = name.clone();
            m.status = status.clone();
        }
        g.rotate(false);
        let base = g.bump();
        let g = &s.groups[&gid];
        push_group_state(s, g, src, &s.sessions[&src], out);
        push_update(s, g, base, &Change::Member(ed), Some(&ed), out);
    }
```
`push_update` шлёт по кадру **каждому** онлайн-участнику (`lib.rs:3083-3089`). Единственный ограничитель — `hello_rate` = 5/с на IP (`lib.rs:129-132`, `185-187`), кулдаун `REJOIN_COOLDOWN` касается только JOIN (`lib.rs:4077-4084`).

**Сценарий.** Атакующий с одной identity в публичной группе на 253 участника циклит: `HELLO3` → `CHALLENGE` → `HELLO3+cookie` с новым `eph` (3 датаграммы). 5 циклов/с → 5 ротаций ключа группы в секунду и 5×252 = 1 260 кадров `GROUP_UPDATE`/с (~150 байт каждый) третьим лицам.

**Влияние.** ~200 КБ/с и ~1 260 пакетов/с на чужой трафик с 5 пакетов/с входящих (≈250× по пакетам); ключ группы меняется 5 раз/с — клиент, потерявший дельту, обязан делать `GET_GROUP` (`client/src/engine.rs:2459`), иначе его кадры отбрасываются. Нужна валидная identity и членство (вход в публичную группу ограничен `join_rate` = 1/с на группу — но нужен один вход).

**Как проверить.** В тесте: `Raw`-клиент в группе с 253 участниками, 20 циклов HELLO3 с новым `eph`; посчитать `GROUP_UPDATE` у второго клиента и `relayed`/`dropped` сервера; замерить `epoch` группы (растёт на 1 за цикл).

**Рекомендация.** Не ротировать ключ на повторный HELLO3 той же identity в пределах окна (или ротировать не чаще `join_rate` на группу); лимит HELLO3 на identity, а не только на IP; при «слишком частом» HELLO3 участника — отвечать текущим `GROUP_STATE` без ротации.

**Как проверить.** Тест по образцу `federation.rs:2524` (`репликация_группы_push_и_delta`): после `ReplGroup` от пира вызвать `handle_mutation(KICK)` от имени владельца (сессия на локальном сервере), затем прислать дельту с `rev+1` от источника — увидеть, что она не применилась (`g.rev` не изменился), а `g.key` остался локальным.

**Рекомендация.** Для `g.fed_origin.is_some()` отклонять мутации владельца (`ERROR` «группа реплицирована: изменения — на сервере-источнике») либо маршрутизировать их заявкой источнику (как `request_join`); как минимум — не менять `rev`/`key` локально.

### CORE-11 · тест `группа_253_участника...`: на Unix `set_recv_buffer` — пустышка, тест меряет буфер ОС · **S4** · уверенность высокая

**Evidence.** `crates/server/src/lib.rs:4684-4694`:
```rust
    /// Просит у ядра увеличенный буфер приёма UDP: длинное сообщение сервера
    /// (GROUP_STATE группы на 253 участника — ~215 КБ, ~175 кусков FRAG)
    /// приходит залпом, дефолтных 64 КБ на Windows не хватает и лишние
    /// датаграммы ядро выбрасывает — сборка не завершается никогда. Ошибка не
    /// критична: остаётся дефолт.
    ///
    /// Только Windows: на Linux (net.core.rmem_default) и macOS дефолт уже
    /// ≥ 128 КБ, тест там исторически зелёный, а libc в этом крейте нет —
    /// лишнюю зависимость ради одного теста не тянем.
    #[cfg(unix)]
    fn set_recv_buffer(_sock: &UdpSocket, _bytes: usize) {}
```
Запрос буфера — `lib.rs:4745`: `set_recv_buffer(&sock, 4 << 20);`. Продовый клиент при этом ставит `SO_RCVBUF` **и на Unix** — `client/src/engine.rs:1593-1606`, `const UDP_RECV_BUF: usize = 4 << 20;` (`engine.rs:1588`).

**Разбор (ответ ведущему; вердикт совпадает с его классификацией).**
- **(в) зависимость от буфера — есть, и она платформенная.** Арифметика по коду: `GROUP_STATE` теста = **197 972** байт (252 подставных по 785 байт на проводе: 32 pk + 1+255 имя + 4 ip + 1 online + 1+255 статус + 1+46 endpoint + 1+4×47 кандидаты; заголовок 91; реальный участник ~61) → **180** FRAG-кадров по 1 140 байт = **205 172** байт UDP. Комментарий `lib.rs:4685` («~215 КБ, ~175 кусков») — округление вверх, порядок тот же. На Linux `SO_RCVBUF` тестом не выставляется, действует `net.core.rmem_default` = 212 992 байт (хост ведущего), а учёт в ядре идёт по `skb->truesize` (~2,3 КБ на датаграмму 1 140 байт) → в буфере помещается **~92** датаграммы из 180. Значит тест на Linux держится только на том, что читающий поток успевает вычитывать во время залпа (паузы `SEND_BURST`=8 / `SEND_PAUSE`=1 мс дают ~25 мс на 180 кадров). На Windows зелено **потому, что** `set_recv_buffer` работает и даёт 4 МиБ. Комментарий «≥ 128 КБ, тест исторически зелёный» неверен для залпа 205 КБ — это и есть дефект теста.
- **(а) ретрансмиссии/подтверждения нет** — см. CORE-10: `FRAG` без ACK и повторов, очереди «дослать позже» нет (`Outbox` живёт до конца `flush`), потеря любого кадра = потеря сообщения, восстановление только по «подсказке эпохи» (следующее событие группы) или переподключением.
- **(б) два `GROUP_LIST`** — это (i) прямой ответ на `CREATE_GROUP` (`lib.rs:4018`) и (ii) объединённая рассылка из `housekeeping` по флагу `list_dirty` (`lib.rs:1781-1783` → `3333-3351`; флаг ставится в `4019`). Внутри одного обработчика `GROUP_STATE` кладётся в `out` **раньше** `GROUP_LIST` (`4017-4018`), а `flush` отправляет по порядку — «обогнать» ответ в рамках одного запроса нельзя. Рассылка из другого потока может **вклиниться** в залп 180 кадров (каждый `flush` паузит по 8 датаграмм) и добавить давление на буфер приёма, но причиной потери сама по себе не является; её приход в тесте доказывает, что путь «сервер → клиент» жив, а потерян именно залп.
- **Вердикт: хрупкий тест** (платформозависимое допущение + неверный комментарий; на Unix запрос буфера — пустышка, поэтому Windows зелёный, а Linux красный 4/4), **маскирующий реальный дефект устойчивости** (CORE-10). Это не дефект продукта и не влияние нагрузки: детерминизм объясняется арифметикой буфера.

**Дополнительный риск (по запросу ведущего): ошибка `setsockopt` игнорируется** (`engine.rs:1590-1591` «Ошибка не критична: остаётся дефолт»; значение не перечитывается через `getsockopt`).
- На Linux `SO_RCVBUF` клампится к `net.core.rmem_max` (типовое значение — те же 212 992; требует проверки `sysctl net.core.rmem_max` на конкретном хосте), т.е. 4 МиБ превращаются в ~2×212 992 ≈ 425 КБ. Для одного `GROUP_STATE` на 253 участника (205 КБ) это ~2× запас — продукт в типовой конфигурации защищён, но не «4 МиБ».
- Если буфер окажется меньше (пониженный `rmem_max`, контейнер с урезанными sysctl, Windows-политика), клиент об этом **не узнает**: ошибка проигнорирована, фактический размер не проверяется. Дальше срабатывает CORE-10: потеря кадра = потеря `GROUP_STATE`, а **повторного запроса состояния нет** — восстановление только когда придёт кадр с более новой эпохой (`engine.rs:2459`, `5514-5519` → `GET_GROUP` не чаще 1/с на группу, `132-133`, `3280-3287`) или после переподключения (`2969`). Для вошедшего последним это «тишина» без признака ошибки.
- Рекомендация: после `setsockopt` читать `getsockopt` и логировать фактический размер + метрика; при фактическом буфере меньше нескольких `GROUP_STATE` — либо предупреждать, либо (главное) добавить таймер повторного `GET_GROUP` после `JOIN`/`HELLO3` (CORE-10).

**Как проверить (решающий эксперимент).** В `#[cfg(unix)] fn set_recv_buffer` теста (`lib.rs:4693`) добавить `libc::setsockopt(SO_RCVBUF, 4<<20)` как в `client/src/engine.rs:1593-1606` и перезапустить. Зелёный → подтверждена буферная природа (тест починить, CORE-10 остаётся); красный → искать потерю в серверном пути отправки (тогда это дефект кода; первые подозреваемые — `send_to`, игнорирующий ошибку `lib.rs:1122`, и `split_frag`).

**Рекомендация.** Починить тест (libc-ветка `set_recv_buffer`, либо уменьшить группу, либо читать в отдельном потоке), `UDP_RECV_BUF` вынести в общий крейт, чтобы тест и продовый клиент настраивали сокет одинаково; добавить тест-инвариант на размер `GROUP_STATE` (CORE-08).

---

### CORE-12 · `релей_под_нагрузкой`: busy-wait + жёсткий бюджет 30 с в функциональном наборе · **S4** · уверенность высокая

**Evidence.** `crates/server/src/lib.rs:6479-6503`:
```rust
        let t0 = Instant::now();
        for i in 0..N {
            while i as u64 > got.load(Ordering::Relaxed) + WINDOW && t0.elapsed() < BUDGET {
                thread::yield_now();
            }
            a.sock.send_to(&frame, srv).unwrap();
        }
        while (got.load(Ordering::Relaxed) as usize) < N && t0.elapsed() < BUDGET {
            thread::yield_now();
        }
        ...
        assert!(elapsed < BUDGET, "{N} фреймов за {elapsed:?}");
```

**Разбор.** Отправитель крутит `yield_now()` в тесном цикле, пока счётчик приёма не догонит; рядом в том же процессе 4 воркера сервера, `housekeeping` и поток-читатель. При нехватке ядер busy-wait отбирает кванты у читателя → `got` перестаёт расти → отправитель ждёт до конца `BUDGET` и падает на `elapsed < BUDGET`. Симптом («20 000 фреймов за 30.000001866s») — ровно исчерпание бюджета. При нормальных условиях тест проходит за 1,27–1,30 с (23-кратный запас). Признаков остановки релея в коде нет: `relay_group` не блокируется ничем, кроме `state.read()` и мьютекса сессии (`lib.rs:2174-2182`).

**Вердикт: хрупкий тест + окружение** (busy-wait на общем CPU и wall-clock бюджет в функциональном наборе), не дефект релея. Проверяемо: печатать `got` раз в секунду при падении — если он растёт, а потом замирает, это голодание читателя, а не стопор релея; либо заменить busy-wait на блокирующее ожидание и поднять `BUDGET`.

**Рекомендация.** Убрать busy-wait, вынести нагрузочный характер в отдельный `#[ignore]`-тест/бенчмарк, а в функциональном наборе проверять «релей не встал» по счётчику `relayed` без wall-clock лимита.


## 4. Проверено — находок нет

Ниже — контроль, который я целенаправленно искал и **не** нашёл сломанным (с указанием, где именно проверено).

**Декодеры и границы (protocol).** `split_frame` строг: `body.len() == len`, короткий/длинный фрейм — ошибка (lib.rs:431-439); `Reader` не паникует: `bytes` проверяет остаток, `str`/`array`/`tail` — через него (690-756); `capacity_for` (706-708) применён **во всех** списковых декодерах (`dec_group_state`, `dec_group_list`, `dec_invite_list`, `dec_admin_info`, `dec_friend_list`, `dec_fed_groups`, `dec_server_hint`, `dec_mesh_seed`, `dec_mesh_section`, `MeshForward`, `Rpc::Nodes`) — счётчик из сети не раздувает аллокацию; циклы `for _ in 0..n` упираются в ошибку чтения на первом отсутствующем байте, т.е. O(1) после исчерпания. Строгие длины: `Hello3::decode` (`finish()`, handshake.rs:284-311), `Welcome::decode` (461-489, `n <= MAX_LINKS`), `dec_challenge`, `MeshHello::decode` (ровно 185), `MeshForward::decode` (`inner_len == remaining`, хопы, visited, получатель/источник не в visited), `Rpc::decode` (`remaining() == 0`), `dec_probe_req`/`dec_probe_resp` (ровно 64 / 24-56), `RotationLink::from_bytes` (ровно 160). Переполнений длин не нашёл: везде `usize`-арифметика после проверки `remaining()`; `u16::try_from` в `frame_header`/`MeshForward::encode`. Единственные паники в кодировании — `plain_frame` на body > u16 (lib.rs:441-448) и `assert!` в `seal_ctrl/seal_group`; все вызовы в сервере передают заведомо малые тела (CHALLENGE 17, UNSUPPORTED < 100, RESET 0, PROBE_RESP 56, WELCOME ≤ 1 442) — **с сети не достижимы**.

**Криптографические инварианты.** `was_contributory` проверяется на всех DH: static (lib.rs:270-277), эфемерный (handshake.rs:53-60), mesh (mesh.rs:437-444), федерация (`verify_and_dh`); нулевой/малого порядка ключ → отказ, а не предсказуемый секрет. Cookie привязан к `ip(16) || port || eph_pub || bucket` и принимается для текущего и предыдущего bucket'а (handshake.rs:192-227) — повтор HELLO3 с другого адреса не проходит (тест `lib.rs:5109-5128` это доказывает). Окно повторов: `check` до расшифровки, `commit` только после (lib.rs:3707-3728), корректно на `u64::MAX` и на прыжках (replay.rs:54-83 + тесты). Group-фрейм: AAD покрывает общий заголовок и `GroupHeader` (включая `epoch`), nonce = `src BE || counter LE` (lib.rs:599-639) — подмена epoch/src/dst ломает тег. FRAG: `count ≤ 256`, `idx < count`, строгие длины кусков, ≤ 8 сборок, таймаут 5 с, девятая вытесняет старую, память ≤ 8×281 600 (frag.rs:15-23, 158-221) — харнесс это же и проверяет.

**Рукопожатие как автомат.** Cookie проверяется **до** подписи (lib.rs:3416-3433); версия — до разбора раскладки (`hello_version`, 3396-3409); `UNSUPPORTED` не длиннее запроса (1226-1231, `find(|b| HDR_LEN + b.len() <= req_len)`); повтор HELLO3 той же попытки → только тот же WELCOME, не чаще 500 мс, `last_seen` не обновляется (3508-3522); HELLO3 закрытой попытки гасится `retired_eph` на 65 с ≥ времени жизни cookie (889-893, 111); смена identity на том же адресе и адреса у той же identity обрабатывается (3541-3557); DH и подпись WELCOME считаются **без** блокировки состояния (3460-3483). `resolve_pin` требует цепочку от закреплённого ключа с проверкой каждой подписи, сцепления и совпадения последнего звена с `server_ed/server_x` (handshake.rs:509-532) — «принять любой чужой ключ» невозможно; усечение цепочки до 8 звеньев — документированное ограничение (риск клиента, не сервера).

**Конкурентность и блокировки.** Порядок `state → fed` соблюдён: `fed` берётся под `state` (save_now 1687-1691, `fed_publish_dirty` 2422-2441, `relay_for_peer` из `relay_group` 2188-2190, `reconcile` 1533-1547), и **ни один** из 26 сайтов `sh.fed.lock()` в federation.rs не берёт `state` под собой (проверено grep'ом по `sh.state.` / `sh.fed.lock`: 1430 и 1534 — до `fed`, остальные — без `state`). Отправка всегда после снятия блокировки (`Outbox`, flush в конце обработчика). Индексы `s.sessions[&src]` / `s.groups[&gid]` / `get_mut(..).unwrap()` в мутациях безопасны: они под write-lock и после проверки наличия в том же обработчике (проверил все 30+ мест). Паники под локом, достижимой с сети, не нашёл; общая слабость вынесена в §5 (H-5).

**Персистентность.** `tmp + sync_all + rename` (persist.rs:272-284); `server.json.lock` держится на всё чтение-изменение-запись и в `save_now`, и в `rotate_key` (lib.rs:1669-1699, 529-563) — тест `rotate_key_ждёт_блокировку_записи_сервера` (5683) это фиксирует; смена ключа извне подхватывается (`keep_rotated_key` 1706-1731: `starts_with` + большая длина); `LOAD_MARGIN` = 2^16 защищает `epoch/rev` от повторной выдачи после краха (82, 1436-1437); `dirty` снимается **до** снятия снапшота, поэтому изменение, пришедшее после `swap(false)`, всё равно попадает в снапшот, а при ошибке записи `dirty` возвращается (1682-1698).

**Лимиты и анти-усиление.** Все значения `Limits::default` (lib.rs:178-206) совпадают с таблицей SECURITY.md §10 — дрейфа нет. Открытые ответы не длиннее запроса: CHALLENGE 17 < HELLO3 ~171, UNSUPPORTED ≤ запроса, RESET пуст, PROBE_RESP 24/56 < 64 (probe.rs:31-55), WELCOME — только после cookie. Лимитер IP: 16 шардов × 4096, при переполнении сначала выбрасываются восполнившиеся корзины, иначе отказ новому адресу (609-629); IPv6 считается по /64 (1214-1222) — обход «2^64 адресов» закрыт. Релей: коэффициент усиления ровно 1 (та же датаграмма уходит одному получателю, 2196-2204), проверка сессии + членства + `m.ip == h.src` (2152-2163), общий с федеративным релеем лимит на сессию (2174-2182). `MAX_MEMBERS` 253, `GID` 1..254, `MAX_FED_GROUPS` 512, `MAX_PEERS` 64, `MAX_PENDING` 32 — все проверяются. Эвикция надгробий (936-961) и `left` (2002-2019) не даёт расти `server.json`; баны/приглашения/друзья ограничены и чистятся по TTL (1858-2052).

**Аренда адресов.** Пул 64 770 (`valid`: 255×254, без `.0/.255` и служебной `/24`), `by_pub`/`by_ip` согласованы во всех операциях (`assign`/`revoke`/`get_or_alloc`/`set_member_ip`), адрес стабилен за identity и общий для всех групп (тест 7158), `reserved` уважается и при выдаче, и при исчерпании, `revoke` забывает `seen` (перевыдача не наследует чужой срок), `expired` не срабатывает на `ttl == 0` и на обратный ход часов, выселение идёт **до** `revoke` — два владельца одного адреса невозможны (1900-1955). Владелец группы не выселяется — иначе группа осталась бы без управляющего (1939-1946). Гонок с параллельными входами нет: `ip_for` вызывается только под write-lock.

**Федерация.** Тай-брейк встречных SRV_HELLO детерминирован (меньший ed — инициатор), повтор HELLO получает тот же ACK по подписи, запоздалый HELLO не перезаписывает initiator-сессию (federation.rs:596-675, 546-553); ACK принимается только от адреса ожидающей попытки и только с заявленным/закреплённым ed/x (694-740); `FED_GROUP_PUSH`/`DELTA` от другого источника по тому же uuid отвергаются (1087-1143) — «первая запись фиксирует origin» реализовано; своя группа не перезаписывается (1081-1086, 2473-2478); `FED_ADDR` проверяет `c.server == from` (1167-1169) и диапазон пула, конфликты решает меньшим id (1201-1290); `FED_RELAY` перепроверяет участников, `src/dst/epoch`, расшифровывает и **пересобирает** кадр под локальный gid с новым счётчиком (2789-2825) — «слепая пересылка» исключена; счётчик релея имеет 32 случайных старших бита на процесс, чтобы не столкнуться с последовательностью отправителя (1674-1685). Петли/дубли: `visited`, `hops ≤ 3`, `origin`-фильтр, `mine`-фильтр.

**TCP-фолбэк.** Фрейминг `u16 LE len`, `0` и `> max_frame` закрывают соединение (tcp.rs:400-416); `read_full` проверяет простой **и посреди кадра** (368-388) — slowloris не держит соединение; очередь ограничена (`sync_channel(queue_len)`, `try_send` → отбрасывание = потерянная датаграмма, 150-163); `max_conns`/`max_per_ip` (325-332); `remove_if(peer, id)` не даёт снять чужую (переиспользованную) запись; таймауты чтения/записи. **Дефект — только разделение адресного пространства (CORE-02).**

**Метрики/проба/сигналы.** 18 метрик, **ни одной метки** (labels) → кардинальность и PII в метках исключены by design (metrics.rs:134-260); `/metrics` рендерится из атомиков, `/healthz` = «все потоки живы И housekeeping недавно отмечался» (lib.rs:1035-1042), что ловит и падение воркера, и зависание; HTTP-парсер: `MAX_REQUEST` 4096, общий дедлайн 750 мс, только GET/HEAD, 404/405 (metrics.rs:341-432). Проба: ровно 64 байта, свежесть ±120 с, лимит по IP + общий plain-бюджет, ответ 24/56 ≤ запроса, сессии не создаёт (probe.rs). Сигналы: обработчик только ставит атомарный флаг, второй сигнал — немедленный выход с кодом 1 (`register_conditional_shutdown`), Windows ловит CTRL_CLOSE/LOGOFF/SHUTDOWN отдельным обработчиком с грейсом 4 с (signals.rs:44-58, 116-163).

**Авторизация мутаций.** Владелец-only: INVITE (4213), KICK/BAN (4427), UNBAN (4490), TRANSFER_OWNER (4508), RENAME (4531), DELETE (4543), ADMIN_INFO (3852). Членство: GET_GROUP (3838), GROUP_ATTACH (4169), JOIN_FED (3002). Вход: бан → отказ, приватная → приглашение, `full()` → отказ, `join_rate` на группу, `REJOIN_COOLDOWN`, живой `left` для приватной (4029-4094). Кик/бан снимают приглашение и `detached` (4436-4443), ротируют ключ с `revoke_prev` (4446-4449). Приглашения: лимит на группу и на цель, продление вместо дубля, `INVITE_LIST` окнами по 16 с `covers/next_from` (4192-4273). Друзья: взаимность, лимиты `max_friends`/`max_friend_reqs_per_target`, TTL (friends.rs:138-250).

**Качество тестов.** `crates/server/src/lib.rs` содержит ~3 800 строк интеграционных тестов на реальных UDP-сокетах с «сырым» клиентом (`Raw`, 4716-4897): анти-hijack (5109), повтор HELLO3 и лимит WELCOME (5160), повтор ctrl (5229), лимитер IPv6 /64 и «UNSUPPORTED не длиннее запроса» (5255), лимиты приглашений/банов/входов (5298, 5340), чехарда LEAVE/JOIN (5411), персистентность кика/бана/эпохи (5505, 5540), `rotate-key` под нагрузкой и при остановке (5683, 6359, 6398), загрузка `server.json` v2/v3 (6511, 7197), аренды (7268-7418), федерация end-to-end (7870, 8047). Тесты проверяют **состояние**, а не только отсутствие паники (например `s.by_pub[&a.pk] == a_addr`) — это сильная сторона. Пробелы: `tests/sigterm.rs` под `#![cfg(unix)]` (на Windows тест-бинарь пуст → путь `SetConsoleCtrlHandler`/финального сохранения на Windows не проверяется), тест зависит от формата лога (`Server code`) и от `kill` в PATH; нет тестов на CORE-02 (совпадение ip:port TCP/UDP), CORE-01 (исчерпание пинов), CORE-05 (предел сессий), CORE-04 (мутация реплики).

## 5. Гипотезы и вопросы к владельцу

**H-1 (гипотеза, не находка).** Причина детерминированного падения `группа_253_участника...` на Linux — буфер приёма (CORE-11), но **возможна** и серверная потеря: `send_to` не проверяет результат `send_to` сокета (`let _ = self.sock.send_to(...)`, lib.rs:1122) и не повторяет; при `ENOBUFS`/`EAGAIN` датаграмма теряется молча. Разделяет эксперимент из CORE-11. Если подтвердится серверная потеря — поднять CORE-10 до S2.

**H-2 (проверено, не дефект).** Пересборка кадра в `fed_deliver_relay` шифрует под чужим `src` со счётчиком со случайными старшими 32 битами (federation.rs:1674-1685) — совпадение nonce с последовательностью отправителя ~2^-32 на кадр. Осознанный компромисс; при желании — счётчик на `(uuid, src)` вместо `(uuid)`.

**H-3 (дизайн, требует решения).** `fed_accept_join` не проверяет, что запрошенный `pk` — клиент приславшего пира (это и невозможно без дополнительного подтверждения): любой закреплённый пир добавляет произвольные identity в наши публичные группы, с ротацией ключа на каждого (lib.rs:2898-2921). В связке с CORE-01 предусловие «быть закреплённым» стоит атакующему одного `SRV_HELLO`.

**H-4 (мелкое).** `handle_query(FRIEND_GROUPS)` (lib.rs:3807-3832) позволяет любому клиенту узнать, в каких **публичных** группах состоит заданный `ed_pub` — перечисление состава по ключу. Если это не задумано, нужен фильтр «только друзья».

**H-5 (системная слабость, не отдельная находка).** Все блокировки берутся как `.read()/.write()/.lock().unwrap()` (408 вхождений по установленным фактам). Паника под write-guard'ом отравляет лок, после чего **каждый** воркер умрёт на следующем `.unwrap()`, а процесс останется жив (главный поток ждёт сигнал): `/healthz` вернёт 503, но сервер фактически мёртв. Сейчас достижимой с сети паники под локом я не нашёл, но защиты нет: стоит либо `PoisonError::into_inner`, либо `catch_unwind` вокруг обработчика датаграммы с метрикой.

**H-6 (вопрос).** Эксплуатация с `--federate` на публичном интернете предполагается? Если да — CORE-01 обязателен к исправлению; если федерация задумана только для доверенных сетей, это нужно явно написать в SERVER.md / SECURITY.md §18.3 и в `--help`.

**H-7 (вопрос).** Ожидаемое поведение `Server::wait()` (CORE-09): внутренний API для тестов или поддерживаемый способ встраивания?

**H-8 (вопрос).** План по ретрансмиссии FRAG (CORE-10)? 253 участника × 255-байтовые поля уже дают 180 кадров и 205 КБ на одно `GROUP_STATE` — это 73 % от `FRAG_MAX_PAYLOAD` (281 600) и втрое больше дефолтного буфера приёма Windows.

**H-9 (вопрос, следствие CORE-11).** Считать ли отсутствие `getsockopt`-проверки фактического `SO_RCVBUF` дефектом? Сейчас клиент не знает, сколько ему дали, а при малом буфере единственный симптом — «нет состояния» без повтора (CORE-10). Минимальная мера: лог + метрика фактического размера, и таймер повторного `GET_GROUP` после входа.

## 6. Итог

Ядро написано заметно аккуратнее, чем предполагает статистика по `.unwrap()`: **все** сетевые декодеры проверяют остаток до чтения, не аллоцируют по счётчику из сети (`Reader::capacity_for` применён везде, где есть списки), не паникуют на обрезке/хвостах, а харнесс `fuzz_tests.rs` покрывает **каждый** декодер (включая федеративные и mesh) 20 000 мутациями на фиксированном seed. Криптографические инварианты на месте: `was_contributory` на всех DH, cookie привязан к адресу и эпохе ключа и проверяется до подписи, окно повторов сдвигается только после AEAD, заголовок группового кадра целиком в AAD, `resolve_pin` не принимает ключ без цепочки от закреплённого. Лимиты из SECURITY.md §10 совпадают с кодом один-в-один, релей не усиливает трафик (коэффициент 1), открытые ответы не длиннее запроса, лимитер IPv6 считается по /64, эвикция корзин и надгробий не даёт структурам расти бесконечно, аренда адресов уникальна и стабильна, персистентность — `tmp+fsync+rename` под общей блокировкой с `rotate-key`, а порядок блокировок `state → fed` соблюдён во всех 26 точках (ABBA-дедлока нет). Это сильный результат для 22 тысяч строк.

Главные риски лежат не в декодерах, а **на стыках подсистем**. Первый и самый серьёзный — федерация: TOFU-закрепление принимает любой самоподписанный `SRV_HELLO` (CORE-01), поэтому 64 чужих ключа навсегда занимают таблицу пиров (нет TTL, эвикции и CLI-снятия), а закреплённый «пир» получает право добавлять произвольные identity в наши публичные группы. Второй — TCP-фолбэк, который делит адресное пространство с UDP вопреки прямому предупреждению в шапке своего же модуля (CORE-02): при совпадении `ip:port` (один NAT/CGNAT) кадры одной сессии, включая `GROUP_STATE` с ключом группы, уходят в чужое TCP-соединение, а закрытие TCP снимает чужую UDP-сессию. Третий — отсутствие ретрансмиссии `FRAG` (CORE-10): `GROUP_STATE` на 253 участника — это 180 кадров и 205 КБ одним залпом, и потеря **одного** кадра лишает клиента ключа до следующего события группы; именно этот дефект стоит за детерминированным падением теста на Linux (CORE-11: тестовый `set_recv_buffer` на Unix — пустышка, поэтому тест меряет буфер ОС, а не код; продукт на обеих платформах буфер настраивает).

Отдельно стоит отметить «экономику доверия»: сессии создаются бесплатно и без предела (CORE-05), а дешёвые запросы (`MESH_INFO`, `LIST_GROUPS`) вызывают O(n)-обходы и сортировки под read-lock (CORE-06), причём `std::sync::RwLock` не гарантирует приоритет писателю — то есть CPU-DoS одной валидной identity потенциально тормозит входы и ротации ключей. Плюс системная хрупкость `.unwrap()` на отравленных локах (H-5): любая будущая паника под write-guard'ом превращается в отказ всех воркеров при живом процессе. Из мелочей: `Store::save` не синхронизирует каталог (CORE-07), `push_ctrl` в release молча теряет сообщение больше `FRAG_MAX_PAYLOAD` (CORE-08), `Server::wait()` не сохраняет состояние (CORE-09), тест `релей_под_нагрузкой` флейкует из-за busy-wait и жёсткого 30-секундного бюджета (CORE-12).

Итого: S1 не подтверждён (потенциал S1 есть только у CORE-02 при выполнимом совпадении `ip:port`); S2 — два (CORE-01, CORE-02); S3 — пять (CORE-03, CORE-04, CORE-05, CORE-06, CORE-10); S4 — пять (CORE-07, CORE-08, CORE-09, CORE-11, CORE-12). Приоритет исправлений: CORE-01 и CORE-02 (доверие/утечка), затем CORE-10 + CORE-11 (устойчивость и честность тестов), затем CORE-05/CORE-06 (пределы и стоимость запросов).
