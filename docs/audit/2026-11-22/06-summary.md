1. `tunnel-server`: `группа_253_участника_с_длинными_полями_приходит_через_frag` — **детерминированно

2. `tunnel-server`: `релей_под_нагрузкой` — 2 падения из 5 (в падении исчерпан весь бюджет 30 с),
   успешные прогоны 1.27–1.30 с. Busy-wait `yield_now()` + жёсткий бюджет в функциональном наборе.
3. `tunnel-client`: `mesh_e2e::e2e_потерянный_ack_не_снимает_путь` — 1 падение из 3 на Windows.
4. `tunnel-client`: `offline_ipc_e2e::очередь_уходит_демону_и_очищается` — падение в CI на macOS

## 3. Топ находок

Порядок — по «влияние × достижимость». Все ссылки проверены ведущим (кроме помеченных).

### 3.1. Обход бана через федеративную реплику — `BIZ-02` (S2, по влиянию S1)
`server/src/lib.rs:3019-3026` вставляет участника в группу реплики, `:3057` сразу шлёт ему
`GROUP_STATE` с текущим ключом; баны в `GroupSnap` не реплицируются, поэтому локальная проверка
`g.banned` (`:3005`) на реплике пуста. Origin при этом корректен — отклоняет забаненного
(`:2905`), но реплика уже отдала ключ. Предусловия: `--federate`, публичная группа, существующая
реплика. Обесценивает обещание `SECURITY.md §15 №10` «BAN запрещает вход».

### 3.2. TCP и UDP делят адресное пространство — `CORE-02` (S2, по влиянию S1)
Шапка `server/src/tcp.rs:18-23` прямо предупреждает: «TCP и UDP — РАЗНЫЕ пространства адресов,
сессии нужно ключевать по `Peer`». Интеграция делает наоборот: `lib.rs:405-413` передаёт
`peer.addr()` без транспорта, сессии ключуются по `SocketAddr`, `send_to` (`:1110-1123`)
угадывает транспорт по `is_live(Peer::Tcp(addr))`, а `drop_session_at` (`:1073-1079`) снимает
сессию по адресу. При совпадении `ip:port` (один NAT/CGNAT) кадры с ключом группы уходят чужому
TCP-соединению, а закрытие TCP сносит чужую UDP-сессию.

### 3.3. Потеря identity при ошибке чтения конфига — `CLNT-04` (S2, по влиянию S1)
`client/src/store.rs:385-394`: `Err(_) => Ok(Config::default())` ловит любую ошибку, а не только
«файла нет». `daemon/src/engine_backend.rs:274-281` видит `identity.is_none()`, генерирует новую
identity и немедленно пишет её поверх файла. Резервных копий нет. `EACCES`, `EIO`, sharing violation
антивируса — достаточно.

### 3.4. Права `server.json` задаёт umask — `SEC-01` (S2, по влиянию S1)
`server/src/persist.rs:222-228` и `:272-284` создают каталог и файл без режима; в `server.json`
лежат открытые seed'ы сервера и ключи всех групп. Контроль есть только в юните
(`UMask=0077`, `StateDirectoryMode=0700`); при ручном запуске из документации — 0644.

### 3.5. Загрузка `wintun.dll` по голому имени в повышенном процессе — `SEC-02` (S2)
`client/src/tun.rs:9-25`: если DLL нет рядом с exe — `load_from_path("wintun.dll")`.
`wintun 0.5.1` использует `libloading 0.8.9`, где `Library::new` = `LoadLibraryExW(name, NULL, 0)`
без `LOAD_LIBRARY_SEARCH_*`, то есть со стандартным порядком поиска, включающим CWD и `PATH`.
`tunnel-client run` требует администратора (`main.rs:1269`). Аудитор оценивал уверенность как
среднюю — проверка исходников libloading её повышает.

### 3.6. Таблица пиров федерации исчерпывается навсегда — `CORE-01` (S2)
`server/src/federation.rs:636-647`: любой входящий `SRV_HELLO` с самоподписью закрепляется
(TOFU), `MAX_PEERS = 64` (`:127`), пины персистентны, TTL/эвикции/CLI-снятия нет. 64 чужих ключа
блокируют федерацию с настоящими пирами; закреплённый «пир» через `JoinRequest → fed_accept_join`
(`lib.rs:2867-2946`) добавляет произвольные identity в публичные группы.

### 3.7. Тихая смерть туннеля при зелёном индикаторе — `DES-02` (S2)
`client/src/engine.rs:2386-2400`: `JoinHandle` потоков `rx`/`cmd` не сохраняется, живость не
проверяется. Паника в `rx_loop` оставляет процесс живым, `meta.connected` — «в сети», команды
уходят в мёртвый канал.

### 3.8. Офлайн-очередь теряет и перекладывает правки — `CLNT-03` + `DES-01` (S2)
`offline.rs:298-309` очищает очередь по сравнению `CfgView`, в котором нет `active_server`
(`snapshot.rs:372-395`) — `SwitchServer` теряется с сообщением «правки применены».
Плюс `DelServer{idx}`/`SetPrimaryServer{idx}` позиционные (`offline.rs:418-436`) и при
воспроизведении в конфиг демона с другим порядком серверов бьют по чужой записи.

### 3.9. Федеративные входы не расходуют `join_rate` — `BIZ-01` (S2)
`lib.rs:3002-3011` (`join_fed`) проверяет только `banned/private/full`; лимитер
`g.joins.take(join_rate, join_burst)` есть только в `join_group` (`:4091-4096`). Каждая пара
JOIN/LEAVE у владельца — ротация ключа, а для копии — заявка владельцу.

### 3.10. Невидимка виден в mesh-секции — `BIZ-03` (S2)
`lib.rs:2288-2303` формирует mesh-записи без проверки `invisible`, хотя `mesh_seed` (`:2331`)
её делает. Раскрываются факт онлайна и статический X25519-ключ.

### 3.11. TUI остаётся на прежней identity — `FRNT-1` (S2)
`client/src/remote.rs:359-363`: при смене identity демона печатается «перезапустите TUI», после
чего подписка продолжается (`:364-370`), а `my_pub`/`my_code` (`tui/app.rs:585-587`) остаются
старыми — `owner_is_me` (`:747`) считается по чужому ключу, `copy code` отдаёт прежний код.

### 3.12. Потеря FRAG-кадра = до 15 с без группы — `CORE-10` + `CLNT-05` + `CLNT-01` (S3)
Ретрансмиссии и ACK у FRAG нет (`frag.rs:147-151`), `GET_GROUP` отправляется один раз
(`engine.rs:3273-3289`), восстановление — только следующим `GROUP_LIST` (`LIST_EVERY = 15 с`).
Буфер приёма не перечитывается (`engine.rs:1588-1607`): на Linux 4 МиБ клампятся к `rmem_max`,
фактический размер неизвестен. Верификация: `CLNT-01` понижена с S2 до S3 — при `rmem_max = 212992`
эффективный буфер ≈ 425 КБ против ~205 КБ одного сообщения, продукт проходит, но запаса нет
(несколько больших групп подряд уже нет).

- **systemd-юнит**: `UMask=0077`, `StateDirectoryMode=0700`, `ProtectSystem=strict`,

- **Инженерная гигиена**: clippy `-D warnings` чист, `cargo deny`/`audit` чист, fmt чист,

## 7.1. Открытый вопрос, требующий решения владельца

`SEC-06`/`SEC-02` закрыты, но остался вопрос из отчёта безопасности (§6): в проверке адреса
источника `is_relay` условие включает `src == env.server()`, то есть участник, подделавший
адрес сервера, проходит проверку `src_ip`. Это укладывается в принятый риск №2 (общий ключ
группы), но заявленная митигация «приём только с известных адресов» в этом случае не работает.
Нужно решение: либо исключить `src == server` из `is_relay`, либо зафиксировать это в
`SECURITY.md §15 №2` как остаточный риск.

## 9. Предложение по процессу

1. **Сделать документацию проверяемой.** Число тестов, версия протокола, номера кадров и лимиты
   должны генерироваться или проверяться скриптом в CI: сейчас три документа дают три разных
   числа, а «акт приёмки» ссылается на сдвинутые строки.
2. **Разделить быстрые и медленные тесты.** Функциональный набор не должен падать от буфера ОС и
   бюджета 30 с; e2e с таймингами — отдельная джоба с `--test-threads=1` и повторами.
3. **Добавить джобу `nat-lab`** в CI (сейчас описана в TESTING, но не запускается) — это
   единственный способ держать L0–L2 под контролем.
4. **Машиночитаемая таблица контроля.** `SECURITY.md §17` уже почти таблица «контроль → файл:строка»;
   если довести до скрипта, дрейф («⏳ на сделанном») будет ловиться автоматически.
5. **Федерация как отдельная модель угроз.** Текущий `SECURITY.md` описывает её как расширение,
   но найденные `BIZ-01/02`, `CORE-01` показывают, что у неё свои границы доверия и свои лимиты.
