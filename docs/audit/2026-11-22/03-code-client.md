## 3. Находки

### S2

#### CLNT-01 · engine.rs (приём UDP / FRAG) · **S2** · уверенность **высокая**

**Evidence.** `crates/client/src/engine.rs:1583-1607`:

```
1583	/// Сколько просим у ядра под очередь приёма UDP. Длинное сообщение сервера
1584	/// (GROUP_STATE группы на 253 участника — ~215 КБ, ~175 кусков FRAG) приходит
1585	/// залпом; дефолтных 64 КБ на Windows не хватает, и часть датаграмм ядро
1586	/// выбрасывает — сборка FRAG не завершается никогда. 4 МиБ — с запасом на
1587	/// несколько таких сообщений подряд.
1588	const UDP_RECV_BUF: usize = 4 << 20;
1590	/// Просит у ядра увеличенный буфер приёма UDP. Ошибка не критична: остаётся
1591	/// дефолт, и длинные сообщения могут теряться (см. `UDP_RECV_BUF`).
1597	    unsafe {
1598	        let len = bytes as libc::c_int;
1599	        let _ = libc::setsockopt(
1600	            sock.as_raw_fd(),
1601	            libc::SOL_SOCKET,
1602	            libc::SO_RCVBUF,
1603	            (&raw const len).cast(),
1604	            size_of::<libc::c_int>() as libc::socklen_t,
1605	        );
1606	    }
```

Вызовы: `engine.rs:1903` (одноразовое `CtrlConn` для CLI) и `engine.rs:2347` (движок).
Windows-вариант (`engine.rs:1611-1626`) устроен так же — `let _ = setsockopt(… SO_RCVBUF …)`.

**Сценарий.** Клиент просит 4 МиБ под очередь приёма, но результат `setsockopt`
отбрасывается (`let _ =`), а фактический размер нигде не читается обратно (`getsockopt`
нет). На Linux `SO_RCVBUF` ограничен `net.core.rmem_max` (по умолчанию 212 992 Б;
ведущий подтвердил `rmem_default = 212992`): запрос 4 МиБ молча урезается до ~208 КиБ, и
`setsockopt` возвращает **успех** — проверка кода возврата тоже ничего бы не дала.
`GROUP_STATE` группы на 253 участника — ~215 КБ ≈ 175 датаграмм, приходящих залпом (это
записано в комментарии выше; `crates/server/src/lib.rs:4685`). Эффективный буфер
оказывается **того же порядка, что и один залп**, поэтому достаточно одной преемпции
потока-читателя, чтобы ядро выбросило кусок. Сборка FRAG в клиенте — «всё или ничего»
(`crates/protocol/src/frag.rs:211-213`): пропуск одного куска убивает всю сборку,
`FRAG_TIMEOUT` = 5 с её выбрасывает (`frag.rs:148-151`), повторной передачи кусков в
протоколе нет. На Windows потолка `rmem_max` нет, 4 МиБ применяются — отсюда наблюдаемая
асимметрия «Linux красный, Windows зелёный» (ведущий воспроизвёл: 4/4 падения на Linux).

**Влияние.** На Linux группы с большим составом (и любое длинное сообщение сервера:
`GROUP_STATE`, `INVITE_LIST`, `FRIEND_LIST`) систематически не доходят с первого раза:
группа остаётся без ключа до следующего `GROUP_LIST` (см. CLNT-05, до 15 с), трафик в неё не
идёт. При потере `GROUP_STATE` после `JOIN` участие в группе фактически не поднимается.
Это не только флейк теста — это же поведение у пользователя на Linux.

**Как проверить.** На Linux: `sysctl net.core.rmem_max` (ожидается 212992); прочитать
фактический буфер сокета движка (`ss -m` либо добавить `getsockopt(SO_RCVBUF)` в лог) —
увидите ~208 КиБ вместо 4 МиБ. Затем `sysctl -w net.core.rmem_max=4194304` и повторить
`cargo test -p tunnel-server группа_253_участника`: если тест зеленеет — причина подтверждена.
(Прогон на Linux — запрос к ведущему, сам не запускаю.)

**Рекомендация.** (1) Читать обратно `getsockopt(SO_RCVBUF)` и логировать расхождение;
(2) на Unix при нехватке прав пробовать `SO_RCVBUFFORCE` (CAP_NET_ADMIN), иначе писать в лог
явное предупреждение с требуемым `net.core.rmem_max`; (3) добавить требование
`net.core.rmem_max >= 4194304` в документацию по установке на Linux; (4) по существу
протокола — рассмотреть повторную передачу недостающих FRAG-кусков.

#### CLNT-02 · engine.rs + mesh.rs (приём mesh) · **S2** · уверенность **высокая**

**Evidence.** `crates/client/src/engine.rs:2508-2511` (mesh разбирается **до** любой
проверки источника) и `3843-3845`:

```
2508	    if proto::mesh::is_mesh(typ) {
2509	        handle_mesh_frame(env, src, typ, body);
2510	        return true;
2511	    }
...
3843	fn handle_mesh_frame(env: &Env, src: SocketAddr, typ: u8, body: &[u8]) {
3844	    let w = mesh_world(env);
3845	    let check = GroupCheck { groups: &w.groups };
```

`mesh_world` (`engine.rs:3797-3838`) на **каждую** датаграмму: берёт мьютекс групп,
аллоцирует `Vec<u32>` на каждую группу (`3807`), `Vec<[u8;32]>` всех участников
(`3809-3810`), затем берёт мьютекс DHT и **клонирует весь кеш контактов** (`3827`:
`let mut contacts = env.dht.lock().unwrap().contacts();`), плюс системный вызов `local_addr`
(`3837`). Проверка «свой ли это ed» — уже **после** этого, в `mesh.rs:540-547`:

```
540	        if !ctx.member(&hello.ed) {
541	            self.stats.dropped += 1;
542	            return None;
543	        }
544	        if hello.verify_from(&hello.ed, ctx.now_ms).is_err() {
```

**Сценарий.** Любой, кто знает UDP-эндпоинт клиента (он виден участникам группы в
`GROUP_STATE`: `endpoint` и `candidates`), шлёт датаграммы вида
`"TNL2" + typ 0x30 + len + тело` (`proto::mesh::is_mesh` — диапазон `0x30..=0x3F`,
`split_frame` требует только magic и совпадения длины). Каждая датаграмма в 153 байта
заставляет клиент: захватить мьютекс групп, аллоцировать ~20 КБ (кеш DHT до 256 контактов),
захватить мьютекс DHT, сделать `getsockname`. Для **участника группы** сверху добавляются
Ed25519-проверка подписи и X25519-DH (`mesh.rs:544-549`) — и всё это под взятым мьютексом
`env.mesh` (`engine.rs:3857-3860`).

**Влияние.** Поток `rx` — единственный путь приёма **всех** датаграмм, включая кадры сервера
(`dispatch` → `in_tx.send(Input::Server…)`, `engine.rs:2533-2540`). Пока он занят разбором
mesh-мусора, кадры сервера не доходят до движка; `SERVER_TIMEOUT` = 20 с (`engine.rs:84`)
означает, что достаточно sustained-флуда, чтобы клиент потерял сессию с сервером и ушёл в
реконнект — то есть туннель рвётся. Параллельно блокируются `route_packet`/`answer_dns` (им
нужен мьютекс групп) и `mesh_round`/`tick` (мьютекс mesh). Предусловие: знание эндпоинта
(участник группы или наблюдатель трафика); членство в группе для самого флуда **не
требуется**. Ограничения частоты mesh-кадров в коде нет.

**Как проверить.** Слать в сокет движка датаграммы `TNL2/0x30/len=0` с постороннего адреса с
частотой 10-50 тыс/с и измерять: (а) задержку доставки кадров сервера (`stats.rx_pkts`), (б) время
удержания мьютекса `groups` (таймер вокруг `mesh_world`), (в) рост RSS.

**Рекомендация.** (1) Проверять дешёвые предусловия **до** `mesh_world`: держать в `MeshState`
множество ed-ключей известных контактов/участников и отбрасывать кадры, чей открытый
заголовок не указывает на известного пира; (2) ограничить частоту mesh-кадров с одного
адреса (token bucket на IP, как `HINT_MAX_PER_WINDOW` для эпох) и общий бюджет mesh-кадров в
секунду; (3) строить `mesh_world` лениво/кэшировать (снимок меняется раз в `GROUP_STATE`, а не
на каждую датаграмму); (4) вынести разбор mesh в отдельную очередь, чтобы поток `rx` не
блокировался.

где `same` = `CfgView::from_cfg(&local) == snap.cfg` (`offline.rs:281-284`), а `CfgView`

При этом `Cmd::SwitchServer` меняет именно `active_server` (`offline.rs:499-503` →
`store.rs:297-315` `activate_server`).

**Сценарий.** Демона нет (штатный офлайн). Пользователь переключает сервер на тот, у которого
пустой список автовхода (свежедобавленный сервер — типичный случай): `apply_local` пишет
`active_server = B` и кладёт `SwitchServer{B}` в очередь. Появляется демон со своим
`client.json` (`active_server = A`, `autojoin = []`). Все поля `CfgView` совпадают →
`same == true` → очередь **очищается** с уведомлением «отложенные правки уже применены».
Демон остаётся на сервере A, `SwitchServer` не уходит никогда. TUI после `adopt` показывает
снимок демона (`offline.rs:189-201`), то есть сервер A, а в лог записано, что правки применены.
Правка потеряна, состояние интерфейса ложно.

**Влияние.** Молчаливая потеря пользовательской команды + ложное сообщение об успехе. Худший
вариант: пользователь думает, что он на приватном сервере B, а трафик идёт через A.
Воспроизводимость детерминированная (при пустых списках автовхода).

**Как проверить.** Тест по образцу `offline.rs:959` (`очередь_переживает_перезапуск_tui`):
локальный конфиг с двумя серверами и пустым `autojoin`; `eng.send(Cmd::SwitchServer{B})` без
демона; поднять заглушку демона с конфигом, где `active_server = A`; проверить, что очередь пуста
и `SwitchServer` не отправлен, а в событиях — «уже применены».

**Рекомендация.** Сравнивать полный конфиг, а не `CfgView`: добавить в `CfgView` `active_server`
(и `autojoin_by_server`) либо, что надёжнее, не очищать очередь по сравнению конфигов вовсе —
очищать только те команды, которые демон подтвердил, а неотправленные оставлять до `flush`.

и `crates/daemon/src/engine_backend.rs:274-285`:

**Сценарий.** `Err(_)` ловит **любую** ошибку чтения, а не только «файла нет»: `EACCES`/ACL после
смены владельца, `EIO`, временная недоступность сетевого домашнего каталога (`$HOME` на NFS),
`ERROR_SHARING_VIOLATION` на Windows (файл на мгновение занят антивирусом или вторым процессом).
В этом случае `load` возвращает `Ok(Config::default())` — «конфига нет». Демон видит
`identity.is_none()`, генерирует **новую** identity и немедленно сохраняет её поверх существующего
файла (`engine_backend.rs:278-280`). Старые `ed_seed`/`x_seed`, серверы и друзья теряются
безвозвратно; в лог пишется «создана новая identity». Резервных копий `client.json` в коде нет
(проверено: `grep -rn "bak|backup"` по `crates/client/src` даёт только тестовые пути
`profile.rs:569-576`).

**Влияние.** Потеря identity = потеря friend code, всех групп, друзей и доверия серверов;
восстановление невозможно. Требуется внешнее условие (ошибка чтения), поэтому S2, а не S1, —
но последствие по шкале S1.

**Как проверить.** Тест: каталог с валидным `client.json`; снять право на чтение (Unix: `chmod 000`;
Windows: запретить чтение в ACL для пользователя процесса) и запустить `DaemonEngine::open` —
ожидание `Err`, файл не изменён. Фактически `Ok`, файл перезаписан новой identity.

**Рекомендация.** Различать ошибки: `ErrorKind::NotFound` → `Config::default()`, всё остальное → `Err`
с путём и причиной (демон уже умеет показывать `{"engine": null, "error": …}`,
`engine_backend.rs:582-588`). Дополнительно — однократная резервная копия `client.json.bak` перед
первой перезаписью и запрет генерации новой identity, если файл существует, но не прочитан.

#### CLNT-05 · engine.rs (восстановление GROUP_STATE) · **S3** · уверенность **высокая**

**Evidence.** `engine.rs:3273-3289` — `GET_GROUP` отправляется один раз, запись из `want_group`
сразу удаляется:

```
3273	        if !st.want_group.is_empty() {
3274	            let due: Vec<u32> = st
3275	                .want_group
3276	                .iter()
3277	                .filter(|g| {
3278	                    st.last_get
3279	                        .get(g)
3280	                        .is_none_or(|t| now.duration_since(*t) >= GET_GROUP_EVERY)
3281	                })
3282	                .copied()
3283	                .collect();
3284	            for gid in due {
3285	                st.want_group.remove(&gid);
3286	                st.last_get.insert(gid, now);
3287	                st.send_ctrl(env, ctrl::GET_GROUP, &payloads::enc_gid(gid));
```

Повторно группа попадает в `want_group` только из `GROUP_LIST` (`engine.rs:4871-4889`, период
`LIST_EVERY` = 15 с, `engine.rs:62`). `NeedGroup` из пути данных возникает лишь для **уже
известной** группы (`engine.rs:2912-2916`: `if env.groups…contains_key(&gid)`), а неизвестная
группа отбрасывается молча (`engine.rs:5547-5549`).

**Сценарий.** `JOIN_GROUP` → сервер шлёт `GROUP_STATE` (~175 кусков FRAG) → один кусок теряется
(см. CLNT-01) → сборка умирает через 5 с → группы нет в `env.groups` → кадры группы отбрасываются,
`NeedGroup` не генерируется (группы нет), `want_group` пуст. Восстановление наступает только со
следующим `GROUP_LIST` (≤15 с), который увидит «своя группа, а у нас её нет» → `want_group` →
`GET_GROUP`. До этого — до 15+ с без ключа и без трафика, при этом в UI группа уже показана из
`GROUP_LIST` (`engine.rs:4890`).

**Влияние.** Нет отказоустойчивости запроса состояния: одна потерянная датаграмма стоит до 15 с
простоя группы; для сценария «потерялся `GROUP_STATE` после `JOIN`» клиент выглядит участником без
связи. Не блокер (самовосстановление есть), но именно это делает CLNT-01 заметным для
пользователя.

**Как проверить.** E2E: перехватить один FRAG-кусок `GROUP_STATE` (прокси, как `LossyProxy` в
`engine_e2e.rs`) и замерить время до появления ключа. Ожидание: 5 с (таймаут сборки) + до 15 с
(период списка).

**Рекомендация.** Хранить «ожидаю состояние» отдельно от `want_group`: после отправки `GET_GROUP` держать
запись с дедлайном (например, 2×`GET_GROUP_EVERY`) и повторять запрос, пока состояние не пришло; для
неизвестной группы, в которую мы входили (`JOIN_GROUP` отправлен), — тоже ставить дедлайн.

#### CLNT-07 · engine.rs + tun_linux/tun_macos (IPv6-оверлей) · **S3** · уверенность **высокая**

**Evidence.** Умолчание трейта — «ничего» (`engine.rs:1238-1242`), и Unix-реализации его не
переопределяют (`engine.rs:1363-1373` — только `inject` и `ensure_address`):

```
1238	    /// Назначить адаптеру IPv6 оверлея (`ipv6::v6_of`, префикс /64) для
1239	    /// своего IPv4 `v4`, заменив прежний. По умолчанию — ничего.
1240	    fn ensure_address6(&self, _v4: u32) -> Result<()> {
1241	        Ok(())
1242	    }
```

При этом готовые функции есть и не вызываются: `tun_linux.rs:247-248`
(`pub fn ensure_address6(&self, ip: Ipv6Addr, prefix: u8)`) и `tun_macos.rs:207-208`
(`pub fn ensure_address_v6(&self, ip: Ipv6Addr, prefix: u8)`) — их сигнатура не совпадает с трейтом
(`u32`), поэтому из движка (`engine.rs:5396`) они недостижимы. Переопределён только Windows
(`engine.rs:1297-1303`, через `ipv6::cmd_add_windows`).

**Сценарий.** Linux/macOS: движок вызывает `ensure_address6(my_ip)` → no-op → IPv6-адрес оверлея на
адаптер не назначается. Пакеты IPv6 в оверлее при этом продолжают приниматься и инжектиться
(`route_target`/`source_member` работают), но ОС их отбрасывает (нет адреса и префикса на
интерфейсе), а исходящий IPv6-трафик приложение не может породить вовсе. Документация
утверждает обратное: `docs/NETWORKING.md:64` — «На адаптер назначается один IPv6-адрес с
префиксом `/64` (Windows, Linux, macOS)».

**Влияние.** Заявленная функция не работает на 2 из 3 платформ, без диагностики (ошибки нет —
`Ok`). `ping6` до адреса пира не проходит; `TROUBLESHOOTING.md:118` списывает это на «может не
применяться в версии клиента», то есть дрейф спеки уже начал маскировать дефект.

**Как проверить.** На Linux: `ip -6 addr show <адаптер>` после входа в группу — ожидается
`fd66:766c:696e::<a>:<b>/64`, фактически адреса нет. (Прогон — запрос к ведущему.)

**Рекомендация.** Либо реализовать `ensure_address6(u32)` для `LinuxTun`/`Utun` через существующие
`ensure_address6`/`ensure_address_v6` (`ipv6::v6_of` даёт адрес), либо честно ограничить документацию
Windows и убрать обещание из `NETWORKING.md`/`ARCHITECTURE.md`.

#### CLNT-08 · tcp_link.rs (очередь приёма TCP) · **S3** · уверенность **средняя**

**Evidence.** `tcp_link.rs:80` — неограниченный канал, `tcp_link.rs:195-211` — читатель кладёт в него
всё, что пришло, без обратного давления:

```
80	        let (tx, rx) = mpsc::channel();
...
205	        let mut frame = vec![0u8; len];
206	        if s.read_exact(&mut frame).is_err() || tx.send(frame).is_err() {
207	            break;
208	        }
```

**Сценарий.** TCP-фолбэк включается, когда UDP молчит (`should_fallback`). Сервер (или on-path на
TCP-соединении) пишет кадры до 4096 байт так быстро, как позволяет канал; потребитель
(`tcp_rx_loop`, `engine.rs:2548-2563`) обрабатывает по одному кадру за итерацию и складывает их во
**вторую** неограниченную очередь `in_tx` (`engine.rs:2312`, `mpsc::channel::<Input>()`). Обе очереди
растут без предела: память клиента ограничена только объёмом входящего потока.

**Влияние.** Исчерпание памяти/OOM клиента при hostile-сервере или on-path атакующем на TCP-плече.
Предусловие сильное (нужен контроль над сервером или пути), поэтому S3; при этом `SECURITY.md`
§15 #14 описывает TCP-фолбэк как «те же фреймы и AEAD», не упоминая отсутствие предела очереди.

**Как проверить.** Тест: поддельный сервер принимает соединение и пишет кадры максимального размера
в цикле; замерить RSS клиента через 10-30 с.

**Рекомендация.** Ограничить очередь (`mpsc::sync_channel(N)` с блокировкой читателя при заполнении — TCP
сам даст обратное давление) и/или бюджет байт/с на приём до аутентификации кадра; при переполнении
рвать соединение, а не копить.

## 4. Проверено — находок нет

- **Правила приёма группового кадра** (`engine.rs:5532-5706`): порядок 1-6 соблюдён, расшифровка
  до проверки окна, дедуп (issue #25) заполняется только после `win.commit`, повтор получает ACK,
  а не NACK; `expect("участник проверен")` (`5623`) защищён проверкой `5588` и ничем не
  инвалидируется между ними.
- **Окна повторов принадлежат ключу, а не эпохе** (`engine.rs:245-249`, `GroupSess::rx_window`):
  откат номеров после падения сервера окна прежнего ключа не наследует; `KeyLog`
  (`engine.rs:326-349`) возвращает счётчик и окна при возврате к отслуженному ключу (повтор nonce
  был бы раскрытием трафика).
- **Grace прошлого ключа** (`engine.rs:496-530`): `keep` только при переходе ровно на `epoch+1` и без
  `revoke_prev` — ключ, который знает исключённый при скачке эпохи, в grace не остаётся.
  Соответствует §15 #6.
- **`epoch_hint`/`hint_due`** (`engine.rs:544-584`): сигнал GET_GROUP только от правдоподобного источника
  (релей или известный адрес пира), пауза с удвоением и предел 8/мин — усиления «заставь тянуть
  GROUP_STATE» нет.
- **Арифметика IP/MTU и срезы буферов** (`ipv6.rs:32-154`, `dns.rs:73-107`, `dns.rs:166-192`): все
  срезы защищены проверками длины, `IHL`/`total length` сверяются с фактической длиной, `parse_qname`
  ограничен 255 байтами и не уходит в бесконечность, сжатие (указатели) отклоняется. Паник на
  враждебном трафике не нашёл.
- **Инъекция в TUN** (`engine.rs:5691-5696`): ошибка `inject` не роняет движок; DNS-ответ
  (`answer_dns`, `engine.rs:5972-6012`) строится только для пакетов к `100.66.0.53:53` и корректно
  считает контрольные суммы.
- **Анти-спуфинг источника данных** (`engine.rs:5572-5574`): `source_member(payload)` обязан совпасть
  с `h.src` — и для IPv4, и для IPv6-оверлея.
- **Остановка потоков** (`engine.rs:2379-2445`, `1218-1225`, `6226-6244`): при ошибке `first_connect`
  выставляется `quit`, поток `cmd` завершается по закрытию канала, `rx` — по флагу с 250 мс
  таймаутом; `Drop for Engine` будит движок `Cmd::Quit`. Утечки потоков/сокетов не нашёл.
- **Неограниченные коллекции**: `sessions` ≤ 256 (`mesh.rs:51`), `budgets` ≤ 8 (`mesh.rs:459-461`),
  `forwards` ≤ 128 (`mesh.rs:78`), `pending_hs`/`pings`/`routes` чистятся по TTL (`mesh.rs:1155,
  1209-1212`), кольца дедупа ограничены 64 потоками × 64 записи (`engine.rs:252-259, 470-487`), окна
  повторов — по числу участников под ключом. Списки друзей и приглашений на клиенте не
  ограничены, но ограничены сервером (`max_friend_reqs_per_target = 64`, `max_friends = 512`,
  `crates/server/src/lib.rs:202-203`) — дефектом не считаю.
- **Релей** (`mesh.rs:916-1097`): `hops`/`visited`/`loop` проверяются, `inner` валидируется по открытому
  заголовку (`check_group`), бюджет списывается на входе и на выходе, `MAX_PENDING_FORWARDS`/
  `FORWARD_WAITERS_MAX` ограничивают записи. Релеить «не то» нельзя: `inner` зашифрован ключом
  группы, реле его не расшифровывает.
- **Дедупликация путей (issue #25)** (`engine.rs:5848-5967`, `path.rs:802-831`): `fallbacks` не выдаёт
  дубликатов (Direct, Server, максимум один `PeerRelay`), кадр запечатывается один раз, копии —
  те же байты; `DUP_TARGETS_MAX`/`DUP_COST_RATIO`/`caps::DUP` — все предусловия проверены.
  `e2e_дублирование_по_двум_путям_доставляет_один_раз` проверяет и `dup_dropped`, и `dup_sent` (тест не
  может позеленеть вхолостую).
- **Гистерезис и пин** (`path.rs:888-1052`, `789-831`): пин сильнее автоматики, «мёртвый» пин даёт
  `PathLost` и откат, но не удаляется; `dwell` не блокирует переключение со сломанного пути.
- **Проба** (`probe.rs:104-164`): ответ привязан к nonce и к адресу пробы, чужой ключ даёт
  `KeyMatch::Mismatch` (не «подлинность»), `src` сознательно игнорируется (NAT) — это соответствует
  §15 #18 «подсказка, а не доказательство».
- **Хранилище: битый JSON** обрабатывается корректно (`store.rs:388` возвращает `Err` через `?`, демон
  показывает `{"engine": null, "error"}`) — проверял специально, потому что это единственный «соседний»
  сценарий с CLNT-04.
- **Миграции** (`store.rs:404-425`): алиас, равный friend code, очищается; отсутствующий `state`
  читается как `Legacy`; все поля `Config` с `serde(default)`.
- **Друзья/приглашения** (`friends.rs:205-252`, `invites.rs:145-171`): повтор обновляет без дубликата,
  встречные заявки дают дружбу, отказ помнится 5 с, окно списка не возвращает отклонённое;
  `on_synced` снимает неподтверждённое.
- **E2E-каркас** (`engine_e2e.rs:169-190`): `wait` блокирующий, с таймаутом 10 с и дампом всех событий
  при провале — «зелени вхолостую» не даёт; негативные проверки опираются на счётчики
  (`dup_dropped`, `tx_pkts`), а не на «ничего не пришло».

## 5. Гипотезы и вопросы к владельцу

### 5.1. Ответ на запрос ведущего (Linux-флейк `группа_253_участника…`)

**Подтверждаю данные ведущего по коду:** `UDP_RECV_BUF = 4 << 20` (`engine.rs:1588`), вызовы —
`engine.rs:1903` (`CtrlConn`) и `engine.rs:2347` (движок), результат `setsockopt` отброшен
(`let _ =`, комментарий «Ошибка не критична» на `1590-1591`), фактический размер не читается.

**(1) Что делает движок, если `setsockopt` не удался и часть FRAG потеряна.** Частичного применения нет:
`GROUP_STATE` разбирается только из полностью собранного сообщения (`engine.rs:4826-4834` →
`payloads::dec_group_state`), сборка «всё или ничего» (`frag.rs:211-213`). Если кусок потерян: через
`FRAG_TIMEOUT` = 5 с сборка выбрасывается (`frag.rs:148-151`), сообщение не всплывает, события нет
(только `eprintln` при `--debug`, `engine.rs:1857-1862`). Повторный GET_GROUP по таймауту
**не срабатывает**: `GET_GROUP` отправляется ровно один раз на запись `want_group`, запись тут же
удаляется (`engine.rs:3284-3287`). `GET_GROUP_EVERY` = 1 с (`engine.rs:132-133`) — это
ограничитель **частоты**, а не таймер повтора. Восстановление — только через `GROUP_LIST`
(`LIST_EVERY` = 15 с, `engine.rs:62`), который увидит «своя группа с другой ревизией» или «своей
группы у нас нет» и снова положит gid в `want_group` (`engine.rs:4871-4889`). Итог: ключ
появляется не раньше следующего `GROUP_LIST`, то есть **до ~15 с + RTT** после потери, а не через 1 с.

**(2) Может ли группа остаться без ключа навсегда.** В штатном случае нет: `GROUP_LIST` приходит
периодически, и `reconcile`/`want_group` восстановят состояние (в том числе для группы, которой у
нас нет вовсе). «Навсегда» возможно только если сам `GROUP_LIST` перестанет доходить (обрыв) или
если группа есть у нас с **той же** ревизией, но без ключа — такого состояния код не создаёт: запись
в `env.groups` появляется только из `GROUP_STATE` (`engine.rs:4826-4834`), то есть всегда с ключом.
Отдельно: для неизвестной группы `NeedGroup` из пути данных не возникает
(`engine.rs:2912-2916` требует `contains_key`), кадры отбрасываются (`engine.rs:5547-5549`) —
то есть «без ключа, но с трафиком» не бывает, бывает «без группы и без трафика» (CLNT-05).

**(3) Пределы одновременных сборок FRAG.** `FRAG_MAX_PENDING` = 8 сборок на **каждый** набор ключей
(`crates/protocol/src/frag.rs:21`; `Reassembler` живёт в `Keyset`, `engine.rs:1759-1770`, наборов ≤
`MAX_KEYSETS` = 4, `engine.rs:153`), `FRAG_MAX_COUNT` = 256 кусков, `FRAG_MAX_PAYLOAD` = 281 600 Б,
`FRAG_TIMEOUT` = 5 с. При переполнении девятая сборка **вытесняет самую старую** (`frag.rs:188-193`) —
молча, без события; кусок, противоречащий начатой сборке, уничтожает её (`frag.rs:175-181`).
Память ограничена сверху 8 × 281 600 ≈ 2,2 МБ на набор ключей. Для сценария с 253 участниками лимиты
ни при чём: там одна сборка.

**Классификация.** По моей оценке это **дефект кода клиента (CLNT-01) + хрупкость теста**, а не
«влияние нагрузки»: тест сам просит 4 МиБ (`crates/server/src/lib.rs:4745` вызывает тот же
`set_recv_buffer`), то есть авторы уже знали про залп; на Linux запрос молча урезается ядром, и запаса
не остаётся. Разделяющая проверка: `sysctl net.core.rmem_max` + `getsockopt(SO_RCVBUF)` на сокете
теста/клиента. Если после `net.core.rmem_max=4194304` тест зеленеет — виноват буфер (CLNT-01); если
остаётся красным — копать темп отправки сервером (это уже серверная сторона, не моя область).

### 5.2. Гипотезы (не подтверждены кодом, требуют проверки)

1. **`dup_extra_paths` может послать копию тому же релею.** `chosen` берётся в `route_packet`
   (`engine.rs:5768`), а `fallbacks` — позже (`engine.rs:5950`); если между ними `paths_round` в
   потоке движка пересчитал `t.peer.via`, то `chosen` = `PeerRelay{A}`, а в `fallbacks` уже
   `PeerRelay{B}` — кадр уйдёт релею, выбранному `try_relay`, и копией — B. Получатель
   дедуплицирует, так что это только лишний трафик; в находки не выношу.
2. **`last_hs` в `MeshState` не чистится** (`mesh.rs:351`): записи удаляются только неявно, при
   переполнении DHT; рост ограничен числом контактов (≤256), но при длинной жизни клиента и
   смене адресов может накапливаться. Нужен замер.
3. **`PeerSess::knows`** определяет «свой адрес пира» по `endpoint`/`candidates` от сервера
   (`engine.rs:229-247`); если сервер отдаёт кандидатов широко (LAN), круг адресов, с которых
   принимается кадр, шире одного пира — усиления не даёт (ключ группы всё равно нужен), но стоит
   подтвердить на серверной стороне.

### 5.3. Вопросы к владельцу

1. Планируется ли повторная передача недостающих FRAG-кусков (сейчас потеря одного куска стоит до
   15 с простоя группы)? Если нет — нужно ли хотя бы событие «сообщение сервера не собрано» вместо
   `eprintln` под `--debug`?
2. `SO_RCVBUF`: сознательно ли оставлена «мягкая» деградация на Linux (CLNT-01), или установка на Linux
   должна требовать `net.core.rmem_max`? Сейчас в документации этого требования нет.
3. Очередь офлайн-правок: должна ли она переживать смену сервера (CLNT-03) или `SwitchServer`
   намеренно не повторяется демону?
4. `client.json` с `ed_seed`/`x_seed` пишется без `fsync` и без резервной копии (CLNT-10/CLNT-04):
   приемлемо ли это, учитывая, что потеря файла = потеря identity?
5. IPv6-оверлей на Linux/macOS (CLNT-07): это «ещё не подключено» или «не планируется»? От ответа
   зависит, править код или документацию.

## 6. Итог

Ядро клиента — зрелый код с необычно внимательным отношением к инвариантам: окна повторов
привязаны к ключу, а не к номеру эпохи; дедуп (issue #25) заполняется только после успешного
`commit`; релей проверяет `hops`/`visited`/`check_group` и не может подменить `inner`; `KeyLog` не даёт
повторно использовать nonce при возврате к старому ключу; правила приёма §8 реализованы в
правильном порядке, и на враждебном трафике я не нашёл ни одной паники (все срезы в
`dns.rs`/`ipv6.rs` защищены, `expect` в горячем пути закрыт проверкой выше). E2E-набор (36 тестов
движка, 12 mesh, 3 пробы) устроен так, что не может позеленеть вхолостую: ожидание событийное
с дампом при провале, негативные проверки опираются на счётчики.

Главный риск — не логика протокола, а **границы ресурсов на входе**: единственный поток `rx`
обслуживает и сервер, и mesh, а mesh-кадры разбираются до любой проверки источника (CLNT-02),
поэтому 153-байтовая датаграмма от постороннего стоит клиенту ~20 КБ аллокаций, двух мьютексов
и (для участника) Ed25519+X25519 — без ограничения частоты. Тот же класс — неограниченная очередь
TCP-канала (CLNT-08). Второй по важности сюжет — **устойчивость длинных сообщений сервера**:
запрос 4 МиБ на `SO_RCVBUF` на Linux молча урезается ядром (CLNT-01), а восстановление после
потерянного `GROUP_STATE` возможно только через 15-секундный `GROUP_LIST` (CLNT-05), из-за чего
группа остаётся без ключа; это же объясняет Linux-only падение теста на 253 участника.

Третий сюжет — **локальное состояние и identity**: любая ошибка чтения `client.json` трактуется как
«конфига нет», что ведёт к генерации новой identity и перезаписи файла (CLNT-04), а офлайн-очередь
очищается по сравнению, не включающему `active_server`, из-за чего `SwitchServer` теряется с сообщением
«правки применены» (CLNT-03). Оба дефекта дают молчаливую потерю данных при полностью «зелёном»
интерфейсе.

Принятые риски из `SECURITY.md` §15 (seed'ы в открытом `client.json` и права по umask — §12 и #4;
отравление DHT — #20; подделка пробы — #18; релей видит метаданные — #16; отсутствие PFS у групповых
ключей — #11) я дефектами **не считаю**: код ведёт себя ровно так, как описано. Находки
CLNT-01…CLNT-10 — это места, где заявленный контроль отсутствует или где поведение кода
расходится с документацией.
